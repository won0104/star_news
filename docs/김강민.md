# 지식그래프 기반 추천 시스템 학습 정리 (.feat GPT talk) (26.08.24 ~ 26)

> 지식그래프 기반 뉴스 추천 서비스를 설계하기 위해 학습한 내용을 정리한 TIL 문서입니다.  
> 핵심 개념부터 뉴스 데이터를 그래프로 만드는 과정, 추천 후보 탐색, 모델 기반 추천으로의 확장까지 정리했습니다.

---

## 1. 한눈에 보는 핵심 정리

- **지식그래프(Knowledge Graph)** 는 객체(Node)와 관계(Edge)를 중심으로 정보를 연결하는 구조다.
- 뉴스 추천에서는 **기사 자체도 Node** 가 되고, 기사에서 추출된 기업·인물·주제·사건도 Node가 된다.
- 제목, 날짜, URL처럼 단순한 설명값은 **Property** 로 둔다.
- 다른 객체와 계속 연결해 탐색하거나 추천에 활용할 대상은 **Node** 로 두는 것이 좋다.
- **Ontology** 는 그래프 안의 개념, 관계, 의미, 규칙을 정의하는 체계다.
- 뉴스 원문은 보통  
  **NER → Entity Linking → Relation Extraction → Ontology Mapping → Knowledge Graph 저장**  
  순서로 그래프로 변환한다.
- 추천 후보는 **Neighbor, Hop, Path, Meta-path, Subgraph** 탐색으로 찾을 수 있다.
- 초기 서비스는 **Rule/Path 기반 추천** 으로 시작하고, 사용자 행동 데이터가 쌓이면 **ML Ranking / GNN** 으로 확장할 수 있다.
- 중요한 설계 원칙은 **Class는 보수적으로 유지하고, Entity와 Relation을 점진적으로 확장하는 것** 이다.

---

# Part 1. 지식그래프의 기본 개념

## 1-1. 지식그래프란?

RDB가 **테이블과 조인**을 중심으로 데이터를 연결한다면, 지식그래프는 **Node - Edge - Node** 구조를 중심으로 데이터를 표현한다.

### RDB 방식

```text
Article Table
Company Table
Article_Company Table
```

### 지식그래프 방식

```text
[Article A] ──MENTIONS──> [NVIDIA]
[Article A] ──ABOUT─────> [AI]
[NVIDIA] ──BELONGS_TO──> [Semiconductor]
```

지식그래프의 핵심은 단순히 데이터를 이어놓는 것이 아니라, **객체와 관계의 의미를 명확하게 설계하고 그 연결을 탐색하는 것** 이다.

---

## 1-2. Node, Edge, Property

| 개념 | 의미 | 뉴스 추천 예시 |
| --- | --- | --- |
| Node | 그래프 안의 객체 | 기사 A, 삼성전자, NVIDIA, AI, 반도체 |
| Edge / Relation | 객체 사이의 관계 | 기사 A - MENTIONS - 삼성전자 |
| Property | 객체나 관계를 설명하는 값 | 기사 제목, 작성일, URL, confidence |
| Label / Type | Node의 종류 | Article, Company, Person, Topic |

### 기사도 Node인가?

뉴스 추천에서는 **기사 자체도 Node로 두는 것이 자연스럽다.**

추천 시스템이 최종적으로 추천하는 대상이 기사이기 때문이다.

```text
[기사 A] : Article
  title: "엔비디아 차세대 GPU 공개"
  published_at: "2026-08-23"
  url: "..."

[기사 A] ─MENTIONS→ [NVIDIA]
[기사 A] ─MENTIONS→ [Jensen Huang]
[기사 A] ─ABOUT────→ [AI]
[기사 A] ─ABOUT────→ [반도체]
```

### Node와 Property를 구분하는 기준

다음 질문으로 구분하면 이해하기 쉽다.

> **이 값을 앞으로 추천 경로에서 탐색하거나 연결할 것인가?**

- 그렇다면 → **Node 후보**
- 단순 설명값이라면 → **Property 후보**

예를 들면:

- 제목, 날짜, URL → Property
- 삼성전자, NVIDIA, 반도체 → Node

# Part 2. Triple, RDF, Property Graph

## 2-1. Triple

Triple은 지식그래프에서 하나의 사실을 표현하는 기본 단위다.

```text
Subject - Predicate - Object
```

즉,

```text
주어 - 관계 - 목적어
```

예시:

```text
(NVIDIA, CEO_OF, Jensen Huang)
(ArticleA, MENTIONS, NVIDIA)
(NVIDIA, BELONGS_TO, Semiconductor)
```

---

## 2-2. RDF

**RDF(Resource Description Framework)** 는 세상의 지식을 Triple의 집합으로 표현하는 표준 방식이다.

RDF에서는 속성도 Triple로 표현할 수 있다.

```text
ArticleA ─title──────→ "엔비디아 신제품 공개"
ArticleA ─date───────→ "2026-08-23"
ArticleA ─MENTIONS───→ NVIDIA
ArticleA ─ABOUT──────→ AI
```

---

## 2-3. Property Graph

Property Graph는 **Node와 Edge를 명확한 객체로 다루고, Node와 Edge 각각에 Property를 붙이는 방식** 이다.

Neo4j가 대표적인 Property Graph Database다.

```text
[ArticleA]
 title: "엔비디아 신제품 공개"
 published_at: "2026-08-23"

[ArticleA]
   │
   │ MENTIONS
   │ confidence: 0.97
   │ importance: 0.91
   ▼
[NVIDIA]
```

---

## 2-4. RDF와 Property Graph 비교

| 구분 | RDF | Property Graph |
| --- | --- | --- |
| 기본 단위 | Triple | Node + Edge + Property |
| 속성 표현 | 속성도 Triple로 표현 | Node/Edge Property로 표현 |
| 강점 | 표준화, 외부 지식 공유, Ontology | 서비스 구현, 탐색, Edge 속성 관리 |
| 대표 질의 | SPARQL | Cypher |
| 대표 활용 | Wikidata, DBpedia, Semantic Web | Neo4j 기반 서비스 그래프 |

핵심 차이는 관계의 다양성이 아니라 **표현 철학** 에 있다.

- RDF → 모든 것을 Triple로 표현
- Property Graph → Node와 Edge에 Property를 직접 부여

---

# Part 3. Ontology - 그래프의 의미와 규칙

## 3-1. Ontology란?

Ontology는 단순한 관계 규칙보다 조금 더 넓은 개념이다.

> 무엇이 존재하고, 그것들이 어떤 의미를 가지며, 어떤 관계를 맺을 수 있는지 정의한 체계

### 핵심

```text
Schema = 구조
Ontology = 구조 + 의미 + 규칙
```

---

## 3-2. Schema와 Ontology의 차이

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| Schema | 어떤 Node/Edge 구조를 쓸지 정의 | Article - MENTIONS - Company |
| Ontology | 구조의 의미와 규칙까지 정의 | MENTIONS의 출발점은 Article, 도착점은 Entity |
| Inference | 규칙을 이용해 숨은 사실을 추론 | SemiconductorCompany이면 Company이기도 함 |

실제 데이터는 다음과 같이 저장될 수 있다.

```text
[기사 A] ─MENTIONS────→ [삼성전자]
[기사 A] ─PUBLISHED_BY→ [동아일보]
```

Ontology에서는 관계의 규칙을 정의한다.

```text
MENTIONS      : Article → Entity
PUBLISHED_BY  : Article → NewsOrganization

Company            : Entity의 하위 개념
NewsOrganization   : Organization의 하위 개념
```

즉,

- 실제 Edge → 데이터
- Ontology → 어떤 종류의 Node끼리 어떤 관계를 가질 수 있는지 정의하는 규칙

---

## 3-3. Domain과 Range

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| Domain | 관계의 출발 Node Type | CEO_OF의 Domain = Person |
| Range | 관계의 도착 Node Type | CEO_OF의 Range = Company |
| Class | 개념의 종류 | Person, Company, Article |
| Instance | 구체적인 실제 대상 | Jensen Huang, NVIDIA, 기사 A |

---

## 3-4. Ontology가 추천에 중요한 이유

Ontology가 있으면 직접 연결되지 않은 것도 의미적으로 확장할 수 있다.

### 직접 저장된 사실

```text
NVIDIA ─INSTANCE_OF→ SemiconductorCompany
```

### Ontology 규칙

```text
SemiconductorCompany ─IS_A→ Company
Company ─IS_A→ Organization
```

### 추론 가능한 사실

```text
NVIDIA는 Company다.
NVIDIA는 Organization이다.
```

이런 구조가 있으면 NVIDIA와 직접 연결된 기사뿐 아니라 **반도체, AI 인프라, HBM, 관련 기업** 등으로 추천 범위를 확장할 수 있다.

> Ontology는 노드를 직접 이어놓은 선이 아니라,  
> 그 선이 어떤 의미인지 판단하고 숨은 연결까지 추론하게 해주는 규칙집이다.

---

# Part 4. Class, Entity, Topic 범위 정하기

## 4-1. Node가 많아지는 것과 Class가 많아지는 것은 다르다

뉴스에는 인물, 기업, 기관, 사건, 주제 등이 계속 등장하기 때문에 Entity Node 수는 매우 많아질 수 있다.

하지만 그렇다고 Class까지 계속 늘릴 필요는 없다.

> **Class는 적게 유지하고, 실제 다양성은 Entity Node와 Relation으로 표현한다.**

---

## 4-2. Class / Node / Property 구분 기준

| 판단 질문 | Class 후보 | Node 후보 | Property 후보 |
| --- | --- | --- | --- |
| 여러 구체적 대상을 분류하는 타입인가? | Person, Company, Article | 삼성전자, 손흥민 | - |
| 공통 규칙을 적용해야 하는가? | Company - PRODUCES - Product | - | - |
| 그 자체를 탐색하고 연결하고 싶은가? | - | 반도체, K-pop, 금리 | - |
| 단순 객체 설명값인가? | - | - | 제목, 작성일, URL |
| 일시적 지위나 역할인가? | 필요하면 Role Class | 대통령, 축구선수 Role Node | - |

---

## 4-3. 도메인은 Topic Node로 다루기

정치, 경제, IT, 스포츠, 연예 같은 대분류는 Class보다 **Topic Node** 로 두는 편이 자연스럽다.

```text
(:Topic {name: "정치"})
(:Topic {name: "경제"})
(:Topic {name: "IT"})
(:Topic {name: "스포츠"})
(:Topic {name: "연예"})
```

세부 Topic은 다음과 같이 연결할 수 있다.

```text
[AI] ─SUBTOPIC_OF→ [IT]
[반도체] ─SUBTOPIC_OF→ [IT]
[K-pop] ─SUBTOPIC_OF→ [연예]
[프로야구] ─SUBTOPIC_OF→ [스포츠]
[기준금리] ─SUBTOPIC_OF→ [경제]
```

---

### 설계 원칙

> Class는 보수적으로 만들고, 실제 지식은 Entity와 Relation을 통해 풍부하게 만든다.

처음부터 모든 Class를 정의하려고 하면 Ontology가 지나치게 복잡해진다.

---

# Part 5. 뉴스 원문을 지식그래프로 바꾸는 과정

```text
뉴스 원문
   ↓
NER
   ↓
Entity Linking / Entity Resolution
   ↓
Relation Extraction
   ↓
Ontology Mapping
   ↓
Knowledge Graph 저장
```

---

## 5-1. NER - 개체명 인식

NER은 **Named Entity Recognition** 의 약자로, 문장에서 이름이 붙은 중요한 대상을 찾는 작업이다.

### 예시 문장

```text
삼성전자는 엔비디아에 HBM 공급을 확대할 계획이다.
```

### NER 결과

```text
삼성전자 → Company
엔비디아 → Company
HBM → Product
```

주의할 점은 NER은 **무엇이 등장했는지** 만 찾는다는 것이다.

삼성전자와 엔비디아가 어떤 관계인지까지는 아직 알 수 없다.

---

## 5-2. Entity Linking - 정체 확정

Entity Linking은 NER이 찾은 표현이 실제 어떤 Entity인지 확정하는 과정이다.

예를 들어 `"삼성"`이라는 표현은 다음 여러 후보를 가질 수 있다.

```text
- 삼성전자
- 삼성그룹
- 삼성SDI
- 삼성물산
```

문맥이 다음과 같다면:

```text
HBM, 반도체, 생산, 설비
```

삼성을 **Samsung Electronics** 로 연결할 수 있다.

Entity Linking에서는 특히 두 가지 오류를 조심해야 한다.

- **Split Error**: 같은 대상을 여러 Node로 나누는 오류
- **Merge Error**: 다른 대상을 하나의 Node로 합치는 오류

이 오류들은 추천 품질에 큰 영향을 준다.

---

## 5-3. Relation Extraction - 관계 추출

Relation Extraction은 이미 추출된 Entity들이 서로 어떤 관계인지 찾아내는 작업이다.

### 문장

```text
삼성전자는 엔비디아에 HBM을 공급하기 위해 생산량을 확대했다.
```

### Entity

```text
삼성전자
엔비디아
HBM
```

### 추출 가능한 관계

```text
삼성전자 ─SUPPLIES_TO→ 엔비디아
삼성전자 ─PRODUCES───→ HBM

ArticleA ─MENTIONS→ 삼성전자
ArticleA ─MENTIONS→ 엔비디아
ArticleA ─ABOUT───→ HBM
```

---

## 5-4. 뉴스에서는 Event도 중요하다

뉴스 추천에서는 단순히 같은 기업을 다루는 기사만 찾는 것이 아니라, **같은 사건을 여러 언론사가 어떻게 다루었는지 묶는 것** 도 중요하다.

예시:

```text
기사 A: 연준이 기준금리를 0.25%p 인하했다.
기사 B: 미국 중앙은행, 금리 인하 결정.
기사 C: Fed가 기준금리를 내리면서 증시가 상승했다.
```

이를 하나의 Event로 묶을 수 있다.

```text
[기사 A] ─REPORTS→ [Fed Rate Cut Event]
[기사 B] ─REPORTS→ [Fed Rate Cut Event]
[기사 C] ─REPORTS→ [Fed Rate Cut Event]
```

---

# Part 6. 그래프에서 추천 후보를 찾는 법

## 6-1. Neighbor, Hop, Path

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| Neighbor | 바로 연결된 이웃 Node | 기사 A의 이웃: NVIDIA, AI |
| Hop | Edge를 몇 번 건넜는가 | 기사 A → NVIDIA = 1-hop |
| Path | 실제로 지나간 경로 | 기사 A → NVIDIA ← 기사 B |
| Traversal | 그래프를 따라 탐색하는 행위 | 사용자가 읽은 기사에서 관련 Entity로 이동 |

예를 들어 사용자가 기사 A를 읽었다고 하면:

```text
User ─READ→ 기사 A ─MENTIONS→ NVIDIA ←MENTIONS─ 기사 B
```

기사 B는

> 사용자가 읽은 기사와 같은 기업을 다룬 기사

라는 이유로 추천 후보가 된다.

---

## 6-2. Meta-path

Meta-path는 실제 Node 이름을 제거하고 **Node Type과 Relation Type만 남긴 경로 패턴** 이다.

| Meta-path | 의미 | 추천 설명 |
| --- | --- | --- |
| Article → Company ← Article | 같은 기업을 다룬 기사 | 최근 읽은 기사와 동일한 기업을 다룸 |
| Article → Topic ← Article | 같은 주제 기사 | 최근 관심 주제와 관련된 기사 |
| Article → Event ← Article | 같은 사건 기사 | 같은 이슈를 다룬 다른 기사 |
| Article → Company → Industry ← Company ← Article | 같은 산업 기사 | 같은 산업에 속한 기업 관련 기사 |
| Article → Company → COMPETES_WITH → Company ← Article | 경쟁사 기사 | 관심 기업의 경쟁사 이슈 |

---

## 6-3. Subgraph와 후보 생성

전체 그래프를 매번 모두 탐색할 필요는 없다.

추천 시에는 사용자 주변의 작은 그래프만 잘라서 사용할 수 있는데, 이를 **Subgraph** 라고 한다.

```text
전체 KG
수십만~수백만 Node
수천만 Edge

        ↓

UserA의 최근 읽은 기사 20개
→ 관련 Entity 100개
→ 최근 후보 Article 1,000개
→ Ranking
→ Top 20
```

---

## 6-4. Rule / Path 기반 점수 계산

초기에는 별도의 모델 없이 사람이 직접 가중치를 정해서 추천 점수를 계산할 수 있다.

예시:

```text
같은 Event    +5
같은 Company  +4
같은 Person   +3
같은 Topic    +2
같은 Industry +1
```

후보 기사 B가

- 공통 Company 1개
- 공통 Topic 2개

를 가진다면:

```text
점수 = 1 × 4 + 2 × 2 = 8점
```

### 핵심 구분

- **Graph Traversal** → 후보를 찾는 단계
- **Ranking** → 후보 중 무엇을 먼저 보여줄지 결정하는 단계

# Part 7. 그래프 추천과 모델 학습 추천의 차이

그래프를 사용한다고 해서 반드시 모델 학습이 필요한 것은 아니다.

핵심 차이는 **추천 점수를 사람이 정하는가, 모델이 데이터에서 학습하는가** 이다.

| 구분 | 그래프 규칙 기반 추천 | 모델 학습 기반 추천 |
| --- | --- | --- |
| 점수 기준 | 사람이 직접 정의 | 사용자 행동 데이터에서 학습 |
| 학습 데이터 | 없어도 가능 | 클릭, 읽은 시간, 저장 등 필요 |
| 초기 서비스 | 강함 | Cold Start 문제 |
| 설명 가능성 | 높음 | 상대적으로 낮음 |
| 개인화 | 제한적 | 강함 |
| 예시 | 같은 Event +5 | P(click \| user, article) 예측 |

---

## 7-1. GNN은 무엇을 학습하는가?

GNN은 **Graph Neural Network** 의 약자로, 주변 Node들의 정보를 모아 각 Node의 표현을 학습하는 모델이다.

예를 들어 NVIDIA 주변에 다음 Node들이 있다고 하자.

```text
- Semiconductor
- AI
- GPU
- Jensen Huang
- AMD
- 관련 기사
```

GNN은 이 주변 정보를 이용해 NVIDIA를 다음처럼 표현할 수 있다.

```text
"NVIDIA는 AI, 반도체, GPU와 강하게 관련된 Node"
```

다만 개인화 추천 GNN을 학습하려면 일반적으로 다음과 같은 사용자 행동 로그가 필요하다.

```text
User - Article 클릭
User - Article 열람
User - Article 저장
```

기사와 Entity만 있는 지식그래프에서도 그래프 표현 학습은 가능하지만, 개인화 추천의 정답 데이터는 부족할 수 있다.

# 부록 A. 팀원 설명용 핵심 문장

| 질문 | 짧은 답변 |
| --- | --- |
| 지식그래프가 뭔가? | 객체와 관계를 중심으로 지식을 연결한 그래프 |
| 기사도 Node인가? | 뉴스 추천에서는 추천 대상이 기사이므로 Article Node로 두는 것이 자연스러움 |
| Property와 Node의 차이는? | 단순 설명값은 Property, 다른 것과 연결해 탐색할 값은 Node |
| Ontology는 뭔가? | 그래프 세계의 개념, 관계, 규칙을 정의한 의미 체계 |
| Class는 많을수록 좋은가? | 아니다. Class는 적게, Entity와 Relation은 목적에 맞게 확장 |
| 추천 후보는 어떻게 찾나? | 사용자가 읽은 기사에서 Entity/Topic/Event를 따라 k-hop, Path, Meta-path로 후보 Article 탐색 |
| GNN은 꼭 필요한가? | 초기에는 아니다. 행동 로그가 쌓이면 Ranking 고도화에 활용 가능 |

# 부록 B. 용어 사전

| 용어 | 의미 |
| --- | --- |
| Node | 그래프 안의 객체. 기사, 기업, 인물, 주제 등이 될 수 있음 |
| Edge / Relation | Node 사이의 관계. MENTIONS, ABOUT, READ 등 |
| Property | Node나 Edge의 속성값. 제목, 날짜, confidence 등 |
| Triple | Subject - Predicate - Object 형태의 하나의 사실 |
| RDF | Resource Description Framework. 모든 지식을 Triple로 표현하는 표준 방식 |
| Property Graph | Node와 Edge에 Property를 직접 붙이는 그래프 모델 |
| Ontology | 개념, 관계, 규칙을 정의한 의미 체계 |
| Class | 개념의 종류. Person, Company, Article 등 |
| Instance | Class에 속하는 구체적 대상. 삼성전자, NVIDIA 등 |
| NER | 문장에서 Entity 후보를 찾는 작업 |
| Entity Linking | 표현이 실제 어떤 Entity인지 확정하는 작업 |
| Relation Extraction | Entity 사이의 관계를 추출하는 작업 |
| Hop | Edge를 몇 번 건너갔는지 나타내는 거리 |
| Path | Node 사이를 연결하는 실제 경로 |
| Meta-path | Node/Relation Type으로 일반화한 경로 패턴 |
| Subgraph | 전체 그래프 중 특정 목적에 필요한 일부 그래프 |
| Candidate Generation | 추천 후보를 먼저 좁히는 단계 |
| Ranking | 후보 중 무엇을 먼저 보여줄지 점수화하는 단계 |
| GNN | Graph Neural Network. 주변 Node 정보를 모아 표현을 학습하는 모델 |

사용해볼 것 : Docker/Docker Compose, Nginx, Jenkins, Certbot/HTTPS

## Docker / Docker Compose
- Docker: 애플리케이션과 실행 환경을 컨테이너로 묶어서 실행
- 백엔드, 프론트엔드, DB 등을 각각 컨테이너로 실행 가능
- Docker Compose: 여러 Docker 컨테이너을 docker-compose.yml 하나로 관리
- 프로젝트에서는 Spring, FastAPI, MySQL, Neo4j 등을 묶어 실행하는 용도로 활용 가능

## Nginx
- 외부 요청을 가장 먼저 받는 웹 서버 / 리버스 프록시
- 요청에 따라 적절한 서버로 전달
```
예:
/ → Frontend
/api → Backend
/ai → FastAPI
```
- HTTPS 적용, 포트 숨기기, 요청 분배 등의 역할도 수행

## Jenkins
- CI/CD 자동화 도구
- GitLab에 코드가 Push/Merge되면:
- 코드 변경 → 빌드 → 테스트 → Docker 이미지 생성 → 서버 배포
- Jenkins 자체도 실행할 서버가 필요

### CI/CD

**CI/CD는 코드 변경부터 배포까지의 과정을 자동화하는 방식**입니다.
- **CI (Continuous Integration, 지속적 통합)**
  - 개발자가 코드를 Push/Merge하면
  - 자동으로 **빌드 → 테스트 → 오류 확인**
  - 여러 사람이 작성한 코드를 자주 합치고 문제를 빠르게 발견하는 목적

- **CD (Continuous Delivery / Deployment, 지속적 전달·배포)**
  - CI를 통과한 코드를 실제 서버에 배포하는 과정
  - Docker 이미지 생성, 서버 반영, 컨테이너 재실행 등을 자동화할 수 있음

## Certbot / HTTPS

- Certbot: 인증서 발급·갱신을 쉽게 해주는 도구
- 보통 Nginx와 함께 사용해서 HTTP → HTTPS 적용한다
