## 1. 프로젝트 착수부터 Event-Centric KG 구축안 설계까지 (~2026.08.26)

### 1.1 2026.08.20 — 뉴스 데이터 소스와 서비스 가능성 검증

**핵심 질문**

- 한국어 뉴스를 지속적으로 충분히 확보할 수 있는가?
- API가 표시하는 기사 수와 실제로 접근·저장할 수 있는 기사 수는 같은가?
- 단순 뉴스 추천과 구별되는 기능은 무엇이어야 하는가?

**확인한 내용**

- NewsAPI에 한국어 조건을 적용했을 때 응답은 정상이었지만 totalResults는 0이었다.
- GNews의 전 기간 추정 기사 수는 general 약 118,902건, business 약 83,168건, technology 약 42,060건 등이었다.
- 자체 수집 실험에서는 6시간 구간 59건, 24시간 275건을 수집했고 총 77개 언론사가 포함됐다.
- 무료·유료 API마다 호출량, 전문 제공, 실시간성, 재배포 조건이 달랐다.

**설계에 반영한 판단**

- 특정 뉴스 API 하나에 전체 수집 구조를 의존하지 않는다.
- 기사 수집과 Knowledge Graph 구축을 별도의 파이프라인 문제로 본다.
- 서비스의 차별점을 기사 목록 추천이 아니라 동일 사건 통합과 맥락 탐색에서 찾기 시작했다.

### 1.2 2026.08.21 — GDELT GKG의 서비스 적용 가능성 분석

**핵심 질문**

- GDELT GKG를 정제하면 서비스용 Knowledge Graph로 사용할 수 있는가?
- GKG의 THEMES·인물·기관·장소 정보는 우리가 원하는 사건 그래프와 같은가?

**확인한 내용**

- 특정 시점의 GDELT GKG 데이터 872건 중 한국어 기사는 0건이었다.
- 한겨레 영문판 기사에는 다수의 theme, entity, location 정보가 부착돼 있었다.
- GKG는 기사별 메타데이터를 풍부하게 제공하지만, 여러 기사가 지칭하는 동일한 현실 사건을 하나의 Canonical Event로 통합한 구조는 아니었다.

**설계에 반영한 판단**

~~~text
기사별 theme/entity 추출
≠ 여러 기사에 걸친 Canonical Event 구축
~~~

- GDELT는 theme·entity 후보나 데이터 분석을 위한 보조 소스로 둔다.
- 핵심 Event 통합은 별도의 extraction·resolution·fusion 파이프라인으로 설계한다.

### 1.3 2026.08.22~23 — 기사보다 사건을 탐색하는 사용자 경험 설계

**핵심 질문**

- 개인화 KG가 일반적인 뉴스 추천보다 무엇을 더 잘할 수 있는가?
- 화면의 별 하나는 Article, Topic, Entity, Event 중 무엇이어야 하는가?
- 사용자가 읽지 않은 배경 사건이나 중간 사건을 어떻게 추천할 것인가?

**정리한 서비스 문제**

- 같은 사건을 다룬 기사가 중복 노출된다.
- 현재 사건의 이전 배경과 후속 전개를 찾기 어렵다.
- 사실, 주장, 전망, 반응이 기사 문맥 안에서 섞인다.
- 기존 추천은 “관심사가 비슷해서”라는 설명에 머무르기 쉽다.
- 사용자가 무엇을 읽었는지는 알 수 있지만 어떤 맥락을 놓쳤는지는 알기 어렵다.

**설계에 반영한 판단**

- 기본 탐색 단위를 Article이 아니라 Event로 정했다.
- 전체 뉴스 KG와 사용자의 열람·관심 기록을 분리한다.
- 사용자가 읽은 두 사건 사이의 누락된 사건을 찾는 정보 공백 추천을 차별점으로 삼는다.
- Background, Continuation, Reaction, Larger Context, Actor Trajectory, Perspective 등 관계별 추천 후보를 구상했다.
- 여러 언론사가 동일 Event를 보도한 기사는 우측 고정 패널에서 함께 제공한다.
- 사용자에게 보이는 Event 이름은 사건을 이해할 수 있는 문장형으로 표현한다.

### 1.4 2026.08.24 — Knowledge Graph 기초 개념 정리

**핵심 질문**

- Knowledge Graph에 합의된 단일 정의가 있는가?
- RDF와 KG는 같은 것인가?
- ontology와 reasoning은 무엇인가?
- fact triple의 h, r, t와 추가 문맥 γ는 무엇인가?
- Temporal KG와 Event-Centric KG는 어떻게 다른가?

**학습한 내용**

- KG에는 모든 연구와 산업에서 공유되는 단일 정의가 없다.
- 일반적인 fact는 ⟨h, r, t⟩로 표현하며, γ는 논문에 따라 시간·조건·qualifier·provenance 등 추가 문맥을 나타낼 수 있다.
- RDF는 subject–predicate–object triple을 사용하는 W3C 데이터 모델이며 KG와 동의어가 아니다.
- ontology는 허용되는 개념, 관계, domain/range, 제약과 의미를 정하는 계약이다.
- RDF/OWL reasoning은 선언된 공리와 규칙으로부터 논리적으로 함의되는 사실을 도출하는 과정이다.
- Temporal KG는 사실이나 관계가 언제 유효한지에 초점을 두고, Event-Centric KG는 Event 자체를 first-class node로 둔다.
- Temporal과 Event-Centric은 배타적 분류가 아니며 하나의 KG에서 결합할 수 있다.

**설계에 반영한 판단**

- Event를 그래프의 first-class node이자 기본 탐색 단위로 둔다.
- 같은 actor와 action이 등장해도 시간·장소·수치가 다르면 별도 Event일 수 있다.
- 기사 속 동사를 그대로 새로운 relation으로 만들지 않고, 미리 정의한 ontology의 관계만 허용하는 schema-first 방식을 채택한다.
- 기사 발행 시각과 Event 발생 시각을 분리한다.

### 1.5 2026.08.25 — Event, Mention, Statement, Evidence의 의미 경계

**핵심 질문**

- 기사에 쓰인 사건 표현과 현실에서 발생한 사건은 같은 객체인가?
- 전망·주장·평가도 Event로 저장해야 하는가?
- Article 자체를 evidence로 보면 충분한가?
- 여러 기사에서 추출된 Event를 언제 하나로 병합해야 하는가?
- LLM이 predicate와 ontology를 자유롭게 생성하게 해도 되는가?

**정리한 의미 경계**

~~~text
기사에 실제로 쓰인 사건 표현
≠ 여러 기사 표현이 가리키는 현실 사건
≠ 누군가가 주장한 명제
≠ 그 추출을 뒷받침하는 원문 범위
~~~

| 개념 | 당시 정리한 의미 |
|---|---|
| Article | 기사 원문과 메타데이터 |
| EvidenceSpan | extraction 또는 assertion의 근거가 되는 원문 범위 |
| EventMention | 특정 기사에 나타난 사건 표현 |
| Event | 여러 EventMention이 가리키는 하나의 현실 사건 |
| Statement | 특정 발화자의 주장·전망·평가 |

**학습 및 설계 결과**

- “발화자가 인과를 주장했다”는 사실과 실제 세계의 인과 관계를 구분해야 한다.
- Event matching은 단순 clustering이 아니라 여러 문서에 걸친 identity resolution 문제다.
- 모델 출력은 최종 사실이 아니라 candidate와 score로 취급해야 한다.
- LLM은 gold data pre-annotation, 저신뢰 사례 검토, 복잡한 간접화법 처리 등 보조 역할로 제한한다.
- ontology.yaml을 허용 node/edge, domain/range, argument role, validation, model label, prompt의 단일 기준으로 사용하기로 했다.

### 1.6 2026.08.26 — 구현 가능한 KG 계약과 파이프라인 설계

**핵심 질문**

- 논문 속 개념을 실제 프로젝트의 저장 구조로 어떻게 축소할 것인가?
- 여러 기사에서 같은 현실 Event를 판정하는 절차는 무엇이어야 하는가?
- ontology, 모델, validation이 같은 schema를 사용하게 하려면 어떻게 해야 하는가?

**설계 순서**

~~~text
사용자 질문과 서비스 기능
→ 필요한 지식 단위
→ Ontology Contract
→ Entity/Event Identity와 Fusion
→ Assertion과 Evidence
→ Pipeline 책임과 Validation
~~~

**시스템 책임 분리**

- Control Plane: ontology, gold set, validation, model/ontology version
- Construction Plane: 수집, 추출, 정규화, resolution, fusion, relation 생성, validation, 저장
- Serving Plane: 트렌드, 검색, 관계 탐색, 추천, 개인 기록, 추천 설명

**Cross-document Event resolution 초안**

~~~text
새 EventMention
→ Event type·시간·주체 기반 후보 제한
→ embedding 기반 후보 검색
→ pairwise same-event 분류
→ cluster consistency 검사
→ 기존 Event 병합 또는 새 Event 생성
~~~

**설계에 반영한 판단**

- embedding 유사도뿐 아니라 Event type, actor, target, time, location, value, 상태와 기사 문맥을 함께 비교한다.
- 서로 다른 사건을 잘못 합치는 false merge가 하나의 사건을 나눠 저장하는 false split보다 더 위험하므로 보수적으로 병합한다.
- 모든 추출·관계 결과에 evidence, confidence, origin, model/ontology version, extraction time, review status를 보존한다.
- validation을 통과하지 못한 결과는 factual KG가 아니라 candidate 또는 quarantine 상태로 관리한다.
- 추천 후보는 relation별로 생성하고, 추천 이유는 graph path에서 만든다.

## 2. KG 스키마 및 Event/Statement Extractor 구체화 (2026.08.27)

### 2.1 오늘의 목표

8월 26일까지 정리한 개념적 구조를 팀 공통 KG schema와 실제 Information Extractor의 학습 기준으로 연결했다. 핵심은 Node와 Edge를 늘리는 것이 아니라, 무엇을 Event·Statement로 인정하고 어떤 후보만 최종 KG에 반영할지 명시하는 것이었다.

오늘 작업은 다음 흐름으로 이어졌다.

~~~text
KG의 Event/Statement 의미 경계 확정
→ annotation guideline 작성
→ 뉴스 본문 및 Gold Dataset 정제
→ Extractor·Retriever·Pairwise Reasoner 책임 분리
→ KG 저장 전 validation 기준 구체화
~~~

### 2.2 팀 공통 KG Schema 결정

| 대상 | 결정 |
|---|---|
| Article → Event | COVERS로 정의 |
| Event | 실제 발생·진행·확정된 사건, 결정, 발표를 표현 |
| Statement | 전망, 주장, 평가, 계획, 가능성 등을 표현 |
| EventMention | 최종 KG Node가 아니라 Event Matching 과정의 중간 데이터 |
| Evidence | EvidenceSpan Node 대신 evidenceArticleId, evidenceChunkId 등으로 provenance 추적 |
| Event → Entity | ACTOR, TARGET, PLACE로 역할 분리 |
| Topic | 정치·경제·사회 등 서비스의 고정 대분류 |
| Concept | 기준금리·지진·인플레이션 등 사건 이해를 위한 세부 지식 단위 |
| Event → Event | 직접 저장 관계를 CAUSES, RESPONDS_TO로 제한 |
| 시간 순서 | PRECEDES를 저장하지 않고 Event.occurredAt으로 계산 |
| Event ↔ Story | N:M 관계 |
| Story ↔ Topic | N:M 관계 |
| User | 공용 News KG 밖의 interaction log와 개인화 데이터로 관리 |

Statement에는 ASSERTED_BY와 ABOUT 관계를 둔다. 예를 들어 어떤 전문가가 “정책 X가 물가 상승의 원인”이라고 주장해도 이를 바로 다음과 같은 세계 사실로 저장하지 않는다.

~~~text
정책 X ─CAUSES→ 물가 상승
~~~

대신 “해당 발화자가 그러한 주장을 했다”는 사실을 Statement로 저장한다. 이 구조를 사용하면 서로 상반된 주장도 KG의 모순 없이 함께 표현할 수 있고, 이후 관점 비교와 추천 설명에도 사용할 수 있다.

### 2.3 KG Construction Pipeline 구체화

~~~text
Raw Article
→ Entity / Concept / Time 추출
→ Event Candidate + Statement Candidate 추출
→ 기사 내부 Event 병합 및 중요도 판정
→ 기존 Canonical Event 검색 및 Matching
→ Event → Story Matching
→ Event Relation Extraction
→ Ontology Validation / Conflict Check
→ Neo4j KG 반영
~~~

Event는 하나의 keyword가 아니라 actor, action, target, time, place, value 등이 결합된 사건 표현이다. 따라서 별도의 Keyword Extraction 단계를 반드시 거칠 필요는 없으며, ontology에 필요한 Event·Statement·Entity·Time을 기사에서 직접 추출하는 구조가 더 적합하다고 판단했다.

기사 하나에는 여러 Event Candidate가 존재할 수 있으므로 제목 등장 여부, 기사 내 위치, 반복 빈도, 주요 Entity와의 관련성 등을 이용해 Event Salience를 판단할 필요가 있다.

### 2.4 Event / Statement Annotation Guideline

Event와 Statement를 과거·미래 시제나 특정 keyword만으로 구분하지 않는다. KG에 넣으려는 proposition의 factuality와 modality, 특히 문장의 matrix clause가 무엇을 단정하는지를 우선한다.

| Label | 판정 기준 |
|---|---|
| EVENT | 실제 발생·진행 중인 사건, 이미 내려진 결정, 확정된 사안 |
| STATEMENT | 전망, 예상, 가능성, 추정, 주장, 평가, 해석, 우려, 권고, 계획, 예정, 의지 |
| O | 서비스 KG의 Event나 Statement로 저장할 필요가 없는 일반 설명·배경 정보 |

예시는 다음과 같다.

- “한국은행이 기준금리를 동결했다.” → EVENT
- “금리를 올릴 가능성이 있다.” → STATEMENT
- “전문가는 금리 인상이 물가를 잡을 것이라고 주장했다.” → STATEMENT

“밝혔다”, “전했다”, “말했다”와 같은 reporting verb는 실제 발화 행위가 있었다는 뜻이지만, 그 안의 proposition이 사실이라는 뜻은 아니다. 따라서 발화 행위 자체가 아니라 KG에 저장하려는 내용의 factuality와 modality를 판정해야 한다.

초기 Event/Statement Extractor는 다음 label을 사용하는 단일 BIO Token Classification Head로 시작하기로 계획해봤다.

~~~text
O
B-EVENT
I-EVENT
B-STATEMENT
I-STATEMENT
~~~

기준에 대한 다음과 같은 질문을 만들었다.

- 무엇을 Event와 Statement로 인정할 것인가?
- 어떤 표현을 O로 버릴 것인가?
- trigger/span의 범위를 어디까지로 볼 것인가?
- 부정·가정·전망 속 사건을 어떻게 처리할 것인가?
- 서로 다른 의미의 Event와 Statement를 하나의 span으로 묶지 않을 것인가?

### 2.5 모델 책임 분리

현재 필요한 모델 머신을 세 종류로 나눴다.

| 모델 책임 | 입력과 출력 | 후보 모델 |
|---|---|---|
| Information Extractor | Article → Event / Statement / Entity / Time | KLUE-RoBERTa, KoELECTRA |
| Semantic Retriever | 새 Entity/Event → 기존 KG 후보 Top-K | BGE-M3, multilingual-E5, KoSimCSE |
| Pairwise Reasoner | 후보 A + B → 동일 객체 여부 또는 relation | KLUE-RoBERTa + classification head, reranker 계열 |

현재 첫 실험의 범위는 Event/Statement span extractor다. Entity·Time 추출, Canonical Event 검색, pairwise 동일성 판정은 같은 모델의 부수 기능으로 간주하지 않고 별도 책임으로 분리한다.

### 2.6 평가 데이터 정제 및 Gold v0.3

기존 GNews 수집 데이터에 실제 기사 본문 외의 내용이 섞여 있는 문제를 확인했다.

- AI 해설
- Key Points
- Timeline
- Glossary
- 이모지
- 댓글·제보 UI
- 중복 기사 본문

이를 제거해 body-only 데이터셋을 만들고, 기존 annotation offset을 정제된 본문 기준으로 다시 맞췄다. 원본 JSON에 실제 기사 본문 없이 AI 해설만 존재한 기사는 benchmark에서 제외했다.

POC 기사 29개를 직접 검토하며 Event/Statement 기준과 span 경계를 반복해서 수정했다.

| Gold v0.3 | 수량 |
|---|---:|
| 기사 | 29 |
| EVENT annotation | 123 |
| STATEMENT annotation | 118 |
| 전체 annotation | 241 |

모든 annotation에서 text == article[start:end]가 성립하는지 검증했다. 서로 다른 의미의 EVENT와 STATEMENT가 하나의 span으로 묶인 경우에는 각각 분리했다.

### 2.7 Event Matching·Relation·Validation 기준

#### Canonical Event Matching

embedding은 유사 후보를 검색하는 도구이지 최종 동일성 판정 기준이 아니다. 서로 다른 달의 동일한 금리 동결처럼 문맥이 매우 유사한 별도 사건이 존재하기 때문이다.

따라서 다음 구조 정보를 함께 비교한다.

- Event type
- Actor / Target
- Time
- Location
- Value와 회차

시간·장소·수치·회차·핵심 Actor/Target이 명백하게 충돌하면 embedding similarity가 높아도 병합하지 않는 hard conflict 규칙을 둔다.

#### Event Relation

- CAUSES와 RESPONDS_TO는 기사 문맥에 해당 관계를 뒷받침하는 근거가 있을 때만 생성한다.
- 단순 시간 선후, 의미적 유사성, 같은 Story라는 이유만으로 relation을 확정하지 않는다.
- 동일 Event 판단과 서로 다른 Event 사이의 relation 판단을 별도 문제로 다룬다.

#### Ontology Validation / Conflict Check

최종 KG 저장 전에 다음을 검사한다.

- 허용된 Node/Edge type인가?
- relation의 domain/range가 맞는가?
- Event merge에 time·location·value 충돌이 없는가?
- CAUSES·RESPONDS_TO에 근거와 올바른 방향이 있는가?
- Event.occurredAt과 Time 표현이 일치하는가?

잘못된 Event merge나 인과 relation은 Story timeline, 추천 이유, 이후 모델 학습 데이터까지 오염시킬 수 있으므로, 검증 실패 결과는 바로 factual KG에 넣지 않는다.

### 2.8 오늘 배운 점

- KG 설계에서는 Node와 Edge의 수보다 의미 경계가 중요하다.
- Keyword, EventMention, Canonical Event는 서로 다른 단계의 객체다.
- Event와 Statement의 schema 경계가 annotation label과 모델 평가 기준으로 이어져야 한다.
- 동일 Event 판정과 Event 간 relation 판정은 서로 다른 문제다.
- embedding은 후보 검색 도구이지 사실 판정 도구가 아니다.
- 모델 출력은 candidate이며 validation을 통과해야 KG의 사실이 된다.
- 모델 구조를 먼저 정하기보다 일관된 annotation guideline과 오류 기준을 먼저 만들어야 한다.
