# 지식그래프 기반 추천 시스템 학습 정리 (.feat GPT talk) (26.08.24 ~ 26)

> 지식그래프 기반 뉴스 추천 서비스를 설계하기 위해 학습한 내용을 정리한 TIL 문서입니다.  
> 핵심 개념부터 뉴스 데이터를 그래프로 만드는 과정, 추천 후보 탐색, 모델 기반 추천으로의 확장까지 정리했습니다.

---

## 1. 한눈에 보는 핵심 정리

- **지식그래프(Knowledge Graph)** 는 객체(Node)와 관계(Edge)를 중심으로 정보를 연결하는 구조다.
- 뉴스 추천에서는 **기사 자체도 Node** 가 되고, 기사에서 추출된 기업·인물·주제·사건도 Node가 된다.
- 제목, 날짜, URL처럼 단순한 설명값은 **Property** 로 둔다.
- 다른 객체와 계속 연결해 탐색하거나 추천에 활용할 대상은 **Node** 로 두는 것이 좋다.
- **Ontology** 는 그래프 안의 개념, 관계, 의미, 규칙을 정의하는 체계다.
- 뉴스 원문은 보통  
  **NER → Entity Linking → Relation Extraction → Ontology Mapping → Knowledge Graph 저장**  
  순서로 그래프로 변환한다.
- 추천 후보는 **Neighbor, Hop, Path, Meta-path, Subgraph** 탐색으로 찾을 수 있다.
- 초기 서비스는 **Rule/Path 기반 추천** 으로 시작하고, 사용자 행동 데이터가 쌓이면 **ML Ranking / GNN** 으로 확장할 수 있다.
- 중요한 설계 원칙은 **Class는 보수적으로 유지하고, Entity와 Relation을 점진적으로 확장하는 것** 이다.

---

# Part 1. 지식그래프의 기본 개념

## 1-1. 지식그래프란?

RDB가 **테이블과 조인**을 중심으로 데이터를 연결한다면, 지식그래프는 **Node - Edge - Node** 구조를 중심으로 데이터를 표현한다.

### RDB 방식

```text
Article Table
Company Table
Article_Company Table
```

### 지식그래프 방식

```text
[Article A] ──MENTIONS──> [NVIDIA]
[Article A] ──ABOUT─────> [AI]
[NVIDIA] ──BELONGS_TO──> [Semiconductor]
```

지식그래프의 핵심은 단순히 데이터를 이어놓는 것이 아니라, **객체와 관계의 의미를 명확하게 설계하고 그 연결을 탐색하는 것** 이다.

---

## 1-2. Node, Edge, Property

| 개념 | 의미 | 뉴스 추천 예시 |
| --- | --- | --- |
| Node | 그래프 안의 객체 | 기사 A, 삼성전자, NVIDIA, AI, 반도체 |
| Edge / Relation | 객체 사이의 관계 | 기사 A - MENTIONS - 삼성전자 |
| Property | 객체나 관계를 설명하는 값 | 기사 제목, 작성일, URL, confidence |
| Label / Type | Node의 종류 | Article, Company, Person, Topic |

### 기사도 Node인가?

뉴스 추천에서는 **기사 자체도 Node로 두는 것이 자연스럽다.**

추천 시스템이 최종적으로 추천하는 대상이 기사이기 때문이다.

```text
[기사 A] : Article
  title: "엔비디아 차세대 GPU 공개"
  published_at: "2026-08-23"
  url: "..."

[기사 A] ─MENTIONS→ [NVIDIA]
[기사 A] ─MENTIONS→ [Jensen Huang]
[기사 A] ─ABOUT────→ [AI]
[기사 A] ─ABOUT────→ [반도체]
```

### Node와 Property를 구분하는 기준

다음 질문으로 구분하면 이해하기 쉽다.

> **이 값을 앞으로 추천 경로에서 탐색하거나 연결할 것인가?**

- 그렇다면 → **Node 후보**
- 단순 설명값이라면 → **Property 후보**

예를 들면:

- 제목, 날짜, URL → Property
- 삼성전자, NVIDIA, 반도체 → Node

# Part 2. Triple, RDF, Property Graph

## 2-1. Triple

Triple은 지식그래프에서 하나의 사실을 표현하는 기본 단위다.

```text
Subject - Predicate - Object
```

즉,

```text
주어 - 관계 - 목적어
```

예시:

```text
(NVIDIA, CEO_OF, Jensen Huang)
(ArticleA, MENTIONS, NVIDIA)
(NVIDIA, BELONGS_TO, Semiconductor)
```

---

## 2-2. RDF

**RDF(Resource Description Framework)** 는 세상의 지식을 Triple의 집합으로 표현하는 표준 방식이다.

RDF에서는 속성도 Triple로 표현할 수 있다.

```text
ArticleA ─title──────→ "엔비디아 신제품 공개"
ArticleA ─date───────→ "2026-08-23"
ArticleA ─MENTIONS───→ NVIDIA
ArticleA ─ABOUT──────→ AI
```

---

## 2-3. Property Graph

Property Graph는 **Node와 Edge를 명확한 객체로 다루고, Node와 Edge 각각에 Property를 붙이는 방식** 이다.

Neo4j가 대표적인 Property Graph Database다.

```text
[ArticleA]
 title: "엔비디아 신제품 공개"
 published_at: "2026-08-23"

[ArticleA]
   │
   │ MENTIONS
   │ confidence: 0.97
   │ importance: 0.91
   ▼
[NVIDIA]
```

---

## 2-4. RDF와 Property Graph 비교

| 구분 | RDF | Property Graph |
| --- | --- | --- |
| 기본 단위 | Triple | Node + Edge + Property |
| 속성 표현 | 속성도 Triple로 표현 | Node/Edge Property로 표현 |
| 강점 | 표준화, 외부 지식 공유, Ontology | 서비스 구현, 탐색, Edge 속성 관리 |
| 대표 질의 | SPARQL | Cypher |
| 대표 활용 | Wikidata, DBpedia, Semantic Web | Neo4j 기반 서비스 그래프 |

핵심 차이는 관계의 다양성이 아니라 **표현 철학** 에 있다.

- RDF → 모든 것을 Triple로 표현
- Property Graph → Node와 Edge에 Property를 직접 부여

---

# Part 3. Ontology - 그래프의 의미와 규칙

## 3-1. Ontology란?

Ontology는 단순한 관계 규칙보다 조금 더 넓은 개념이다.

> 무엇이 존재하고, 그것들이 어떤 의미를 가지며, 어떤 관계를 맺을 수 있는지 정의한 체계

### 핵심

```text
Schema = 구조
Ontology = 구조 + 의미 + 규칙
```

---

## 3-2. Schema와 Ontology의 차이

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| Schema | 어떤 Node/Edge 구조를 쓸지 정의 | Article - MENTIONS - Company |
| Ontology | 구조의 의미와 규칙까지 정의 | MENTIONS의 출발점은 Article, 도착점은 Entity |
| Inference | 규칙을 이용해 숨은 사실을 추론 | SemiconductorCompany이면 Company이기도 함 |

실제 데이터는 다음과 같이 저장될 수 있다.

```text
[기사 A] ─MENTIONS────→ [삼성전자]
[기사 A] ─PUBLISHED_BY→ [동아일보]
```

Ontology에서는 관계의 규칙을 정의한다.

```text
MENTIONS      : Article → Entity
PUBLISHED_BY  : Article → NewsOrganization

Company            : Entity의 하위 개념
NewsOrganization   : Organization의 하위 개념
```

즉,

- 실제 Edge → 데이터
- Ontology → 어떤 종류의 Node끼리 어떤 관계를 가질 수 있는지 정의하는 규칙

---

## 3-3. Domain과 Range

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| Domain | 관계의 출발 Node Type | CEO_OF의 Domain = Person |
| Range | 관계의 도착 Node Type | CEO_OF의 Range = Company |
| Class | 개념의 종류 | Person, Company, Article |
| Instance | 구체적인 실제 대상 | Jensen Huang, NVIDIA, 기사 A |

---

## 3-4. Ontology가 추천에 중요한 이유

Ontology가 있으면 직접 연결되지 않은 것도 의미적으로 확장할 수 있다.

### 직접 저장된 사실

```text
NVIDIA ─INSTANCE_OF→ SemiconductorCompany
```

### Ontology 규칙

```text
SemiconductorCompany ─IS_A→ Company
Company ─IS_A→ Organization
```

### 추론 가능한 사실

```text
NVIDIA는 Company다.
NVIDIA는 Organization이다.
```

이런 구조가 있으면 NVIDIA와 직접 연결된 기사뿐 아니라 **반도체, AI 인프라, HBM, 관련 기업** 등으로 추천 범위를 확장할 수 있다.

> Ontology는 노드를 직접 이어놓은 선이 아니라,  
> 그 선이 어떤 의미인지 판단하고 숨은 연결까지 추론하게 해주는 규칙집이다.

---

# Part 4. Class, Entity, Topic 범위 정하기

## 4-1. Node가 많아지는 것과 Class가 많아지는 것은 다르다

뉴스에는 인물, 기업, 기관, 사건, 주제 등이 계속 등장하기 때문에 Entity Node 수는 매우 많아질 수 있다.

하지만 그렇다고 Class까지 계속 늘릴 필요는 없다.

> **Class는 적게 유지하고, 실제 다양성은 Entity Node와 Relation으로 표현한다.**

---

## 4-2. Class / Node / Property 구분 기준

| 판단 질문 | Class 후보 | Node 후보 | Property 후보 |
| --- | --- | --- | --- |
| 여러 구체적 대상을 분류하는 타입인가? | Person, Company, Article | 삼성전자, 손흥민 | - |
| 공통 규칙을 적용해야 하는가? | Company - PRODUCES - Product | - | - |
| 그 자체를 탐색하고 연결하고 싶은가? | - | 반도체, K-pop, 금리 | - |
| 단순 객체 설명값인가? | - | - | 제목, 작성일, URL |
| 일시적 지위나 역할인가? | 필요하면 Role Class | 대통령, 축구선수 Role Node | - |

---

## 4-3. 도메인은 Topic Node로 다루기

정치, 경제, IT, 스포츠, 연예 같은 대분류는 Class보다 **Topic Node** 로 두는 편이 자연스럽다.

```text
(:Topic {name: "정치"})
(:Topic {name: "경제"})
(:Topic {name: "IT"})
(:Topic {name: "스포츠"})
(:Topic {name: "연예"})
```

세부 Topic은 다음과 같이 연결할 수 있다.

```text
[AI] ─SUBTOPIC_OF→ [IT]
[반도체] ─SUBTOPIC_OF→ [IT]
[K-pop] ─SUBTOPIC_OF→ [연예]
[프로야구] ─SUBTOPIC_OF→ [스포츠]
[기준금리] ─SUBTOPIC_OF→ [경제]
```

---

### 설계 원칙

> Class는 보수적으로 만들고, 실제 지식은 Entity와 Relation을 통해 풍부하게 만든다.

처음부터 모든 Class를 정의하려고 하면 Ontology가 지나치게 복잡해진다.

# Part 5. 뉴스 원문을 지식그래프로 바꾸는 과정

```text
뉴스 원문
   ↓
NER
   ↓
Entity Linking / Entity Resolution
   ↓
Relation Extraction
   ↓
Ontology Mapping
   ↓
Knowledge Graph 저장
```

---

## 5-1. NER - 개체명 인식

NER은 **Named Entity Recognition** 의 약자로, 문장에서 이름이 붙은 중요한 대상을 찾는 작업이다.

### 예시 문장

```text
삼성전자는 엔비디아에 HBM 공급을 확대할 계획이다.
```

### NER 결과

```text
삼성전자 → Company
엔비디아 → Company
HBM → Product
```

주의할 점은 NER은 **무엇이 등장했는지** 만 찾는다는 것이다.

삼성전자와 엔비디아가 어떤 관계인지까지는 아직 알 수 없다.

---

## 5-2. Entity Linking - 정체 확정

Entity Linking은 NER이 찾은 표현이 실제 어떤 Entity인지 확정하는 과정이다.

예를 들어 `"삼성"`이라는 표현은 다음 여러 후보를 가질 수 있다.

```text
- 삼성전자
- 삼성그룹
- 삼성SDI
- 삼성물산
```

문맥이 다음과 같다면:

```text
HBM, 반도체, 생산, 설비
```

삼성을 **Samsung Electronics** 로 연결할 수 있다.

Entity Linking에서는 특히 두 가지 오류를 조심해야 한다.

- **Split Error**: 같은 대상을 여러 Node로 나누는 오류
- **Merge Error**: 다른 대상을 하나의 Node로 합치는 오류

이 오류들은 추천 품질에 큰 영향을 준다.

---

## 5-3. Relation Extraction - 관계 추출

Relation Extraction은 이미 추출된 Entity들이 서로 어떤 관계인지 찾아내는 작업이다.

### 문장

```text
삼성전자는 엔비디아에 HBM을 공급하기 위해 생산량을 확대했다.
```

### Entity

```text
삼성전자
엔비디아
HBM
```

### 추출 가능한 관계

```text
삼성전자 ─SUPPLIES_TO→ 엔비디아
삼성전자 ─PRODUCES───→ HBM

ArticleA ─MENTIONS→ 삼성전자
ArticleA ─MENTIONS→ 엔비디아
ArticleA ─ABOUT───→ HBM
```

---

## 5-4. 뉴스에서는 Event도 중요하다

뉴스 추천에서는 단순히 같은 기업을 다루는 기사만 찾는 것이 아니라, **같은 사건을 여러 언론사가 어떻게 다루었는지 묶는 것** 도 중요하다.

예시:

```text
기사 A: 연준이 기준금리를 0.25%p 인하했다.
기사 B: 미국 중앙은행, 금리 인하 결정.
기사 C: Fed가 기준금리를 내리면서 증시가 상승했다.
```

이를 하나의 Event로 묶을 수 있다.

```text
[기사 A] ─REPORTS→ [Fed Rate Cut Event]
[기사 B] ─REPORTS→ [Fed Rate Cut Event]
[기사 C] ─REPORTS→ [Fed Rate Cut Event]
```

---

# Part 6. 그래프에서 추천 후보를 찾는 법

## 6-1. Neighbor, Hop, Path

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| Neighbor | 바로 연결된 이웃 Node | 기사 A의 이웃: NVIDIA, AI |
| Hop | Edge를 몇 번 건넜는가 | 기사 A → NVIDIA = 1-hop |
| Path | 실제로 지나간 경로 | 기사 A → NVIDIA ← 기사 B |
| Traversal | 그래프를 따라 탐색하는 행위 | 사용자가 읽은 기사에서 관련 Entity로 이동 |

예를 들어 사용자가 기사 A를 읽었다고 하면:

```text
User ─READ→ 기사 A ─MENTIONS→ NVIDIA ←MENTIONS─ 기사 B
```

기사 B는

> 사용자가 읽은 기사와 같은 기업을 다룬 기사

라는 이유로 추천 후보가 된다.

---

## 6-2. Meta-path

Meta-path는 실제 Node 이름을 제거하고 **Node Type과 Relation Type만 남긴 경로 패턴** 이다.

| Meta-path | 의미 | 추천 설명 |
| --- | --- | --- |
| Article → Company ← Article | 같은 기업을 다룬 기사 | 최근 읽은 기사와 동일한 기업을 다룸 |
| Article → Topic ← Article | 같은 주제 기사 | 최근 관심 주제와 관련된 기사 |
| Article → Event ← Article | 같은 사건 기사 | 같은 이슈를 다룬 다른 기사 |
| Article → Company → Industry ← Company ← Article | 같은 산업 기사 | 같은 산업에 속한 기업 관련 기사 |
| Article → Company → COMPETES_WITH → Company ← Article | 경쟁사 기사 | 관심 기업의 경쟁사 이슈 |

---

## 6-3. Subgraph와 후보 생성

전체 그래프를 매번 모두 탐색할 필요는 없다.

추천 시에는 사용자 주변의 작은 그래프만 잘라서 사용할 수 있는데, 이를 **Subgraph** 라고 한다.

```text
전체 KG
수십만~수백만 Node
수천만 Edge

        ↓

UserA의 최근 읽은 기사 20개
→ 관련 Entity 100개
→ 최근 후보 Article 1,000개
→ Ranking
→ Top 20
```

---

## 6-4. Rule / Path 기반 점수 계산

초기에는 별도의 모델 없이 사람이 직접 가중치를 정해서 추천 점수를 계산할 수 있다.

예시:

```text
같은 Event    +5
같은 Company  +4
같은 Person   +3
같은 Topic    +2
같은 Industry +1
```

후보 기사 B가

- 공통 Company 1개
- 공통 Topic 2개

를 가진다면:

```text
점수 = 1 × 4 + 2 × 2 = 8점
```

### 핵심 구분

- **Graph Traversal** → 후보를 찾는 단계
- **Ranking** → 후보 중 무엇을 먼저 보여줄지 결정하는 단계

# Part 7. 그래프 추천과 모델 학습 추천의 차이

그래프를 사용한다고 해서 반드시 모델 학습이 필요한 것은 아니다.

핵심 차이는 **추천 점수를 사람이 정하는가, 모델이 데이터에서 학습하는가** 이다.

| 구분 | 그래프 규칙 기반 추천 | 모델 학습 기반 추천 |
| --- | --- | --- |
| 점수 기준 | 사람이 직접 정의 | 사용자 행동 데이터에서 학습 |
| 학습 데이터 | 없어도 가능 | 클릭, 읽은 시간, 저장 등 필요 |
| 초기 서비스 | 강함 | Cold Start 문제 |
| 설명 가능성 | 높음 | 상대적으로 낮음 |
| 개인화 | 제한적 | 강함 |
| 예시 | 같은 Event +5 | P(click \| user, article) 예측 |

---

## 7-1. GNN은 무엇을 학습하는가?

GNN은 **Graph Neural Network** 의 약자로, 주변 Node들의 정보를 모아 각 Node의 표현을 학습하는 모델이다.

예를 들어 NVIDIA 주변에 다음 Node들이 있다고 하자.

```text
- Semiconductor
- AI
- GPU
- Jensen Huang
- AMD
- 관련 기사
```

GNN은 이 주변 정보를 이용해 NVIDIA를 다음처럼 표현할 수 있다.

```text
"NVIDIA는 AI, 반도체, GPU와 강하게 관련된 Node"
```

다만 개인화 추천 GNN을 학습하려면 일반적으로 다음과 같은 사용자 행동 로그가 필요하다.

```text
User - Article 클릭
User - Article 열람
User - Article 저장
```

기사와 Entity만 있는 지식그래프에서도 그래프 표현 학습은 가능하지만, 개인화 추천의 정답 데이터는 부족할 수 있다.

# 2026-08-28 GLiNER2.5 실험 정리

## 1. 긴 문서 처리 방식 비교

기존에는 뉴스 기사를 문장 단위로 나누어 모델에 입력했지만, GLiNER2.5의 `extract_long()`을 이용해 기사 전체를 처리하는 방식을 테스트했다.

| 방식                  | Event/기사 | 결과           |
| ------------------- | -------: | ------------ |
| `extract()`         |      0.4 | 단일 윈도우       |
| `extract_long(384)` |      0.3 | 긴 본문 처리 가능   |
| `extract_long(512)` |      0.4 | 384와 큰 차이 없음 |
| `extract_long(768)` |      0.4 | 384와 큰 차이 없음 |

**실제 추출 예시 (`extract()`, exp4_A)**

* 실버바 기사: `국내외사건` | subject=`실버바`
* 축의금 기사: `공개` | subject=`은가은이`, `은가은은`, `은가은을` (3건)
* 10건 중 Event가 나온 기사는 **2건**뿐이며 와인·어빈·KTX 등은 0건

**결론**

* chunk 크기 384~768 사이에서는 추출량 차이가 거의 없었다.
* 긴 뉴스 기사 처리를 위해 `extract_long()`을 사용하는 것은 유효하지만, chunk 크기 자체가 Event 추출량을 크게 좌우하지는 않았다.
* 이후 실험에서는 `chunk=384`를 기준으로 사용했다.

## 2. Event Schema 구조 비교

처음에는 AI Hub 31종 Event를 하나의 `news_event` 구조에 모두 넣었지만, Event 추출량이 지나치게 적었다.

| Schema                     | Event/기사 |
| -------------------------- | -------: |
| AI Hub 31종 단일 `news_event` |      0.3 |
| 7개 Domain으로 분리             |  **1.4** |

**실제 추출 예시 비교**

| 기사         | 31종 단일                  | Domain7 분리                       |
| ---------- | ----------------------- | -------------------------------- |
| 실버바        | `국내외사건` | subject=`실버바` | Event 없음                         |
| 축의금 30만원   | `공개` ×3                 | `증권매매` ×5 + `부동산매매` ×4 + `공개` ×1 |
| 박동빈 사별     | Event 없음                | `증권매매` + `부동산매매`                 |
| KBS 뉴스(가자) | Event 없음                | `산업제품매매` + `공개`                  |

**결론**

* 31개의 Event Type을 한 번에 판단하도록 하는 방식은 GLiNER2.5 Zero-shot 환경에서 부담이 큰 것으로 보였다.
* Event 후보를 Domain 단위로 좁히자 추출량이 약 **4.7배 증가**했다.
* 다만 Domain7은 **Event 추출량은 증가했지만 오분류도 함께 증가했다.**
* Event Ontology를 너무 세분화하기보다 의미적으로 묶어주는 방식이 더 적합할 가능성을 확인했다.

## 3. Description 포함 여부 비교

입력 데이터를 다음 두 가지로 비교했다.

```text
title + content
```

```text
title + description + content
```

| 입력                            | Event/기사 |
| ----------------------------- | -------: |
| title + content               |      1.3 |
| title + description + content |  **1.4** |

**실제 차이**

* 축의금 기사: description 제외 시 Event **10건**, 포함 시 **10건**으로 동일
* description 포함 시에만 실버바 기사에서 `산업제품매매` 1건 추가
* Entity 수준에서는 `실버바`(product), `고금리`(law_policy) 등이 추가로 잡히는 경우가 있었다.

**결론**

* description 추가에 따른 변화는 크지 않았다.
* 다만 추출량이 소폭 증가했고 추가 정보 손실도 없기 때문에 이후에는 `title + description + content`를 사용했다.

## 4. Threshold 비교

Event 추출 Threshold를 변경하며 추출량을 비교했다.

| Threshold | Entity/기사 | Relation/기사 | Event/기사 |
| --------: | --------: | ----------: | -------: |
|      0.40 |       6.7 |         0.0 |      1.4 |
|      0.35 |       7.2 |         0.0 |      1.8 |
|      0.30 |       7.2 |         0.3 |  **2.4** |

**실제 추출 변화 (`threshold=0.3`)**

* 축의금 기사: `증권매매` **7건**, `부동산매매` 4건, `공개` 1건
* KBS 뉴스: `산업제품매매` **2건** + `공개` 2건
* Event가 나온 기사 수: 0.35 기준 **3건** → 0.3 기준 **5건**
* Relation도 처음으로 등장: `works_for` (콜 어빈 → 다저스, confidence 0.47)

**결론**

* Threshold를 낮출수록 Event 추출량은 증가했다.
* 그러나 실제 결과에서는 잘못된 Event도 함께 증가하는 패턴이 나타났다.
* 단순 추출량보다 Precision을 고려해 이후에는 **0.35**를 기준값으로 사용했다.

## 5. 통합 호출 vs 분리 호출

GLiNER2.5의 Entity, Relation, Event를 한 번에 추출하는 방식과 각각 별도로 호출하는 방식을 비교했다.

| 방식    | Entity/기사 | Event/기사 | sec/기사 |
| ----- | --------: | -------: | -----: |
| 통합 호출 |       6.7 |  **1.4** |  0.838 |
| 분리 호출 |   **8.0** |      0.9 |  0.843 |

**실제 추출 차이**

| 기사          | 통합 호출            | 분리 호출        |
| ----------- | ---------------- | ------------ |
| 축의금 30만원    | Event **10건**    | Event **9건** |
| 박동빈 사별      | `증권매매` + `부동산매매` | Event 없음     |
| KBS 뉴스      | `산업제품매매` + `공개`  | Event 없음     |
| Entity(축의금) | 7건               | **10건**      |

**결론**

* Entity는 분리 호출에서 조금 더 많이 추출되었다.
* Event는 통합 호출에서 더 많이 추출되었다.
* Event가 나온 기사도 통합 3건, 분리 1건으로 차이가 있었다.
* 실행 시간은 거의 차이가 없었다.
* GLiNER2.5의 Unified IE 특성을 살리기 위해 이후에는 **통합 호출**을 사용했다.

## 6. Qwen3-1.7B와 Event 추출 결과 비교

동일한 뉴스 10건을 기준으로 GLiNER2.5와 Qwen3-1.7B의 Event 결과를 정성 비교했다.

### GLiNER2.5

* 10건 중 Event가 나온 기사: **3건**
* AI 해설 기사, 스포츠, 인프라 기사 등 7건은 Event 0건
* 축의금 기사에서 잘못된 Event가 반복 생성됐다.

```text
증권매매 | subject=박현호와
증권매매 | subject=박현호
증권매매 | subject=은가은은
부동산매매 | subject=박현호와
부동산매매 | subject=박현호
공개 | subject=은가은은
...
```

총 10건이 생성됐다.

* 박동빈 사별 기사에서도 `증권매매`, `부동산매매`로 잘못 분류
* KBS 가자지구 뉴스에서도 `산업제품매매`, `공개`로 잘못 분류

### Qwen3-1.7B

* **10건 모두** Event 약 2건씩 추출
* 자연어 문장 형태로 추출하기 때문에 기사 전체 맥락이 상대적으로 잘 드러났다.

**축의금 기사**

* 출산 이후 산후 탈모를 고백한 사건
* 박현호가 갈등 끝에 집을 나간 사건

**실버바 기사**

* 투자자들이 금과 은을 적극적으로 매입한 사건
* 홈쇼핑에서 골드·실버바 준비 물량이 빠르게 완판된 사건

**KBS 뉴스**

* 이스라엘 폭격으로 가자지구 민간인 사상자가 발생한 사건
* 하마스 무장해제와 이스라엘 철군에 합의한 사건

**결론**

* 현재 정성 비교에서는 Qwen3-1.7B가 Event 발견과 기사 맥락 이해에서 GLiNER2.5보다 안정적인 결과를 보였다.
* GLiNER2.5는 구조화된 출력에는 장점이 있지만 Event Type 오분류 문제가 컸다.
* 다만 이후 일부 GLiNER 입력에서 전처리 오류가 확인되었기 때문에, **수정된 동일 입력을 기준으로 재비교한 뒤 최종 판단할 필요가 있다.**
* 향후 GLiNER는 Entity/Relation, Qwen은 Event를 담당하는 하이브리드 구조도 검토할 수 있다.

## 7. Event Ontology 축소

기존 AI Hub 31종 Event Type은 GLiNER2.5 Zero-shot 모델이 구분하기에 너무 세분화되어 있다고 판단했다.

따라서 Event Ontology를 의미적으로 통합해 **영어 12종**으로 축소했다.

```text
sports_result
athlete_career_change
entertainment_activity
financial_performance
asset_transaction
acquisition_investment
market_analysis
product_launch
technology_development
policy_regulation
construction_infrastructure
incident_crisis
```

### 결과

| 설정              | Entity/기사 | Relation/기사 | Event/기사 |
| --------------- | --------: | ----------: | -------: |
| 기존 Domain7 한국어  |       6.7 |         0.0 |      1.4 |
| 영어 12종 Ontology |   **7.0** |     **1.6** |  **1.6** |

**실제 추출 예시**

| 기사        | Domain7          | 영어 Ontology                      |
| --------- | ---------------- | -------------------------------- |
| 어빈        | Event 0건         | `sports_result` ×2               |
| KTX 세종선   | Event 0건         | `construction_infrastructure` ×3 |
| 박동빈 사별    | `증권매매` + `부동산매매` | **Event 0건**                     |
| KBS 뉴스    | `산업제품매매` + `공개`  | `policy_regulation`              |
| 실버바       | Event 0건         | `acquisition_investment`         |
| 김빈우 발리 이주 | Event 0건         | `acquisition_investment`         |

**Relation 추출 예시**

```text
works_for
콜 어빈 → 다저스

works_for
에드가르도 엔리케스 → 다저스

located_in
다저 스타디움 → 미국
```

**개선된 점**

* `증권매매`, `부동산매매`, `공개` 등의 기존 오분류가 감소했다.
* 기존에는 거의 나오지 않던 Static Relation이 평균 **1.6건/기사** 추출됐다.
* Entity 추출량도 6.7 → 7.0으로 소폭 증가했다.
* 이를 통해 영어 Schema가 GLiNER2.5에 더 적합할 가능성을 확인했다.
* 단, **추출량 증가가 정확도 향상을 의미하는 것은 아니므로 추가 검증이 필요하다.**

**남은 문제**

* 축의금 기사: `financial_performance ×7`
* KBS 뉴스: 국제분쟁을 `policy_regulation`으로 분류
* 실버바와 김빈우 이주 기사에서 `acquisition_investment` 오분류

## 8. Event Description 보강

새로운 오분류로 `financial_performance`가 과도하게 생성되는 문제가 발생했다.

축의금 30만원이라는 개인 금액 표현을 기업 실적으로 판단해 다음과 같은 결과가 생성됐다.

```text
financial_performance | subject=은가은이
financial_performance | subject=은가은
financial_performance | subject=은가은은
financial_performance | subject=은가은을
...
```

총 7건이 생성됐다.

이를 해결하기 위해 Description에 다음 조건을 추가했다.

```text
기업의 매출, 영업이익, 순이익 등 실제 기업 실적일 때만 사용
단순 금액, 개인 비용, 축의금 등에는 사용하지 않음
```

`policy_regulation`에도 국제분쟁이나 외교 협상을 정책·규제로 판단하지 않도록 설명을 강화했다.

### 결과

* 축의금 기사: `financial_performance ×7` → **변화 없음**
* KBS 뉴스: `policy_regulation` → `financial_performance`로 **오분류 Type만 이동**
* 어빈 기사: `sports_result ×2` 정상 유지
* KTX 기사: `construction_infrastructure ×3` 정상 유지

**결론**

* GLiNER2.5는 자연어 Description의 Negative Constraint를 강하게 반영하지 않는 것으로 보였다.
* Description을 계속 수정하는 방식만으로 Event 오분류를 해결하는 데에는 한계가 있다고 판단했다.

## 9. `other_event` 추가 실험

12개 Event Type 중 적절한 타입이 없는 사건을 억지로 기존 타입에 넣는 문제를 막기 위해 `other_event`를 추가했다.

```text
12종 Event
+
other_event
=
13종
```

### 결과

```text
other_event 추출: 0건
전체 Event: 16건
```

**오분류 이동 사례**

| 기사     | v2                         | v3                      |
| ------ | -------------------------- | ----------------------- |
| KBS 뉴스 | `financial_performance`    | `sports_result`         |
| 축의금    | `financial_performance ×7` | 동일                      |
| 실버바    | `acquisition_investment`   | `financial_performance` |

**결론**

* `other_event`를 추가해도 실제로 선택되지 않았다.
* 기존 오분류가 사라지기보다 다른 잘못된 Event Type으로 이동하는 패턴이 반복됐다.
* GLiNER2.5 Zero-shot Event Classification을 Ontology 이름과 Description만으로 세밀하게 제어하기에는 한계가 있는 것으로 보인다.

## 10. 뉴스 전처리 문제 발견

Ontology 실험 결과를 확인하던 중 일부 AI 해설 기사의 모델 입력 길이가 비정상적으로 짧은 것을 발견했다.

### 수정 전

| 기사        |  입력 길이 |
| --------- | -----: |
| 와인 관련 기사  | 약 145자 |
| 실버바 관련 기사 | 약 293자 |

실버바 기사의 경우 실제 모델에는 다음 정도의 내용만 들어가고 있었다.

```text
지난해부터 시작된 귀금속 광풍에 투자자들이 뭉칫돈을 싸들고
앞다퉈 금과 은을 사들였다.

올해 초 국내 한 홈쇼핑에서 진행한 골드·실버바 판매 방송에선
준비한 물량이 1시간도 채 안 돼 다 팔리는 일도 일어났다.
```

이후 Key Points와 본문 섹션 대부분은 누락됐다.

### 원인

AI 해설 기사에서 `Key Points` 이전 내용만 사용하고 이후 본문 대부분을 제거하고 있었다.

전처리를 수정해 다음 내용을 포함하도록 변경했다.

```text
Key Points
+ 본문 섹션 1
+ 본문 섹션 2
```

타임라인과 용어 해설은 제외하고 최대 약 2,500자까지 사용했다.

### 수정 후

| 기사  |   수정 전 |       수정 후 |
| --- | -----: | ---------: |
| 와인  | 약 145자 | **1,959자** |
| 실버바 | 약 293자 | **2,099자** |

수정 후 실버바 기사에는 다음과 같은 핵심 내용까지 포함된다.

```text
은 가격은 고점 대비 51.3% 하락

금리 인상 기조가 이어질 것으로 예상되면서
당분간 은 가격 반등이 어려울 것으로 전망

1월 고점 이후 현재 온스당 가격이 큰 폭으로 하락
```

**결론**

* 기존 GLiNER Event 실험 일부는 모델 성능 문제뿐 아니라 **입력 데이터 자체가 지나치게 잘려 있었던 영향**을 받았을 가능성이 있다.
* 특히 AI 해설 기사에서 Event가 추출되지 않았던 결과는 다시 검증해야 한다.
* Ontology 실험 결과를 최종 판단하기 전에 수정된 전처리를 기준으로 동일 조건 재실험이 필요하다.

---

## 오늘 결론

* GLiNER2.5의 `extract_long()`으로 긴 뉴스 기사를 처리할 수 있으며 chunk 384~768 사이의 추출량 차이는 크지 않았다.
* AI Hub 31종 Event를 그대로 사용하는 것보다 Domain 분리 및 Ontology 축소가 Event 추출량 증가와 일부 오분류 감소에 효과가 있었다.
* Threshold를 낮추면 Event 추출량은 증가했지만 잘못된 Event도 함께 증가했다.
* Entity/Relation/Event 통합 호출이 Event 추출에서는 분리 호출보다 유리했다.
* 영어 Ontology 적용 이후 Entity 추출량이 소폭 증가하고 Static Relation이 새롭게 추출됐다. 다만 정확도 향상 여부는 추가 평가가 필요하다.
* Event는 특정 Type으로 과분류되는 문제가 지속됐다.
* Description 강화와 `other_event` 추가만으로는 Event 오분류를 해결하지 못했다.
* 현재 정성 비교에서는 Qwen3-1.7B가 Event 발견과 문맥 이해에서 더 안정적인 결과를 보였다.
* 다만 일부 GLiNER 입력에서 **전처리 오류**가 발견됐으므로 Qwen과의 비교 또한 수정된 동일 입력 기준으로 다시 검증할 필요가 있다.
* AI 해설 기사 입력 길이를 와인 **145 → 1,959자**, 실버바 **293 → 2,099자**로 정상화했다.
* 다음 단계에서는 수정된 입력 데이터로 동일 Ontology를 재실행한 뒤 GLiNER2.5의 Event 활용 가능성을 다시 판단한다.

# 7. GitLab ↔ Jenkins 연결

초기에는 Jenkins 전용 SSH Key를 생성하여 GitLab Deploy Key 방식으로 연결하려 했습니다.

그러나 서버에서:

```text
lab.ssafy.com:22
→ BLOCKED
```

임을 확인했습니다.

따라서 SSH 방식은 폐기하고 **HTTPS + GitLab Deploy Token 방식**으로 변경했습니다.

GitLab Deploy Token에는 최소 권한인:

```text
read_repository
```

만 부여했습니다.

Jenkins에는 이를 `Username with password` Credential 형태로 저장했습니다.

```text
ID: gitlab-deploy-token
```

이후 Jenkins Pipeline에서 GitLab Repository의 `master` 브랜치를 직접 Checkout하는 테스트를 수행했고 **Pipeline SUCCESS**를 확인했습니다.

현재 연결 상태:

```text
GitLab master
      ↓ HTTPS :443
Deploy Token
      ↓
   Jenkins
      ↓
 Checkout
      ✅
```
