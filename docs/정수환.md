## 1. NER 모델 (KPF-bert-ner)

- 한국언론진흥재단(빅카인즈)이 뉴스 코퍼스로 학습시킨 개체명 인식 모델
- **TTA 표준 개체명 태그셋(TTAK.KO-10.0852)** 기반, 15개 대분류 × 150개 세분류
- 대분류: PS(인물), LC(지역), OG(기관), AF(인공물), DT(날짜), TI(시간), CV(문명), AM(동물), PT(식물), QT(수량), FD(학문분야), TR(이론), **EV(사건)**, MT(물질), TM(용어)
- 뉴스 특화 카테고리인 "사건(EV)"이 기본으로 포함돼 있어서, 별도 라벨링 데이터 없이도 개체+사건 태깅이 어느 정도 가능
- **실무 이슈**: huggingface config.json에 라벨이 `LABEL_0~299`로 익명화돼 있어 실제 카테고리명 매핑이 별도로 필요함
- 대안: `klue/roberta` 계열은 라벨이 투명하지만 카테고리가 기본적(PER/LOC/ORG 등)이라 EV 같은 세분류가 없음

## 2. 키워드/개념 추출 알고리즘 계보

### TextRank의 한계
- PageRank를 텍스트에 응용한 그래프 기반 알고리즘 (2004년)
- 논문 벤치마크(RaKUn, 2019) 기준 15개 데이터셋 중 **단 한 번도 1위를 못 함** — 그래프 기반 계열 중 가장 낮은 성능
- 개선판들: SingleRank(빈도 가중치 추가), **PositionRank(위치+빈도, 뉴스 도메인에 특히 적합)**, TopicRank/MultipartiteRank

### 통계 기반 — YAKE
- 그래프 없이 순수 통계(대소문자, 위치, 빈도)만으로 계산, 언어 독립적, 매우 빠름

### 임베딕 기반 — KeyBERT
- SBERT로 문서 전체와 후보 단어의 코사인 유사도를 계산해 키워드 선정
- **KeyBERT 자체는 알고리즘/로직일 뿐, 실제 성능은 내부 SBERT 임베딩 모델 품질에 좌우됨**
- 한국어는 `jhgan/ko-sroberta-multitask` 추천 (KorSTS 기준 84~85점)
  - RoBERTa 기반, max_seq_length 128 토큰 제약 → 긴 기사 전문은 chunk 단위로 넣어야 함
  - Mean Pooling 방식으로 문장 벡터 생성

### 실무 조합
- PositionRank(저비용) + KeyBERT(의미 기반) 점수를 정규화 후 가중합해서 종합 스코어링

## 3. SBERT(Sentence-BERT) 원리

- 일반 BERT는 문장 유사도 비교에 최적화되어 있지 않음 (문장쌍을 매번 통째로 재계산해야 해서 느림)
- SBERT는 **샴 네트워크 구조**로 문장쌍 데이터(NLI, STS)를 학습시켜, 문장을 독립적으로 벡터화해도 의미 유사도가 코사인 유사도로 잘 반영되도록 만든 모델
- 한 번 벡터화해두면 이후 비교는 벡터 연산만 하면 되므로 빠름

## 4. Event Extraction — 오늘 가장 깊게 판 부분

### Entity/Concept 추출과 Event 추출은 완전히 다른 작업
- Entity 추출(NER) → **Entity 노드**
- Concept 추출(KeyBERT) → **Concept 노드**
- **Event 추출(Trigger + Argument)** → **Event 노드** (전혀 다른 작업, 오늘 계속 헷갈렸던 지점)

### 시행착오 — 방법론 탐색 과정
1. **임베딩/클러스터링 계열 (AWS 뉴스클러스터링 레포, LLM 클러스터링 논문)**
   - 실제로는 "여러 기사를 사건 단위로 묶는 것"(Event Matching/Story 클러스터링)이지, 문장 내부의 사건 구조를 뽑는 게 아님
   - DBSCAN 등은 "비슷하다/아니다"만 판단, 관계 타입·방향성·인과관계는 표현 못함
2. **SpERT (Span-based Joint Entity and Relation Extraction, 2019)**
   - Entity + Relation(주어-관계-목적어 트리플)을 조인트로 추출
   - 하지만 트리거(무슨 행위)나 시점, 확정성(ACTUAL/PLANNED 등) 정보가 없어서 Event 노드를 채우기엔 부족
   - "협력"이라는 관계 라벨 하나로는 "발표했다"는 구체적 사건인지 단순 배경 서술인지 구분 불가
3. **LLM 기반 생성 방식 (최종 채택 방향)**
   - Trigger + Argument를 텍스트 생성 태스크로 재정의하는 게 최신 학계 트렌드 (2025 서베이 논문 확인)
   - 실제 시도: `sogm1/qwen3-1.7b-news-event-merged` (Qwen3-1.7B LoRA 파인튜닝 모델)
     - 뉴스 텍스트 → 카테고리 분류 + 핵심 이벤트 리스트를 dict 형태로 생성
     - 사건을 자연어 문장으로 통째로 뽑아주는 게 강점
     - 다만 ACTOR/TARGET/PLACE/occurredAt/status 등 세부 필드는 없어서 후처리 필요

### 방법론 비교 정리
| 방법 | 정확도 | 비용 | 비고 |
|---|---|---|---|
| 규칙/트리거 사전 | 낮음 | 매우 낮음 | 1차 스크리닝용 |
| 의존구문분석 | 중간 | 낮음 | 한국어는 조사 기반 역할 추출에 유리 |
| 지도학습 시퀀스 라벨링 | 높음 | 데이터 필요 | 한국어 EE 데이터 희소 (AIHub에 "한국어 다중 이벤트 추출 데이터" 존재 확인, 검토 필요) |
| **LLM 기반 생성** | 높음 | 높음(비용) | 현재 채택 방향, 후보 좁혀서 넘기면 비용 절감 가능 |

## 5. 온톨로지 설계 변경사항 (팀 문서 v2)

- Issue + Story → **Story로 통합**
- **EventMention** 개념 도입: 기사 내 반복 언급되는 사건 표현의 중간 데이터, 최종 그래프엔 저장 안 함 (Canonical Event로 병합 후 저장)
- **Evidence는 별도 노드 대신 엣지 속성(evidenceArticleId 등)으로 처리** → 불필요한 노드 증식 방지
- **Statement 노드 신설**: 전망/주장/평가를 실제 발생한 Event와 명확히 분리
- INVOLVES{role} → **ACTOR/TARGET/PLACE로 세분화** (쿼리 효율 + 명확성)
- Topic은 **고정 6개** (정치/경제/사회/생활문화/IT과학/스포츠엔터), AI가 새 Topic 생성 못하도록 제한
- CAUSES/RESPONDS_TO 관계는 **N:1에서 N:M으로 수정** (하나의 원인이 여러 결과를 낳는 실제 뉴스 패턴 반영)

## 6. 기타

- **Property Graph(Neo4j) vs RDF**: Property Graph는 엣지에도 자유롭게 속성(confidence, evidence 등)을 붙일 수 있어 지금 온톨로지 설계에 적합. RDF는 엣지에 속성을 붙이려면 reification이라는 우회가 필요해 복잡함
- **엣지 분류가 필요한 이유**: 방향성/인과관계 표현, hop 기반 추천 시 관계별 감쇠율 차등 적용, 계층 관계(정보 공백 계산의 핵심) 구조화, Domain-Range 제약을 통한 데이터 품질 검증 등
- **페이지랭크 계열은 "관계가 무엇인지 판단"에는 못 쓰고, "이미 만들어진 그래프에서 무엇이 중요한지 필터링"에만 활용 가능** (예: Concept 허브 필터링, 오늘의 트렌드 산정)

## 1. NER 후처리 파이프라인 (KPF-bert-ner)

### 발견된 문제 7가지 (우선순위 순)

1. **score 필터링 부재** — 13%(154개)가 score 0.7 이하인데도 그대로 섞여 있음
2. **서브워드(`##`) 파편** — 전체의 약 25%. `aggregation_strategy="simple"`을 적용했는데도 라벨이 완전히 일치하지 않으면 병합이 안 되고 새어나옴
3. **반복 등장 고유명사의 라벨 일관성 붕괴** — 문장 단위 독립 추론이 원인 (예: "피노"가 인물→과일→음식으로 오락가락)
4. **짧은 고유명사의 문맥 의존성 오류** — "다저스"만 단독으로 나오면 인물로 오인식
5. **원천 데이터 중복** — 같은 기사가 여러 카테고리에 중복 존재, NER 이전 단계에서 안 걸러지면 개체 빈도 통계가 부풀려짐
6. **클래스 체계 과잉 세분화** — TTA 150개 세분류 중 실사용은 소수
7. **정량 평가(Gold Label) 부재** — 지금까지 정성 평가만 진행

**합의된 우선순위**: 1(score 필터) → 2(서브워드 병합) → 5(중복 제거)를 가장 적은 노력으로 가장 큰 효과를 내는 조합으로 판단, 먼저 구현. 3·4번은 Entity Linking 단계와 통합 예정.

### 구현 (`ner_postprocess_pipeline.py`)

- 처리 순서: **중복 기사 제거 → 서브워드 병합 → score 필터** (역순으로 하면 병합 전에 낮은 점수로 discard되는 파편이 생길 수 있어 이 순서가 맞음)
- 서브워드 병합 시 score는 `min(직전, 파편)` 사용 — 평균이 아닌 min을 쓴 이유는 병합된 개체명의 신뢰도를 보수적으로(가장 약한 고리 기준) 잡기 위함
- 병합 후 1글자만 남으면 폐기 (`min_merged_length`)
- `dedup_articles()`는 title+content 해시로 판정, `removed_article_map`으로 감사(audit) 근거를 남김
- score 3-tier: auto_approved(≥0.9) / review_queue(0.5~0.9) / discarded(<0.5)
- `aggregation_strategy="simple"`은 인접 서브워드의 **라벨이 완전히 같을 때만** 병합해줌 — 그래서 이 정도로도 파편이 남는 것

## 2. LQ-FSE-base (한국어 금융 문장 추출/역할 분류 모델)

- 구조: RoBERTa(klue/roberta-base) 인코더 + Inter-sentence Transformer(2 layers) + Dual Classifiers(Extraction Head + Role Head)
- 4-way Role 분류: **outlook**(전망/예측) / **event**(사건/조치) / **financial**(재무/실적 수치) / **risk**(리스크 요인)
- 입력 제약: 문장당 최대 128 토큰, 문서당 최대 30문장 — **30문장 초과 시 뒤쪽은 그냥 잘려서 버려짐** (앞부분만 씀, chunking 등 별도 처리 없이는 뒷부분 손실)
- **padding**: 모델 입력 텐서 크기를 고정하기 위해 부족한 만큼 가짜 값(`[PAD]` 토큰, 빈 문장)을 채우는 것. `attention_mask`/`doc_mask`로 실제 데이터와 padding을 구분해 모델이 padding을 무시하게 함

### 온톨로지 노드 매핑 결정

| LQ-FSE 라벨 | 목적지 | 근거 |
|---|---|---|
| event | Event 노드 | 기존 qwen3 이벤트 추출 파이프라인과 통합 |
| financial | Event 노드로 승격 | "실적발표" 같은 사건 + 수치는 evidence로 흡수, Statement 하나로 두면 ACTOR/TIME 기반 질의가 안 됨 |
| outlook | Statement (type=prediction, stance=positive) | |
| risk | Statement (type=prediction, stance=risk) | outlook과 같은 예측/의견 축, stance로만 구분해 노드 증식 방지 |

- financial과 event가 결국 같은 목적지로 가기로 하면서, Role Head를 **event+financial 통합 + CLAIM(신설) + outlook + risk** 4-way로 재구성하기로 함 — 클래스 개수는 유지하면서 구성만 교체
- **CLAIM**(assertor 있는 인용/전언 문장, 예: "정부는 ~라고 밝혔다")은 기존 4-way에 없던 카테고리라 재학습 필요. Role Head 재학습은 **문장 단위 라벨링**(sentence → label 1개)이라 NER처럼 span 단위 라벨링보다는 단순함
- 인용동사 사전("밝혔다/주장했다/전했다" 등)으로 1차 필터링하면 CLAIM 라벨링 대상 자체를 줄일 수 있음 (recall 손실 리스크는 있음)

## 3. 아직 안 정해진 온톨로지 구멍

- **Topic**: 6개 고정 카테고리 분류 — 원천 데이터 category 필드가 맞는지 확인이 먼저, 안 맞으면 별도 분류기 필요
- **Statement(fact)**: LQ-FSE-base는 금융 도메인 전용이라 금융 외 "사실 문장"은 커버 못 함 — 범용 분류기 필요하거나 Event로 흡수하는 방향 검토
- **Story**: 개별 기사 레벨이 아니라 여러 기사/Event를 시간 축으로 묶는 corpus 레벨 클러스터링 — 아직 설계 안 됨
- **TIME EXPRESSIONS**: `DATE/TIME/DURATION/SET` 정규화 — 어떤 모델도 담당 안 함, 신규 구멍
- **CLAIM의 assertor**: 화자 식별 — Role Head로는 원천적으로 불가능(문장 단위 분류라 위치 정보 없음), 별도 span 추출 필요

## 4. Transformer 개념 복습

- **Head**: 공용 인코더(RoBERTa+Inter-sentence Transformer) 위에 얹혀 특정 태스크의 최종 출력을 만드는 얇은 출력층(대부분 `Linear(hidden_size, num_classes)` 수준). 인코더는 무겁고 재사용 가능, Head는 가벼워서 새 태스크마다 새로 붙이기 용이
- **`[CLS]` 벡터**: 문장 맨 앞에 인위적으로 삽입하는 특수 토큰의 벡터. 원래는 의미 없는 빈 토큰이지만, 학습 과정에서 분류 loss가 이 위치에만 걸리기 때문에 Self-Attention을 반복하며 문장 전체 정보를 흡수하도록 학습됨. 문장 분류(Role/Extraction Head)에 사용
- **Self-Attention**: 문장 속 모든 단어 쌍마다 Query-Key-Value로 "얼마나 관련 있는지" 점수를 매기고, 그 비중대로 서로의 정보(Value)를 섞는 메커니즘. "Self"는 참고 대상이 같은 시퀀스 내부라는 뜻 (번역처럼 입력↔출력이 다른 시퀀스를 참고하면 그냥 Attention)
- **토큰별 벡터(①) vs 문장 벡터(②)**: RoBERTa forward pass는 문장의 모든 토큰 벡터(①)를 어차피 계산하는데, Role Head는 그중 `[CLS]` 위치(②) 하나만 사용. 나머지는 지금까지 버려지고 있었음

### Span Head 설계 (assertor/content 추출용)

- Role Head(②, 문장 벡터 1개 입력)와 달리, **Span Head는 ①(토큰별 벡터 전부)을 입력**으로 받아 "몇 번째 토큰부터 몇 번째 토큰까지가 assertor/content인가"를 판정 (SQuAD 스타일 start/end logit)
- **중요한 구분**: ①을 재사용하는 건 "RoBERTa를 또 실행하지 않아도 된다"는 **연산 절약**일 뿐, "assertor 위치를 안다"는 뜻이 아님. Span Head가 실제로 assertor를 짚어내려면 여전히 **별도의 span 라벨링 데이터**(assertor_span: start/end 토큰 위치)로 학습해야 함
- CLAIM 판별(Role Head, 문장 단위 라벨) → assertor/content 추출(Span Head, span 단위 라벨)은 **완전히 별개의 두 라벨링 작업**. NER로 "정부"를 이미 뽑아뒀어도 "이 문장에서 정부가 화자 역할을 한다"는 건 다른 정보라 자동으로 해결되지 않음 (게다가 "관계자"·"소식통" 같은 assertor는 애초에 NER 대상도 아님)
- 현실적 절충안: kiwipiepy 의존구문분석 기반 규칙(인용동사 cue → 그 주어를 assertor로)으로 라벨링 없이 먼저 베이스라인을 만들고, 그 결과를 weak label 삼아 Span Head를 점진적으로 개선하는 부트스트래핑 방식

## 5. 참고 문서/자료

- **TimeML/TIMEX3**: 시간 표현 정규화 표준. `anchorTimeID`/`temporalFunction` 속성이 "다음달" 같은 상대 표현을 기준일(article publish date)로 계산하는 메커니즘 — 지금 스키마의 `provisional` 필드와 대응
- **ACE 2005 이벤트 주석 가이드라인**: ACTOR/TARGET/PLACE 구조의 표준. 원래 35개 role을 Actor 하나로 단순화하는 관행이 이미 있음 — 지금 팀 구조와 유사
- **PARC3 (Pareti, 2016)**: 인용 귀속(quotation attribution)을 source-cue-content 3요소로 태깅하는 스키마. assertor 필드 설계 시 참고할 구조
- **DirectQuote / NewsQuote**: 뉴스 도메인 전용 인용 추출 데이터셋, 화자를 entity에 링크하는 방식이 지금 구조와 맞닿아 있음

## 6. Runtime Data Carrier 설계 (검토 시작)

LQ-FSE 실행 중 계산되는 representation을 파이프라인 전체에서 재사용하기 위한 설계 문서를 전달받음. 핵심 구조:

- `ArticleInput` (원문) → `ArticleEncoding`(모델 계산 결과 owner) → `SentenceEncoding`(문장별 token/sentence/document context) → `SentenceProjectionSet`(ontology 해석) → `ExtractionRunContext`(작업 컨테이너)
- **Model Encoding과 Project Interpretation을 분리**: `SentenceEncoding`(모델이 어떻게 읽었는가)과 `SentenceProjection`(우리가 어떻게 해석했는가)을 별개 객체로 둬서, ProjectionPolicy를 바꿔도 LQ-FSE inference를 재실행할 필요 없음
- **Tensor는 runtime 내부에서만 유지**하고 DB/API에 노출 안 함. `EntityMention`/`EventCandidate` 등 Construction Artifact는 벡터를 복제 저장하지 않고 `SpanRef`(token 좌표 + char 좌표 포인터)로 필요할 때 조회
- → 다음 대화에서 단계별로 이어서 검토 예정

"별빛 뉴스" Figma 파일의 `Ver 3.0` 섹션을 하루 종일 붙잡고 있었다. 크게 세 갈래였다: (1) 저장됨 탭 레이아웃 개편과 Exploration 화면의 "더보기" 패턴 추가, (2) 키워드 기반 노드를 이벤트 기반으로 바꿨을 때 생기는 라벨 클러터 문제 탐색과 스토리 시각화 예시 제작, (3) 상대 시간 표현을 절대 시간 포맷으로 전부 통일하고 마지막엔 백엔드 API 명세와 화면을 대조해서 빠진 UI 6곳을 새 화면으로 채워 넣는 작업. 전부 기존 화면은 건드리지 않고 clone해서 옆에 추가하는 방식으로 진행했다.

## 1. 저장됨(북마크) 탭 — 한쪽으로 몰린 레이아웃을 2열 그리드로

기존 저장됨 탭이 카드가 한쪽에 몰려서 레이아웃이 지저분했던 걸 발견. 콘텐츠 폭을 꽉 채우는 2열 카드 그리드(564×190 카드 5장)로 다시 짰다. 나중에 API 대조 작업에서 이 프레임을 다시 clone해서 일괄 선택 체크박스 UI를 얹었는데, 그 과정에서 체크박스가 카드 제목 텍스트 위에 겹치는 버그가 났다 — 아래 "오늘의 실수" 항목 참고.

## 2. Exploration "더보기" 패턴 — 별로 늘리지 않고 카드 오버레이로

주변 노드가 15개를 넘을 때 나머지를 어떻게 보여줄지 고민하다가, 처음엔 8개를 추가로 별로 그려서 23개짜리 확장 그래프를 만들었다. 그런데 다시 보니 "이걸 계속 별로 늘리면 결국 또 복잡해지는 거 아닌가"라는 지적이 나와서, 별을 더 그리는 대신 **딤드 배경 + 리스트 카드 오버레이**로 방향을 바꿨다. 닫기 버튼은 원래 화면으로 돌아가도록 연결. 이 판단이 맞았던 이유는 결국 "그래프 확장"과 "목록 보기"가 다른 문제라는 걸 확인했기 때문 — 15개 안에서는 그래프가 관계를 보여주는 데 유리하지만, 넘치는 나머지는 그냥 훑어보면 되는 목록이라 카드가 더 적절했다.

## 3. 키워드 기반 → 이벤트 기반 노드로 바뀌면 생기는 문제

노드 라벨이 "북한", "반도체" 같은 키워드에서 "미국 북한 제재"처럼 이벤트 문장으로 바뀔 예정이라, 라벨이 길어지면서 별 위에서 지저분해질 걸 미리 우려했다. 확인해보려고 Home과 Exploration/01 두 화면만 파일럿으로 이벤트 기반 버전을 만들어봤는데, 실제로 Home 화면의 "선택된 노드" 궤도 링 장식과 긴 이벤트 라벨이 겹치는 걸 눈으로 확인했다. 우려가 아니라 실제 문제였다는 게 이번 파일럿의 핵심 소득.

그러다 기존에 이미 만들어져 있던 "시안 E(선택 전)"/"시안 F(선택 후)" 프레임을 다시 들여다봤는데, 이게 바로 이 문제에 대한 답이었다: Event(고정된 시간 위치의 +), Entity(선택 전엔 흐릿함), Line(이벤트 선택 시에만 등장하는 연결선), Concept("배경지식" 성운 스타일)로 4개 노드 타입을 이미 구분해두고 있었고, 이벤트들은 "은하수"라 부르는 대각선 시간축(왼쪽=과거, 오른쪽=현재)에 고정되어 있었다. 즉 라벨 클러터 문제는 새 노드 타입 체계를 새로 설계할 게 아니라 이미 있는 성운/은하수 컨셉을 제대로 적용하면 풀리는 문제였다.

## 4. 스토리(연관 이벤트 묶음) 시각화 3안 실험

"스토리를 어떻게 보여줄까"에 대해 패널 타임라인 / 방향성 흐름선(그라디언트 화살표) / 가로 타임라인 바 세 가지 옵션을 제안했고, 하나만 고르지 않고 셋 다 예시로 만들어봤다:
- 예시 A: 세로 패널 타임라인 (스파인 + 날짜별 마일스톤 4개)
- 예시 B: 색이 옅음→진함으로 흐르는 방향성 화살표 5개 구간 + 번호 배지
- 예시 C: 캔버스 하단 가로 타임라인 바 (점 6개 + 날짜 + 짧은 라벨)

세 개를 나란히 만들어보니 비교가 훨씬 쉬웠다 — 말로 설명할 때보다 실제로 그려봐야 장단점이 보인다는 걸 다시 확인.

## 5. 시간 표현 통일 — 상대시간 → 절대시간, 포맷은 두 번 갈아엎음

"최근 24시간", "13시간 전" 같은 상대 시간 표현이 실제 데이터 화면에는 맞지 않는다는 지적이 있어서 절대 시간으로 바꾸는 작업을 했다. 처음엔 `YYYY-MM-DD-HH-MM`(전부 하이픈) 포맷으로 갔는데, "시간·분 부분이 하이픈으로 이어지니까 오히려 헷갈린다"는 피드백을 받고 `2026.08.31 11:02` (점+콜론, 한국 뉴스식) 포맷으로 최종 확정해서 전체 재작업했다. 아이디로 배운 점: 포맷을 정할 때는 만들기 전에 후보를 2~3개 제시하고 실제 값으로 어떻게 보이는지 비교해서 고르는 게 나중에 전체 재작업을 줄인다.

이 스윕 과정에서 두 가지 버그를 잡았다:
- 정규식 `.test()`를 global 플래그(`/g`)로 재사용하면서 `lastIndex`가 이전 문자열에서 넘어와, 몇 개 항목이 조용히 스킵되는 버그. 검증 스윕(전체 프레임을 상대시간/구포맷 패턴으로 재검색)을 한 번 더 돌려서 놓친 걸 찾아냈다.
- 사용자가 대화 중간에 프레임 이름을 바꿔놔서("Exploration/01" → "Exploration/02") 내가 "반영이 안 됐다"는 리포트를 받고 다른 프레임인 줄 알았던 해프닝. 이후로는 이름으로 프레임을 찾을 때 기억에 의존하지 말고 항상 다시 검색해서 확인하는 습관을 들임.

## 6. 백엔드 API 명세 vs 화면 — 격차 6곳 채우기

전체 API 엔드포인트 목록(auth/user/home/article/activity/search/event-story/recommendation/graph)을 받아서 기존 화면과 대조했다. 노드 타입 체계(Event·Entity·Statement·Concept·Topic·Category vs API의 Article·Event·Story·Entity·Concept) 불일치는 구조적으로 큰 이슈라 일단 보류하고, 나머지 6개 구체적인 UI 격차를 새 화면으로 채웠다:

1. 회원가입에 아이디 중복확인 UI가 없고 로그인 식별자가 이메일뿐이라 API 설계와 어긋남 → 아이디 입력 필드 + 중복확인 버튼 + 성공 힌트 추가
2. 계정 설정에 회원탈퇴(`DELETE /users/me`) 버튼 없음 → 경고 문구 + 빨간 테두리 탈퇴 버튼 추가
3. 북마크 기사 일괄 변경 UI 없음 + 북마크 노드 전체 조회 화면 없음 → 체크박스 일괄 선택 바 추가, "즐겨찾기 노드" 탭 신설
4. 홈 "나를 위한 추천" 탭이 라벨만 있고 실제 화면 없음 → 추천 이유 태그가 붙은 카드 4개로 채움
5. 기사 상세에 관련 기사 영역이 비어있고 AI 요약 상태 표시가 없음 → 관련 기사 3건 + "AI 요약 완료" 배지 추가
6. 나의 기록에 개별/전체 삭제 버튼 없음 → 카드별 휴지통 아이콘 + "전체 삭제" 링크 추가

## 7. 오늘의 실수 — 체크박스가 텍스트를 가림

북마크 일괄 선택 체크박스를 카드 좌상단(16,16)에 얹었는데, 처음엔 그 아래 있는 소스명 텍스트(연합뉴스 등, y=20)뿐 아니라 제목·요약·링크까지 전부 오른쪽으로 밀고 폭까지 줄여버렸다. 스크린샷으로 보니 소스명과 "상세 보기" 링크가 두 줄로 줄바꿈되는 참사였다. 원인을 분석해보니 체크박스(y16~34)와 실제로 세로로 겹치는 건 소스명 텍스트(y20~34)뿐이었고, 제목(y46)·요약(y78)·링크(y156)는애초에 겹칠 일이 없었다. 필요한 만큼만 고치는 게 맞았는데 안전하게 간다고 4개를 다 건드린 게 오히려 새 버그를 만든 셈. 수정 후 재검증해서 한 줄로 깔끔하게 정리했다.

## 정리하며

오늘 배운 걸 한 줄로 요약하면: **UI 문제는 말로 논의하는 것보다 실제로 만들어서 스크린샷으로 보는 게 훨씬 빨리 답이 나온다** (더보기 패턴, 이벤트 라벨 클러터, 스토리 시각화 3안 모두 그랬다), 그리고 **작업 범위는 실제로 겹치는 부분만 정확히 고쳐야지, 안전 마진을 넓게 잡는다고 관련 없는 요소까지 건드리면 오히려 새 문제가 생긴다** (체크박스 사건).
