## 1. 프로젝트 착수부터 Event-Centric KG 구축안 설계까지 (~2026.08.26)

### 1.1 2026.08.20 — 뉴스 데이터 소스와 서비스 가능성 검증

**핵심 질문**

- 한국어 뉴스를 지속적으로 충분히 확보할 수 있는가?
- API가 표시하는 기사 수와 실제로 접근·저장할 수 있는 기사 수는 같은가?
- 단순 뉴스 추천과 구별되는 기능은 무엇이어야 하는가?

**확인한 내용**

- NewsAPI에 한국어 조건을 적용했을 때 응답은 정상이었지만 totalResults는 0이었다.
- GNews의 전 기간 추정 기사 수는 general 약 118,902건, business 약 83,168건, technology 약 42,060건 등이었다.
- 자체 수집 실험에서는 6시간 구간 59건, 24시간 275건을 수집했고 총 77개 언론사가 포함됐다.
- 무료·유료 API마다 호출량, 전문 제공, 실시간성, 재배포 조건이 달랐다.

**설계에 반영한 판단**

- 특정 뉴스 API 하나에 전체 수집 구조를 의존하지 않는다.
- 기사 수집과 Knowledge Graph 구축을 별도의 파이프라인 문제로 본다.
- 서비스의 차별점을 기사 목록 추천이 아니라 동일 사건 통합과 맥락 탐색에서 찾기 시작했다.

### 1.2 2026.08.21 — GDELT GKG의 서비스 적용 가능성 분석

**핵심 질문**

- GDELT GKG를 정제하면 서비스용 Knowledge Graph로 사용할 수 있는가?
- GKG의 THEMES·인물·기관·장소 정보는 우리가 원하는 사건 그래프와 같은가?

**확인한 내용**

- 특정 시점의 GDELT GKG 데이터 872건 중 한국어 기사는 0건이었다.
- 한겨레 영문판 기사에는 다수의 theme, entity, location 정보가 부착돼 있었다.
- GKG는 기사별 메타데이터를 풍부하게 제공하지만, 여러 기사가 지칭하는 동일한 현실 사건을 하나의 Canonical Event로 통합한 구조는 아니었다.

**설계에 반영한 판단**

~~~text
기사별 theme/entity 추출
≠ 여러 기사에 걸친 Canonical Event 구축
~~~

- GDELT는 theme·entity 후보나 데이터 분석을 위한 보조 소스로 둔다.
- 핵심 Event 통합은 별도의 extraction·resolution·fusion 파이프라인으로 설계한다.

### 1.3 2026.08.22~23 — 기사보다 사건을 탐색하는 사용자 경험 설계

**핵심 질문**

- 개인화 KG가 일반적인 뉴스 추천보다 무엇을 더 잘할 수 있는가?
- 화면의 별 하나는 Article, Topic, Entity, Event 중 무엇이어야 하는가?
- 사용자가 읽지 않은 배경 사건이나 중간 사건을 어떻게 추천할 것인가?

**정리한 서비스 문제**

- 같은 사건을 다룬 기사가 중복 노출된다.
- 현재 사건의 이전 배경과 후속 전개를 찾기 어렵다.
- 사실, 주장, 전망, 반응이 기사 문맥 안에서 섞인다.
- 기존 추천은 “관심사가 비슷해서”라는 설명에 머무르기 쉽다.
- 사용자가 무엇을 읽었는지는 알 수 있지만 어떤 맥락을 놓쳤는지는 알기 어렵다.

**설계에 반영한 판단**

- 기본 탐색 단위를 Article이 아니라 Event로 정했다.
- 전체 뉴스 KG와 사용자의 열람·관심 기록을 분리한다.
- 사용자가 읽은 두 사건 사이의 누락된 사건을 찾는 정보 공백 추천을 차별점으로 삼는다.
- Background, Continuation, Reaction, Larger Context, Actor Trajectory, Perspective 등 관계별 추천 후보를 구상했다.
- 여러 언론사가 동일 Event를 보도한 기사는 우측 고정 패널에서 함께 제공한다.
- 사용자에게 보이는 Event 이름은 사건을 이해할 수 있는 문장형으로 표현한다.

### 1.4 2026.08.24 — Knowledge Graph 기초 개념 정리

**핵심 질문**

- Knowledge Graph에 합의된 단일 정의가 있는가?
- RDF와 KG는 같은 것인가?
- ontology와 reasoning은 무엇인가?
- fact triple의 h, r, t와 추가 문맥 γ는 무엇인가?
- Temporal KG와 Event-Centric KG는 어떻게 다른가?

**학습한 내용**

- KG에는 모든 연구와 산업에서 공유되는 단일 정의가 없다.
- 일반적인 fact는 ⟨h, r, t⟩로 표현하며, γ는 논문에 따라 시간·조건·qualifier·provenance 등 추가 문맥을 나타낼 수 있다.
- RDF는 subject–predicate–object triple을 사용하는 W3C 데이터 모델이며 KG와 동의어가 아니다.
- ontology는 허용되는 개념, 관계, domain/range, 제약과 의미를 정하는 계약이다.
- RDF/OWL reasoning은 선언된 공리와 규칙으로부터 논리적으로 함의되는 사실을 도출하는 과정이다.
- Temporal KG는 사실이나 관계가 언제 유효한지에 초점을 두고, Event-Centric KG는 Event 자체를 first-class node로 둔다.
- Temporal과 Event-Centric은 배타적 분류가 아니며 하나의 KG에서 결합할 수 있다.

**설계에 반영한 판단**

- Event를 그래프의 first-class node이자 기본 탐색 단위로 둔다.
- 같은 actor와 action이 등장해도 시간·장소·수치가 다르면 별도 Event일 수 있다.
- 기사 속 동사를 그대로 새로운 relation으로 만들지 않고, 미리 정의한 ontology의 관계만 허용하는 schema-first 방식을 채택한다.
- 기사 발행 시각과 Event 발생 시각을 분리한다.

### 1.5 2026.08.25 — Event, Mention, Statement, Evidence의 의미 경계

**핵심 질문**

- 기사에 쓰인 사건 표현과 현실에서 발생한 사건은 같은 객체인가?
- 전망·주장·평가도 Event로 저장해야 하는가?
- Article 자체를 evidence로 보면 충분한가?
- 여러 기사에서 추출된 Event를 언제 하나로 병합해야 하는가?
- LLM이 predicate와 ontology를 자유롭게 생성하게 해도 되는가?

**정리한 의미 경계**

~~~text
기사에 실제로 쓰인 사건 표현
≠ 여러 기사 표현이 가리키는 현실 사건
≠ 누군가가 주장한 명제
≠ 그 추출을 뒷받침하는 원문 범위
~~~

| 개념 | 당시 정리한 의미 |
|---|---|
| Article | 기사 원문과 메타데이터 |
| EvidenceSpan | extraction 또는 assertion의 근거가 되는 원문 범위 |
| EventMention | 특정 기사에 나타난 사건 표현 |
| Event | 여러 EventMention이 가리키는 하나의 현실 사건 |
| Statement | 특정 발화자의 주장·전망·평가 |

**학습 및 설계 결과**

- “발화자가 인과를 주장했다”는 사실과 실제 세계의 인과 관계를 구분해야 한다.
- Event matching은 단순 clustering이 아니라 여러 문서에 걸친 identity resolution 문제다.
- 모델 출력은 최종 사실이 아니라 candidate와 score로 취급해야 한다.
- LLM은 gold data pre-annotation, 저신뢰 사례 검토, 복잡한 간접화법 처리 등 보조 역할로 제한한다.
- ontology.yaml을 허용 node/edge, domain/range, argument role, validation, model label, prompt의 단일 기준으로 사용하기로 했다.

### 1.6 2026.08.26 — 구현 가능한 KG 계약과 파이프라인 설계

**핵심 질문**

- 논문 속 개념을 실제 프로젝트의 저장 구조로 어떻게 축소할 것인가?
- 여러 기사에서 같은 현실 Event를 판정하는 절차는 무엇이어야 하는가?
- ontology, 모델, validation이 같은 schema를 사용하게 하려면 어떻게 해야 하는가?

**설계 순서**

~~~text
사용자 질문과 서비스 기능
→ 필요한 지식 단위
→ Ontology Contract
→ Entity/Event Identity와 Fusion
→ Assertion과 Evidence
→ Pipeline 책임과 Validation
~~~

**시스템 책임 분리**

- Control Plane: ontology, gold set, validation, model/ontology version
- Construction Plane: 수집, 추출, 정규화, resolution, fusion, relation 생성, validation, 저장
- Serving Plane: 트렌드, 검색, 관계 탐색, 추천, 개인 기록, 추천 설명

**Cross-document Event resolution 초안**

~~~text
새 EventMention
→ Event type·시간·주체 기반 후보 제한
→ embedding 기반 후보 검색
→ pairwise same-event 분류
→ cluster consistency 검사
→ 기존 Event 병합 또는 새 Event 생성
~~~

**설계에 반영한 판단**

- embedding 유사도뿐 아니라 Event type, actor, target, time, location, value, 상태와 기사 문맥을 함께 비교한다.
- 서로 다른 사건을 잘못 합치는 false merge가 하나의 사건을 나눠 저장하는 false split보다 더 위험하므로 보수적으로 병합한다.
- 모든 추출·관계 결과에 evidence, confidence, origin, model/ontology version, extraction time, review status를 보존한다.
- validation을 통과하지 못한 결과는 factual KG가 아니라 candidate 또는 quarantine 상태로 관리한다.
- 추천 후보는 relation별로 생성하고, 추천 이유는 graph path에서 만든다.

## 2. KG 스키마 및 Event/Statement Extractor 구체화 (2026.08.27)

### 2.1 오늘의 목표

8월 26일까지 정리한 개념적 구조를 팀 공통 KG schema와 실제 Information Extractor의 학습 기준으로 연결했다. 핵심은 Node와 Edge를 늘리는 것이 아니라, 무엇을 Event·Statement로 인정하고 어떤 후보만 최종 KG에 반영할지 명시하는 것이었다.

오늘 작업은 다음 흐름으로 이어졌다.

~~~text
KG의 Event/Statement 의미 경계 확정
→ annotation guideline 작성
→ 뉴스 본문 및 Gold Dataset 정제
→ Extractor·Retriever·Pairwise Reasoner 책임 분리
→ KG 저장 전 validation 기준 구체화
~~~

### 2.2 팀 공통 KG Schema 결정

| 대상 | 결정 |
|---|---|
| Article → Event | COVERS로 정의 |
| Event | 실제 발생·진행·확정된 사건, 결정, 발표를 표현 |
| Statement | 전망, 주장, 평가, 계획, 가능성 등을 표현 |
| EventMention | 최종 KG Node가 아니라 Event Matching 과정의 중간 데이터 |
| Evidence | EvidenceSpan Node 대신 evidenceArticleId, evidenceChunkId 등으로 provenance 추적 |
| Event → Entity | ACTOR, TARGET, PLACE로 역할 분리 |
| Topic | 정치·경제·사회 등 서비스의 고정 대분류 |
| Concept | 기준금리·지진·인플레이션 등 사건 이해를 위한 세부 지식 단위 |
| Event → Event | 직접 저장 관계를 CAUSES, RESPONDS_TO로 제한 |
| 시간 순서 | PRECEDES를 저장하지 않고 Event.occurredAt으로 계산 |
| Event ↔ Story | N:M 관계 |
| Story ↔ Topic | N:M 관계 |
| User | 공용 News KG 밖의 interaction log와 개인화 데이터로 관리 |

Statement에는 ASSERTED_BY와 ABOUT 관계를 둔다. 예를 들어 어떤 전문가가 “정책 X가 물가 상승의 원인”이라고 주장해도 이를 바로 다음과 같은 세계 사실로 저장하지 않는다.

~~~text
정책 X ─CAUSES→ 물가 상승
~~~

대신 “해당 발화자가 그러한 주장을 했다”는 사실을 Statement로 저장한다. 이 구조를 사용하면 서로 상반된 주장도 KG의 모순 없이 함께 표현할 수 있고, 이후 관점 비교와 추천 설명에도 사용할 수 있다.

### 2.3 KG Construction Pipeline 구체화

~~~text
Raw Article
→ Entity / Concept / Time 추출
→ Event Candidate + Statement Candidate 추출
→ 기사 내부 Event 병합 및 중요도 판정
→ 기존 Canonical Event 검색 및 Matching
→ Event → Story Matching
→ Event Relation Extraction
→ Ontology Validation / Conflict Check
→ Neo4j KG 반영
~~~

Event는 하나의 keyword가 아니라 actor, action, target, time, place, value 등이 결합된 사건 표현이다. 따라서 별도의 Keyword Extraction 단계를 반드시 거칠 필요는 없으며, ontology에 필요한 Event·Statement·Entity·Time을 기사에서 직접 추출하는 구조가 더 적합하다고 판단했다.

기사 하나에는 여러 Event Candidate가 존재할 수 있으므로 제목 등장 여부, 기사 내 위치, 반복 빈도, 주요 Entity와의 관련성 등을 이용해 Event Salience를 판단할 필요가 있다.

### 2.4 Event / Statement Annotation Guideline

Event와 Statement를 과거·미래 시제나 특정 keyword만으로 구분하지 않는다. KG에 넣으려는 proposition의 factuality와 modality, 특히 문장의 matrix clause가 무엇을 단정하는지를 우선한다.

| Label | 판정 기준 |
|---|---|
| EVENT | 실제 발생·진행 중인 사건, 이미 내려진 결정, 확정된 사안 |
| STATEMENT | 전망, 예상, 가능성, 추정, 주장, 평가, 해석, 우려, 권고, 계획, 예정, 의지 |
| O | 서비스 KG의 Event나 Statement로 저장할 필요가 없는 일반 설명·배경 정보 |

예시는 다음과 같다.

- “한국은행이 기준금리를 동결했다.” → EVENT
- “금리를 올릴 가능성이 있다.” → STATEMENT
- “전문가는 금리 인상이 물가를 잡을 것이라고 주장했다.” → STATEMENT

“밝혔다”, “전했다”, “말했다”와 같은 reporting verb는 실제 발화 행위가 있었다는 뜻이지만, 그 안의 proposition이 사실이라는 뜻은 아니다. 따라서 발화 행위 자체가 아니라 KG에 저장하려는 내용의 factuality와 modality를 판정해야 한다.

초기 Event/Statement Extractor는 다음 label을 사용하는 단일 BIO Token Classification Head로 시작하기로 계획해봤다.

~~~text
O
B-EVENT
I-EVENT
B-STATEMENT
I-STATEMENT
~~~

기준에 대한 다음과 같은 질문을 만들었다.

- 무엇을 Event와 Statement로 인정할 것인가?
- 어떤 표현을 O로 버릴 것인가?
- trigger/span의 범위를 어디까지로 볼 것인가?
- 부정·가정·전망 속 사건을 어떻게 처리할 것인가?
- 서로 다른 의미의 Event와 Statement를 하나의 span으로 묶지 않을 것인가?

### 2.5 모델 책임 분리

현재 필요한 모델 머신을 세 종류로 나눴다.

| 모델 책임 | 입력과 출력 | 후보 모델 |
|---|---|---|
| Information Extractor | Article → Event / Statement / Entity / Time | KLUE-RoBERTa, KoELECTRA |
| Semantic Retriever | 새 Entity/Event → 기존 KG 후보 Top-K | BGE-M3, multilingual-E5, KoSimCSE |
| Pairwise Reasoner | 후보 A + B → 동일 객체 여부 또는 relation | KLUE-RoBERTa + classification head, reranker 계열 |

현재 첫 실험의 범위는 Event/Statement span extractor다. Entity·Time 추출, Canonical Event 검색, pairwise 동일성 판정은 같은 모델의 부수 기능으로 간주하지 않고 별도 책임으로 분리한다.

### 2.6 평가 데이터 정제 및 Gold v0.3

기존 GNews 수집 데이터에 실제 기사 본문 외의 내용이 섞여 있는 문제를 확인했다.

- AI 해설
- Key Points
- Timeline
- Glossary
- 이모지
- 댓글·제보 UI
- 중복 기사 본문

이를 제거해 body-only 데이터셋을 만들고, 기존 annotation offset을 정제된 본문 기준으로 다시 맞췄다. 원본 JSON에 실제 기사 본문 없이 AI 해설만 존재한 기사는 benchmark에서 제외했다.

POC 기사 29개를 직접 검토하며 Event/Statement 기준과 span 경계를 반복해서 수정했다.

| Gold v0.3 | 수량 |
|---|---:|
| 기사 | 29 |
| EVENT annotation | 123 |
| STATEMENT annotation | 118 |
| 전체 annotation | 241 |

모든 annotation에서 text == article[start:end]가 성립하는지 검증했다. 서로 다른 의미의 EVENT와 STATEMENT가 하나의 span으로 묶인 경우에는 각각 분리했다.

### 2.7 Event Matching·Relation·Validation 기준

#### Canonical Event Matching

embedding은 유사 후보를 검색하는 도구이지 최종 동일성 판정 기준이 아니다. 서로 다른 달의 동일한 금리 동결처럼 문맥이 매우 유사한 별도 사건이 존재하기 때문이다.

따라서 다음 구조 정보를 함께 비교한다.

- Event type
- Actor / Target
- Time
- Location
- Value와 회차

시간·장소·수치·회차·핵심 Actor/Target이 명백하게 충돌하면 embedding similarity가 높아도 병합하지 않는 hard conflict 규칙을 둔다.

#### Event Relation

- CAUSES와 RESPONDS_TO는 기사 문맥에 해당 관계를 뒷받침하는 근거가 있을 때만 생성한다.
- 단순 시간 선후, 의미적 유사성, 같은 Story라는 이유만으로 relation을 확정하지 않는다.
- 동일 Event 판단과 서로 다른 Event 사이의 relation 판단을 별도 문제로 다룬다.

#### Ontology Validation / Conflict Check

최종 KG 저장 전에 다음을 검사한다.

- 허용된 Node/Edge type인가?
- relation의 domain/range가 맞는가?
- Event merge에 time·location·value 충돌이 없는가?
- CAUSES·RESPONDS_TO에 근거와 올바른 방향이 있는가?
- Event.occurredAt과 Time 표현이 일치하는가?

잘못된 Event merge나 인과 relation은 Story timeline, 추천 이유, 이후 모델 학습 데이터까지 오염시킬 수 있으므로, 검증 실패 결과는 바로 factual KG에 넣지 않는다.

### 2.8 오늘 배운 점

- KG 설계에서는 Node와 Edge의 수보다 의미 경계가 중요하다.
- Keyword, EventMention, Canonical Event는 서로 다른 단계의 객체다.
- Event와 Statement의 schema 경계가 annotation label과 모델 평가 기준으로 이어져야 한다.
- 동일 Event 판정과 Event 간 relation 판정은 서로 다른 문제다.
- embedding은 후보 검색 도구이지 사실 판정 도구가 아니다.
- 모델 출력은 candidate이며 validation을 통과해야 KG의 사실이 된다.
- 모델 구조를 먼저 정하기보다 일관된 annotation guideline과 오류 기준을 먼저 만들어야 한다.

## 3. LQ-FSE 활용 방식 개선 및 Article Construction Runtime 설계 (2026.08.28)

### 3.1 오늘의 목표

Gold v0.3을 기준으로 LQ-FSE의 기존 출력을 평가하고, 모델이 이미 계산한 정보를 별빛 뉴스의 Article Construction Pipeline에서 어떻게 재사용할지 설계했다.

오늘 작업은 다음 흐름으로 진행됐다.

```text
LQ-FSE 출력 구조와 의미 확인
→ selected 필터의 영향 측정
→ Sentence Projection Wrapper 적용
→ BIO Span Head의 역할 재검토
→ 공통 Context Encoder 활용 방향 결정
→ Runtime Data Carrier Contract 설계
→ Article-local 후반 Pipeline 구체화
```

### 3.2 `selected=true` 필터의 Candidate 누락 확인

LQ-FSE는 모든 문장에 대해 `role`과 `extraction_score`를 계산한다. 그러나 원래 모델이 대표문장 추출을 목적으로 설계됐기 때문에 inference 단계에서 `threshold=0.5`, `top_k=3`을 적용하고, 조건을 통과한 일부 문장만 `selected=true`로 반환하고 있었다.

별빛 뉴스의 목적은 대표문장 몇 개를 선택하는 것이 아니라, 후속 단계에서 검토할 EVENT·STATEMENT 후보를 최대한 놓치지 않는 것이다. 따라서 `selected=true`인 문장만 Candidate로 사용하는 방식과 전체 문장을 사용하는 방식을 비교했다.

| 기준                  | Partial Event F1 | Partial Statement F1 | Partial Macro F1 | Candidate Coverage | Count MAE | Candidate 수 |
| ------------------- | ---------------: | -------------------: | ---------------: | -----------------: | --------: | ----------: |
| `selected=true`만 사용 |            0.290 |                0.258 |            0.274 |              0.266 |     6.207 |          77 |
| 전체 문장 사용            |            0.601 |                0.446 |            0.523 |              0.896 |     3.586 |         408 |

전체 문장을 사용했을 때 Candidate Coverage가 `0.266 → 0.896`으로 증가했고, Partial Macro F1도 `0.274 → 0.523`으로 개선됐다.

이에 따라 다음과 같이 결정했다.

* `selected`를 EVENT·STATEMENT Candidate 생성 조건으로 사용하지 않는다.
* `extraction_score`는 EVENT·STATEMENT 분류 confidence로 해석하지 않는다.
* `extraction_score`는 별도의 Extraction Head가 계산한 대표문장·중요도 점수로 본다.
* 낮은 `extraction_score`를 Candidate DROP 조건으로 사용하지 않는다.
* 향후 `extraction_score`는 Event Salience를 판단하는 feature로 활용할 수 있다.

### 3.3 LQ-FSE의 구조와 출력 의미 확인

LQ-FSE의 처리 구조를 다음과 같이 정리했다.

```text
Article
→ Sentence Splitter
→ Tokenizer
→ KLUE-RoBERTa
   ├─ token_hidden
   └─ sentence_hidden
         ↓
   Inter-sentence Transformer
         ↓
   document_context
         ├─ Role Head
         └─ Extraction Head
```

각 출력의 의미는 다음과 같다.

| 출력                 | 의미                                                      |
| ------------------ | ------------------------------------------------------- |
| `token_hidden`     | 각 문장 내부 문맥을 반영한 token representation                    |
| `sentence_hidden`  | KLUE-RoBERTa가 생성한 문장 representation                     |
| `document_context` | 다른 문장과의 관계까지 반영한 document-level sentence representation |
| Role Head          | `event / outlook / financial / risk` 역할 분류              |
| Extraction Head    | 대표문장으로서의 중요도 점수 산출                                      |

KLUE-RoBERTa가 만든 문장 표현을 다시 Inter-sentence Transformer에 입력하므로, 최종 `document_context`에는 해당 문장뿐 아니라 기사 안의 다른 문장 정보도 반영된다.

**해석:** LQ-FSE가 금융 외의 정치·사회 뉴스에서도 비교적 유효하게 작동하는 것은 `event/outlook` 구분이 특정 금융 vocabulary만이 아니라 사건 보고·전망과 같은 담화적 역할을 일부 학습했기 때문일 가능성이 있다. 다만 이는 현재 실험 결과에 대한 해석이며, 추가 데이터로 검증할 필요가 있다.

### 3.4 Sentence Projection Wrapper 구현 및 평가

LQ-FSE의 native role을 별빛 뉴스 ontology의 다음 label로 변환하는 Sentence-level Projection Wrapper를 구현했다.

```text
EVENT / STATEMENT / DROP
```

단순히 다음과 같이 고정 매핑하지는 않았다.

```text
event → EVENT
outlook → STATEMENT
```

Gold v0.3에서 정한 것처럼 문장의 `matrix predicate`가 무엇을 단정하는지와 factuality·modality를 우선해 판정했다.

```text
매출이 증가했다.
→ EVENT

매출이 증가할 전망이다.
→ STATEMENT
```

`financial`, `risk`는 EVENT·STATEMENT와 직접 대응하는 label이 아니므로, native role만으로 결정하지 않고 matrix predicate와 modality를 함께 확인한다.

Wrapper 적용 결과는 다음과 같다.

| 기준                  | Partial Event F1 | Partial Statement F1 | Partial Macro F1 | Candidate Coverage | Count MAE |
| ------------------- | ---------------: | -------------------: | ---------------: | -----------------: | --------: |
| `selected=true`만 사용 |            0.290 |                0.258 |            0.274 |              0.266 |     6.207 |
| 전체 문장 사용            |            0.601 |                0.446 |            0.523 |              0.896 |     3.586 |
| 전체 문장 + Wrapper     |        **0.645** |            **0.509** |        **0.577** |          **0.896** | **3.103** |

모델 weight를 변경하지 않고도 `selected` 제한 제거와 ontology projection만으로 Partial Macro F1을 `0.274 → 0.577`까지 개선했다.

이 결과를 통해 현재 단계에서는 새로운 모델을 바로 추가하기보다, 기존 출력의 의미를 정확히 해석하고 서비스 ontology에 맞게 변환하는 작업이 먼저 필요하다고 판단했다.

### 3.5 BIO Span Head의 역할 재검토

초기에는 LQ-FSE 위에 다음 label을 사용하는 BIO Span Head를 바로 추가하려 했다.

```text
O
B-EVENT
I-EVENT
B-STATEMENT
I-STATEMENT
```

그러나 sentence-level projection만으로도 유효한 성능이 확인됐기 때문에, BIO Head를 구현하기 전에 전체 Construction Pipeline에서 span이 담당해야 할 역할을 먼저 정의하기로 했다.

현재 구상한 구조는 다음과 같다.

```text
Sentence Projection
→ 문장 전체를 EVENT / STATEMENT / DROP으로 판정

Logical Span Proposal
→ 한 문장 내부의 복수 의미 단위 후보 생성

Span Projection
→ 각 child span을 EVENT / STATEMENT / DROP으로 재판정
```

Parent sentence의 label을 child span에 그대로 강제하지 않는다.

```text
정부는 금리를 동결했고,
전문가들은 연말 인상 가능성을 전망했다.

Parent Sentence → STATEMENT일 수 있음

Child A: 정부는 금리를 동결했고
→ EVENT

Child B: 전문가들은 연말 인상 가능성을 전망했다
→ STATEMENT
```

따라서 BIO Head는 Sentence Projection을 대체하는 모델이 아니라, Logical Span Proposal과 Span Projection을 더 정밀하게 만드는 구현 후보로 남겨두었다.

### 3.6 LQ-FSE를 공통 Context Encoder로 활용

Entity, Event, Statement, Time, Relation 단계마다 tokenizer와 RoBERTa를 다시 실행하면 동일한 기사에 대해 이미 계산한 contextual representation을 반복해서 생성하게 된다.

이에 따라 LQ-FSE를 단순한 sentence classifier가 아니라, 기사 한 건에 대한 공통 Context Encoder로 활용하기로 했다.

재사용할 주요 중간 출력은 다음과 같다.

| 출력                 | 주요 활용                                                        |
| ------------------ | ------------------------------------------------------------ |
| `token_hidden`     | Entity Mention, Event Trigger, Time Expression, Logical Span |
| `sentence_hidden`  | 문장 단위 특징과 pooling이 필요한 downstream task                       |
| `document_context` | 기사 전체 문맥을 고려한 문장 판정, resolution, relation extraction         |

`token_hidden` 자체는 각 문장 내부 문맥을 반영한다. 기사 전체 문맥이 필요한 경우에는 해당 token이 속한 문장의 `document_context`를 함께 조회한다.

향후 다음 단계들이 동일한 Article Encoding을 공유하도록 설계한다.

* Entity Mention Extraction
* Event Trigger 및 Candidate Construction
* Statement Candidate Construction
* Time Expression Extraction
* Logical Span Proposal
* Article-local Entity Resolution
* Article-local Event Resolution
* 기사 내부 Event·Statement Relation Extraction

### 3.7 Runtime Data Carrier Contract와 `SpanRef`

한 번 계산한 Article Encoding을 downstream 단계에서 공유하기 위해 runtime carrier 구조를 정의했다.

```text
ExtractionRunContext
├─ ArticleInput
├─ ArticleEncoding
│  └─ SentenceEncoding[]
└─ SentenceProjectionSet

Downstream Candidate
└─ SpanRef
   ├─ ArticleInput.content 참조
   ├─ SentenceEncoding.token_hidden 참조
   └─ SentenceEncoding.document_context 참조
```

각 객체의 역할은 다음과 같다.

| 객체                      | 역할                                                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `ArticleInput`          | 모델이 읽은 입력. `article_id`, `title`, `content`, `published_at` 등을 보유                                                    |
| `ArticleEncoding`       | 한 extraction run에서 생성된 기사 전체 contextual artifact와 수명주기를 소유                                                           |
| `SentenceEncoding`      | 문장별 text·offset·token 정보와 `token_hidden`, `sentence_hidden`, `document_context`, native role, `extraction_score`를 보유 |
| `SentenceProjectionSet` | 별빛 뉴스 ontology 기준의 `EVENT / STATEMENT / DROP` 판정과 reason code를 보유                                                    |
| `SpanRef`               | 원문의 특정 범위와 관련 contextual representation을 다시 찾기 위한 runtime handle                                                     |
| `ExtractionRunContext`  | 위 정보를 하나의 article inference 작업 공간으로 묶는 최상위 runtime carrier                                                           |

다음 원칙을 적용한다.

* `SentenceEncoding`과 `SentenceProjection`은 합치지 않는다.
* ProjectionPolicy가 변경돼도 Article Encoding을 다시 계산하지 않아야 한다.
* hidden Tensor는 runtime에서만 유지하고 API나 DB에 저장하지 않는다.
* EntityMention·EventCandidate 등에 vector를 복제하지 않는다.
* 원문 문자열의 runtime Source of Truth는 `ArticleInput.content` 하나로 둔다.
* 최종 저장 단계에서만 필요한 `text`, `startOffset`, `endOffset` 등을 materialize한다.

`SpanRef`는 단순히 text 복제를 줄이기 위한 객체가 아니다.

| `SpanRef` 정보              | 연결 대상                                                     |
| ------------------------- | --------------------------------------------------------- |
| `char_start / char_end`   | `ArticleInput.content`에서 원문 복원                            |
| `token_start / token_end` | `SentenceEncoding.token_hidden`에서 span vector 조회          |
| `sentence_index`          | parent sentence의 `sentence_hidden`과 `document_context` 조회 |

따라서 `SpanRef`를 다음과 같이 정의했다.

> 원문 위치와 token context, article-level sentence context를 다시 연결하는 runtime handle

EntityMention, EventCandidate, StatementCandidate, TimeExpression 등은 필요한 범위를 `SpanRef`로 가리키고, 영속화가 필요한 최종 결과를 만들 때만 원문과 offset을 materialize한다.

### 3.8 Article-local 후반 Pipeline 구체화

EventCandidate 생성 이후의 처리 흐름을 다음과 같이 정리했다.

```text
EventCandidate[]
→ Event Argument Linking
→ Article-local Event Resolution
   ├─ MERGE
   └─ KEEP
→ ResolvedLocalEvent[]
→ Relation Pair Generation
→ Article-local Relation Extraction
→ RelationCandidate[]
→ Ontology Validation / Conflict Check
→ ArticleConstructionResult
```

같은 기사에서 동일 사건이 반복 서술된 경우에는 Relation을 생성하기 전에 먼저 하나의 `ResolvedLocalEvent`로 통합한다.

그렇지 않으면 같은 사건 표현이 여러 번 등장했다는 이유로 다음과 같은 중복 relation이 만들어질 수 있다.

```text
E1 ─CAUSES→ E3
E2 ─CAUSES→ E3
```

기사 내부 Relation Extraction의 초기 범위는 다음과 같이 제한한다.

| Source    | Relation      | Target |
| --------- | ------------- | ------ |
| EVENT     | `CAUSES`      | EVENT  |
| EVENT     | `RESPONDS_TO` | EVENT  |
| STATEMENT | `ABOUT`       | EVENT  |
| 그 외       | `NONE`        | -      |

Cross-document Event relation은 현재 Article Construction의 범위에 포함하지 않는다. 우선 한 기사 안에서 Candidate를 구성하고 중복을 해소한 뒤, 근거가 있는 최소 relation만 생성하는 데 집중한다.

### 3.9 오늘의 핵심 결과

오늘의 주요 결과는 다음 두 가지다.

```text
1. LQ-FSE를 단순한 문장 분류 모델이 아니라,
   기사 한 건에서 계산한 token·sentence·document context를
   Construction Pipeline 전체가 공유하는 Context Encoder로 활용한다.

2. 새로운 모델이나 Head를 추가하기 전에,
   현재 모델이 이미 계산하고 있지만 버리고 있던 정보와
   downstream 단계가 실제로 필요로 하는 데이터를
   Contract로 먼저 정의한다.
```

실험 측면에서는 모델 weight를 변경하지 않고 다음 두 변경만으로 Partial Macro F1을 `0.274 → 0.577`까지 개선했다.

* `selected=true` 제한 제거
* Sentence Projection Wrapper 적용

설계 측면에서는 Encoding과 Ontology Projection을 분리하고, `SpanRef`를 통해 원문·token context·document context를 다시 연결하는 runtime 구조를 확정했다.

### 3.10 오늘 배운 점

* 모델이 출력한 score의 의미를 확인하지 않고 다른 task의 confidence로 사용하면 안 된다.
* 대표문장 선택과 EVENT·STATEMENT Candidate 추출은 서로 다른 목적의 문제다.
* 기존 모델의 성능은 weight뿐 아니라 출력 선택과 ontology projection 방식에도 크게 영향을 받는다.
* Sentence Projection과 Span Projection은 서로 다른 해상도의 판정 단계다.
* Parent sentence의 label을 child span에 그대로 전파해서는 안 된다.
* Encoding 결과와 서비스 ontology의 해석 결과를 분리해야 정책 변경에 유연하게 대응할 수 있다.
* hidden vector를 객체마다 복제하기보다 위치 참조를 통해 공유하는 편이 runtime 구조와 provenance 관리에 적합하다.
* 모델 구현 전에 단계별 입력·출력·책임을 Contract로 정의하면 불필요한 재계산과 객체 중복을 줄일 수 있다.

### 3.11 다음 작업

* Article Encoding Contract와 Sentence Projection Contract 작성
* Sentence Projection Wrapper의 confusion case 분석
* Logical Span Proposal과 Span Projection의 입력·출력 기준 정의
* 해당 기준을 바탕으로 BIO Span Head의 필요성과 label 구조 재검토
* Event Argument Linking과 Article-local Event Resolution Contract 구체화
* Relation Extraction 결과에 대한 Ontology Validation 규칙 정의

### 3.12 한 줄 회고

> 오늘은 새로운 모델을 추가하기보다, 기존 LQ-FSE가 이미 계산하고 있던 정보를 제대로 꺼내 쓰는 것만으로 성능을 개선하고 이후 파이프라인 전체가 공유할 수 있는 실행 구조로 확장했다.

## 4. 기존 모델 활용에서 직접 Head 설계로 전환 (2026.08.29)

### 4.1 오늘의 전환점

8월 28일까지는 가능하면 LQ-FSE의 기존 weight를 그대로 두고, `selected` 제한을 풀거나 Projection/Rule/Decoder를 덧붙여 별빛 뉴스에 맞게 확장하는 쪽으로 끝내고 싶었다. 이미 학습된 모델을 잘 해석해서 쓰는 편이 효율적이고, 굳이 새로운 신경망을 만들지 않아도 서비스에 필요한 Article-local KG를 만들 수 있다면 그게 더 좋은 선택이라고 생각했다.

그런데 후반 Construction 책임을 하나씩 적어보니 기존 LQ-FSE가 애초에 학습하지 않은 출력이 너무 많았다.

```text
기존 LQ-FSE가 잘하는 것
- 문장 중요도
- 문장 역할
- 기사 내부 sentence context

별빛 뉴스가 추가로 필요한 것
- Entity / Time exact span
- Event / Statement exact semantic span
- Trigger
- Statement Type
- Assertor
- Event Argument
- Entity / Event Coreference
- Event Relation
```

이 시점에서 "기존 모델을 최대한 안 건드리는 것" 자체가 목적이 되어서는 안 된다고 판단했다. Backbone은 최대한 재사용하되, **우리 ontology가 정의한 문제를 직접 supervision하는 Head는 결국 우리가 설계하고 학습해야 한다**는 쪽으로 방향을 바꿨다.

즉 이 날은 Backbone/Head라는 용어를 처음 알게 된 날이라기보다, 그 구조를 이해한 뒤에도 미뤄두고 있던 **직접 Head 설계와 학습을 실제로 시작하기로 결정한 날**에 가깝다.

### 4.2 논문을 다시 보며 Backbone과 Head의 경계를 정리

BERT의 원 논문은 pretrained bidirectional encoder 위에 비교적 작은 task-specific output layer를 붙여 여러 downstream task로 fine-tuning할 수 있다는 구조를 보여준다. 이 관점은 "Backbone을 직접 처음부터 만들지 않아도, 그 위에 우리 task를 위한 Head를 설계하는 것은 충분히 독립적인 모델링 작업"이라는 점을 이해하는 데 도움이 됐다.

- Devlin et al., [BERT: Pre-training of Deep Bidirectional Transformers for Language Understanding](https://aclanthology.org/N19-1423/), 2019

또 LQ-FSE의 구조를 이해하면서는 BERTSUM의 extractive summarization 구조를 함께 봤다. BERTSUM은 BERT 기반 document encoder 위에 inter-sentence Transformer를 쌓아 sentence representation들 사이의 관계를 다시 모델링한다. LQ-FSE가 KLUE-RoBERTa의 문장 표현 위에 Inter-sentence Transformer를 두고 문장 중요도/역할을 판단하는 이유를 이해하는 데 직접적인 비교점이 됐다.

- Liu & Lapata, [Text Summarization with Pretrained Encoders](https://aclanthology.org/D19-1387/), 2019

내가 가져가고 싶었던 것은 "요약 모델" 자체가 아니라 다음 구조적 아이디어였다.

```text
Pretrained Token Encoder
        ↓
Sentence Representation
        ↓
Document-level Sentence Interaction
        ↓
Task-specific Head
```

### 4.3 기존 Head를 교체 가능한 부품으로 보기 시작

LQ-FSE의 Role Head와 Extraction Head를 더 이상 모델 전체와 한 덩어리로 보지 않고, 공통 representation 위의 task-specific module로 분리해서 보기 시작했다.

```text
Backbone
→ contextual representation 생성

Shared / Document Context Module
→ 기사 내부 문맥을 추가로 구성

Task Head
→ 특정 Gold supervision을 prediction으로 변환
```

이 구조로 보면 다음이 가능하다.

- Backbone을 frozen한 채 Head만 학습
- Head별 parameter를 독립 저장
- 같은 frozen representation에서 Head architecture만 교체하며 실험
- "Backbone 표현이 부족한가"와 "Head 학습이 잘못됐는가"를 분리해서 진단
- task별로 서로 다른 layer나 representation을 사용할 수 있음

그리고 PyTorch에서 새로운 신경망을 만든다는 것도 결국 `nn.Module`, `Linear`, `TransformerEncoder`, pooling, loss 등을 조합해 **입력 표현과 supervision 사이의 계산 경로를 내가 정의하는 일**이라는 점을 받아들이기 시작했다.

### 4.4 가장 먼저 분리해야 했던 책임: 중요 문장과 의미 판정

기존 LQ-FSE의 Extraction Head는 대표문장 추출을 위한 중요도이고, 별빛 뉴스의 EVENT/STATEMENT는 ontology의 의미 판정이다.

```text
대표문장인가?
≠ EVENT proposition이 존재하는가?
≠ STATEMENT proposition이 존재하는가?
```

8월 28일의 `selected=true` 실험에서 이미 selection을 제거했을 때 candidate coverage가 크게 올라간 것을 확인했기 때문에, 이 책임 충돌을 neural structure에서도 분리하기로 했다.

Sentence Projection은 이후 다음처럼 두 개의 독립 bit로 발전시키기로 했다.

```text
EVENT_PRESENT
STATEMENT_PRESENT

00 → DROP
10 → EVENT
01 → STATEMENT
11 → MIX
```

처음부터 EVENT/STATEMENT를 mutually exclusive 3-class로 가정하지 않은 이유는, 한 문장 안에 실제 사건과 전망·주장이 동시에 존재할 수 있기 때문이다.

### 4.5 이 날 시작한 구조 설계의 큰 방향

이후 모델을 단순히 "Head 여러 개"가 아니라 세 종류의 계산 family로 나누어 생각하기 시작했다.

```text
Token / Span Family
- Entity
- Time
- Semantic Span
- Trigger

Attribute Family
- Statement Type

Pair Family
- Assertor
- Argument
- Relation
- Entity Coreference
- Event Coreference
```

모든 task가 서로 다른 neural encoder를 가져야 하는 것은 아니고, **semantic responsibility와 physical neural module을 구분**해야 한다고 보았다. 예를 들어 여러 pair task는 source/target 표현을 만드는 공통 Pair Encoder를 공유하고 마지막 classifier만 다르게 둘 수 있다.

이때부터 프로젝트의 성격도 조금 다르게 느껴졌다. 처음에는 공개된 모델을 우리 서비스에 맞게 잘 "활용"하는 프로젝트라고 생각했는데, 필요한 supervision을 직접 정의하고 그 위에 Head와 decoder를 설계하기 시작하니 사실상 **pretrained backbone 위에서 Article-local KG construction model을 직접 만드는 작업**으로 커지고 있었다.

### 4.6 오늘 배운 점

- Backbone/Head를 이해하는 것과 실제로 Head를 설계하기로 결정하는 것은 다른 단계였다.
- 기존 모델 weight를 지키는 것보다 우리 ontology의 책임을 정확히 supervision하는 것이 더 중요하다.
- pretrained Backbone을 frozen해서 사용하더라도, shared context와 task Head를 새로 설계하면 충분히 독립적인 모델 구조가 된다.
- 하나의 score를 여러 의미로 재사용하기보다 목적이 다른 task는 Head와 metric도 분리해야 한다.
- 모델 구조를 직접 만든다는 것은 거대한 Transformer를 처음부터 pretrain한다는 뜻이 아니라, **어떤 representation을 어떤 supervision으로 변환할지 계산 구조를 설계하는 것**이기도 하다.

### 4.7 한 줄 회고

> 원래는 가능하면 기존 모델을 안 건드리고 끝내고 싶었는데, 우리 ontology가 요구하는 출력을 끝까지 적어보니 결국 피할 수 없었다. 이 날부터는 "모델을 어떻게 활용할까"보다 "우리 문제를 풀 모델을 어떻게 설계할까"를 생각하기 시작했다.

## 5. 재현 가능한 실험 기반과 첫 Custom Architecture 설계 (2026.08.30)

### 5.1 오늘의 목표

Head를 직접 만들기로 했지만 바로 10여 개의 Head를 붙이는 것은 위험하다고 판단했다. 먼저 **공통 표현부와 첫 learned vertical slice를 재현 가능하게 만드는 것**부터 시작했다.

동시에 Pilot 29개만으로는 다중 Head 학습을 판단하기 어려웠기 때문에 1,000기사 Gold 확장까지 이어지는 작업 순서를 재구성했다.

### 5.2 재현성의 단위를 checkpoint 하나보다 크게 정의

weight 파일 하나가 존재한다고 같은 실험이 재현되는 것은 아니다.

```text
weights
+ backbone revision
+ tokenizer
+ preprocessing / sentence split
+ layer selection
+ model config
+ projection / decoder policy
+ candidate universe
+ training config / seed
```

가 함께 고정되어야 같은 실험이라고 볼 수 있다.

그래서 legacy checkpoint를 분리하고, cache와 online inference가 같은 representation을 만드는지 parity를 확인한 뒤 새로운 Head를 붙이는 순서로 바꿨다.

### 5.3 Frozen Backbone Cache를 먼저 만든 이유

앞으로 Entity, Time, Span, Trigger, Pair task를 반복 실험하려면 매번 KLUE-RoBERTa/LQ-FSE를 처음부터 실행하는 비용이 너무 크다.

따라서:

```text
Article
→ Sentence Split
→ Frozen Backbone
→ token_hidden cache
→ 이후 Head 실험에서 재사용
```

구조를 먼저 만들었다.

이렇게 하면 Head를 바꿀 때 representation producer까지 같이 바뀌는 일을 막을 수 있고, 실험 속도도 크게 줄일 수 있다. 이후 KF-DeBERTa로 Backbone을 바꾼 뒤에도 이 "frozen feature cache + task-local Head probe" 방식은 그대로 유지됐다.

### 5.4 Sentence Context를 직접 설계하기 시작

기존 LQ-FSE의 inter-sentence 구조를 그대로 가져오기보다, frozen token representation 위에서 **새로운 sentence/document context module**을 만들기 시작했다.

당시 설계한 흐름은 다음과 같다.

```text
Frozen token_hidden
        ↓
Learned Sentence Pooling
├ first-token projection
└ source-token attention pooling
        ↓ learned gate
Sentence Representation
        ↓
Sentence Position Features
        ↓
Document Transformer
        ↓
document_context
        ↓
Global Context Fusion
├ sentence fusion
└ token fusion
        ↓
Sentence Presence Head
```

Sentence pooling에서 first token을 버리지 않은 이유는 기존 LQ-FSE가 실제로 그 위치의 representation을 사용해 학습되어 있었기 때문이다. 동시에 first token만 문장 전체 의미라고 가정하지 않기 위해 source token attention pooling을 추가하고 둘의 비율을 learned gate로 정했다.

문장 위치 역시 단순 learned position table 하나보다 다음 정보를 함께 쓰도록 설계했다.

```text
- source absolute sentence index
- 원 기사에서 앞/뒤 상대 위치
- 실제 consumed window 안에서 앞/뒤 상대 위치
```

즉 이 단계부터 단순 classifier를 붙이는 것이 아니라 **우리 runtime contract와 실제 기사 처리 방식까지 반영한 representation 구조**를 만들기 시작했다.

### 5.5 Sentence Presence를 첫 learned vertical slice로 선택

첫 번째 learned task는 Sentence Presence로 잡았다.

```text
[EVENT_PRESENT, STATEMENT_PRESENT]
```

두 독립 logit을 출력하고 각각 BCE로 학습하도록 했다. 이는 MIX를 보존하기 위한 구조적 결정이었다.

중요한 점은 문장 Head만 만드는 것이 목적이 아니었다. 이 vertical slice를 통해 다음 전체 경로를 먼저 검증하고 싶었다.

```text
Frozen cache
→ Gold strict join
→ article-level split
→ custom shared context
→ task Head
→ dev checkpoint selection
→ test evaluation
→ weight / config / provenance 저장
```

이 경로가 안정적으로 동작해야 이후 Entity/Time/Pair Head를 같은 방식으로 늘릴 수 있다고 보았다.

### 5.6 작업 로드맵 재구성

우선순위를 다음처럼 정리했다.

```text
v2 최소 계약 문서
→ Workspace 재구성
→ Legacy checkpoint 분리 + parity
→ Viewer profile parameter화
→ Pilot 29 Gold 누락 복구
→ Frozen Backbone cache
→ online/cache parity
→ Sentence Context + Presence vertical slice
→ Token / Candidate / Pair Head
→ GNews 1,000기사 Gold 확대
→ Integrated checkpoint / runtime
```

이 단계에서 느낀 가장 큰 문제는 "Head가 많다"는 사실 자체가 아니라, **모든 Head가 같은 Gold와 runtime 의미 계약을 바라보게 만드는 일**이었다.

### 5.7 논문과 연결해서 본 구조

BERTSUM에서 sentence representation 위에 inter-sentence Transformer를 쌓는 방식은 LQ-FSE 구조를 이해하는 참고점이 됐지만, 나는 summarization objective를 그대로 가져오지 않았다. 우리 목적은 대표문장 selection이 아니라 기사 전체에서 proposition과 graph material을 최대한 보존하는 것이다.

따라서 논문에서 가져온 것은 "문장 간 interaction을 별도 document layer에서 학습할 수 있다"는 구조적 아이디어이고, supervision은 별빛 뉴스의 Sentence Presence로 바꿨다.

### 5.8 오늘 배운 점

- 새로운 Head를 만드는 것보다 먼저 반복 가능한 experiment vertical slice를 만드는 것이 중요하다.
- Custom architecture와 runtime contract가 따로 놀면 offline F1이 좋아도 실제 서비스 모델로 이어지기 어렵다.
- Frozen Backbone cache는 단순 속도 최적화가 아니라 representation을 고정해 Head 실험을 공정하게 만드는 장치다.
- 문장 representation도 CLS/first-token 하나로 고정하기보다 기존 신호와 learned pooling을 함께 비교할 수 있게 만드는 편이 안전하다.

### 5.9 한 줄 회고

> Head를 만들기로 마음먹고 나니 오히려 먼저 해야 할 일은 "많이 만드는 것"이 아니라, 하나를 만들어도 다음 실험이 흔들리지 않는 구조를 만드는 것이었다.

## 6. Gold v2.0 완성과 Token·Candidate·Pair Head 구조 확장 (2026.08.31)

### 6.1 오늘의 목표

GNews 1,000기사에 대해 Article-local KG Construction에 필요한 supervision을 실제 학습 가능한 형태로 확장하고, Sentence Presence 한 개로 검증한 구조를 여러 Head family로 넓혔다.

이 시점부터 "모델을 반쯤 만드는 것 같다"는 느낌이 더 강해졌다. Backbone은 pretrained model을 쓰지만, 어떤 candidate를 만들고 어떤 representation을 공유하고 어떤 loss로 무엇을 예측하는지는 점점 우리 프로젝트의 설계가 되고 있었다.

### 6.2 Gold v2.0과 supervision 규모

1,000개 기사에 대해 주요 Construction task의 annotation을 확장했다.

| 항목 | 대략적 규모 |
|---|---:|
| Article | 1,000 |
| Entity Mention | 10.6k |
| Event Candidate / Trigger | 8.6k |
| Statement Candidate | 13k 수준 |
| Argument Link | 2.2k 수준 |
| Relation | 1.8k 수준 |

Pilot 29개에서는 잘 보이지 않던 class imbalance, candidate explosion, 희소 relation 문제가 실제 숫자로 드러나기 시작했다.

### 6.3 모델 책임을 8단계로 정리

Head가 늘어나면서 파일 이름이나 classifier 개수보다 **semantic responsibility**를 먼저 고정하기 위해 전체 모델을 다음 8단계 vocabulary로 정리했다.

```text
① 공통 표현부
② 문장 판정부
③ 구간 추출부
④ 속성 판정부
⑤ 방향 관계 판정부
⑥ 동일성 판정부
⑦ 후보 제한부
⑧ 그래프 조립부
```

각 단계의 의미는 다음처럼 잡았다.

- ① 공통 표현부: frozen Backbone과 article/document context
- ② 문장 판정부: EVENT/STATEMENT proposition presence
- ③ 구간 추출부: Entity, Time, Semantic Span, Trigger
- ④ 속성 판정부: Statement Type 등 span/node attribute
- ⑤ 방향 관계 판정부: source→target이 있는 Assertor, Argument, Relation
- ⑥ 동일성 판정부: 순서 없는 Entity/Event Coreference
- ⑦ 후보 제한부: 불가능한 pair 제거, training sampling, runtime pruning
- ⑧ 그래프 조립부: deterministic materialization, validation, provenance

이 구분 덕분에 "Head가 몇 개인가"보다 "어떤 책임이 neural이고 어떤 책임이 deterministic policy인가"를 이야기할 수 있게 됐다.

### 6.4 Token/Span Head와 Pair Head를 다른 family로 설계

단일 BIO Head 하나로 모든 것을 해결하지 않고 task 특성에 따라 representation을 다르게 보기로 했다.

```text
Entity / Time
→ token sequence + BIO

Semantic Span / Trigger
→ start / end boundary

Statement Type
→ span representation → attribute classification

Assertor / Argument / Relation
→ ordered source-target pair

Entity / Event Coreference
→ symmetric pair
```

여러 Pair task가 공통으로 사용할 수 있도록 source와 target representation을 만드는 shared pair encoder를 두는 방향을 잡았다. 반대로 Coreference는 A→B와 B→A가 의미상 같은 identity problem이므로 ordered relation과 같은 encoder/decoder를 그대로 쓰지 않도록 했다.

### 6.5 "같은 의미 책임"과 "같은 Neural Head"는 다르다

이때 중요한 설계 원칙을 하나 확정했다.

```text
Semantic responsibility
≠ Physical neural Head / module
```

예를 들어 Assertor와 Argument는 다른 supervision이지만 공통 `DirectedPairEncoder`를 공유할 수 있다. 반대로 Relation 안에 endpoint가 전혀 다른 label을 한 softmax에 넣는 것은 나중에 문제가 될 수 있다.

이 원칙은 9월 3~4일 Relation ontology migration에서 실제로 중요해졌다.

### 6.6 ArticleConstructionResult를 "미니 지도"로 보기

최종 출력은 하나의 node prediction이 아니라 기사 한 건에서 나온 작은 graph artifact라고 정리했다.

```text
ArticleConstructionResult
├ Article metadata / lineage
├ EntityMention[]
├ LocalEntity[]
├ TimeExpression[]
├ Event[]
├ Statement[]
├ Argument[]
├ Coreference / Relation[]
└ Validation / Trace
```

이 Article-local graph를 나중에 전체 Neo4j News KG와 resolution/merge하는 것이 목표다.

이 관점을 잡고 나니 모델 평가도 단일 F1만으로 끝나서는 안 되고, 나중에는 decoded graph와 cascade까지 봐야 한다는 점이 명확해졌다.

### 6.7 오늘 배운 점

- Head를 늘리는 것보다 task의 endpoint와 candidate universe를 명확히 하는 것이 먼저다.
- 같은 shared representation을 쓸 수 있는 task와 독립 구조가 필요한 task를 구분해야 한다.
- Article-local KG 모델은 classifier 묶음이라기보다 여러 neural scorer와 deterministic graph assembly가 결합된 pipeline이다.
- Gold가 커지면서 rare class와 negative pair 수가 architecture만큼 중요한 설계 변수가 됐다.

### 6.8 한 줄 회고

> 처음에는 Head 몇 개만 붙이면 될 줄 알았는데, 1,000기사 Gold를 만들고 나니 문제는 Head 개수가 아니라 서로 다른 task를 하나의 일관된 모델 계약으로 묶는 일이었다.
