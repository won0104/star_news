## 1. NER 모델 (KPF-bert-ner)

- 한국언론진흥재단(빅카인즈)이 뉴스 코퍼스로 학습시킨 개체명 인식 모델
- **TTA 표준 개체명 태그셋(TTAK.KO-10.0852)** 기반, 15개 대분류 × 150개 세분류
- 대분류: PS(인물), LC(지역), OG(기관), AF(인공물), DT(날짜), TI(시간), CV(문명), AM(동물), PT(식물), QT(수량), FD(학문분야), TR(이론), **EV(사건)**, MT(물질), TM(용어)
- 뉴스 특화 카테고리인 "사건(EV)"이 기본으로 포함돼 있어서, 별도 라벨링 데이터 없이도 개체+사건 태깅이 어느 정도 가능
- **실무 이슈**: huggingface config.json에 라벨이 `LABEL_0~299`로 익명화돼 있어 실제 카테고리명 매핑이 별도로 필요함
- 대안: `klue/roberta` 계열은 라벨이 투명하지만 카테고리가 기본적(PER/LOC/ORG 등)이라 EV 같은 세분류가 없음

## 2. 키워드/개념 추출 알고리즘 계보

### TextRank의 한계
- PageRank를 텍스트에 응용한 그래프 기반 알고리즘 (2004년)
- 논문 벤치마크(RaKUn, 2019) 기준 15개 데이터셋 중 **단 한 번도 1위를 못 함** — 그래프 기반 계열 중 가장 낮은 성능
- 개선판들: SingleRank(빈도 가중치 추가), **PositionRank(위치+빈도, 뉴스 도메인에 특히 적합)**, TopicRank/MultipartiteRank

### 통계 기반 — YAKE
- 그래프 없이 순수 통계(대소문자, 위치, 빈도)만으로 계산, 언어 독립적, 매우 빠름

### 임베딕 기반 — KeyBERT
- SBERT로 문서 전체와 후보 단어의 코사인 유사도를 계산해 키워드 선정
- **KeyBERT 자체는 알고리즘/로직일 뿐, 실제 성능은 내부 SBERT 임베딩 모델 품질에 좌우됨**
- 한국어는 `jhgan/ko-sroberta-multitask` 추천 (KorSTS 기준 84~85점)
  - RoBERTa 기반, max_seq_length 128 토큰 제약 → 긴 기사 전문은 chunk 단위로 넣어야 함
  - Mean Pooling 방식으로 문장 벡터 생성

### 실무 조합
- PositionRank(저비용) + KeyBERT(의미 기반) 점수를 정규화 후 가중합해서 종합 스코어링

## 3. SBERT(Sentence-BERT) 원리

- 일반 BERT는 문장 유사도 비교에 최적화되어 있지 않음 (문장쌍을 매번 통째로 재계산해야 해서 느림)
- SBERT는 **샴 네트워크 구조**로 문장쌍 데이터(NLI, STS)를 학습시켜, 문장을 독립적으로 벡터화해도 의미 유사도가 코사인 유사도로 잘 반영되도록 만든 모델
- 한 번 벡터화해두면 이후 비교는 벡터 연산만 하면 되므로 빠름

## 4. Event Extraction — 오늘 가장 깊게 판 부분

### Entity/Concept 추출과 Event 추출은 완전히 다른 작업
- Entity 추출(NER) → **Entity 노드**
- Concept 추출(KeyBERT) → **Concept 노드**
- **Event 추출(Trigger + Argument)** → **Event 노드** (전혀 다른 작업, 오늘 계속 헷갈렸던 지점)

### 시행착오 — 방법론 탐색 과정
1. **임베딩/클러스터링 계열 (AWS 뉴스클러스터링 레포, LLM 클러스터링 논문)**
   - 실제로는 "여러 기사를 사건 단위로 묶는 것"(Event Matching/Story 클러스터링)이지, 문장 내부의 사건 구조를 뽑는 게 아님
   - DBSCAN 등은 "비슷하다/아니다"만 판단, 관계 타입·방향성·인과관계는 표현 못함
2. **SpERT (Span-based Joint Entity and Relation Extraction, 2019)**
   - Entity + Relation(주어-관계-목적어 트리플)을 조인트로 추출
   - 하지만 트리거(무슨 행위)나 시점, 확정성(ACTUAL/PLANNED 등) 정보가 없어서 Event 노드를 채우기엔 부족
   - "협력"이라는 관계 라벨 하나로는 "발표했다"는 구체적 사건인지 단순 배경 서술인지 구분 불가
3. **LLM 기반 생성 방식 (최종 채택 방향)**
   - Trigger + Argument를 텍스트 생성 태스크로 재정의하는 게 최신 학계 트렌드 (2025 서베이 논문 확인)
   - 실제 시도: `sogm1/qwen3-1.7b-news-event-merged` (Qwen3-1.7B LoRA 파인튜닝 모델)
     - 뉴스 텍스트 → 카테고리 분류 + 핵심 이벤트 리스트를 dict 형태로 생성
     - 사건을 자연어 문장으로 통째로 뽑아주는 게 강점
     - 다만 ACTOR/TARGET/PLACE/occurredAt/status 등 세부 필드는 없어서 후처리 필요

### 방법론 비교 정리
| 방법 | 정확도 | 비용 | 비고 |
|---|---|---|---|
| 규칙/트리거 사전 | 낮음 | 매우 낮음 | 1차 스크리닝용 |
| 의존구문분석 | 중간 | 낮음 | 한국어는 조사 기반 역할 추출에 유리 |
| 지도학습 시퀀스 라벨링 | 높음 | 데이터 필요 | 한국어 EE 데이터 희소 (AIHub에 "한국어 다중 이벤트 추출 데이터" 존재 확인, 검토 필요) |
| **LLM 기반 생성** | 높음 | 높음(비용) | 현재 채택 방향, 후보 좁혀서 넘기면 비용 절감 가능 |

## 5. 온톨로지 설계 변경사항 (팀 문서 v2)

- Issue + Story → **Story로 통합**
- **EventMention** 개념 도입: 기사 내 반복 언급되는 사건 표현의 중간 데이터, 최종 그래프엔 저장 안 함 (Canonical Event로 병합 후 저장)
- **Evidence는 별도 노드 대신 엣지 속성(evidenceArticleId 등)으로 처리** → 불필요한 노드 증식 방지
- **Statement 노드 신설**: 전망/주장/평가를 실제 발생한 Event와 명확히 분리
- INVOLVES{role} → **ACTOR/TARGET/PLACE로 세분화** (쿼리 효율 + 명확성)
- Topic은 **고정 6개** (정치/경제/사회/생활문화/IT과학/스포츠엔터), AI가 새 Topic 생성 못하도록 제한
- CAUSES/RESPONDS_TO 관계는 **N:1에서 N:M으로 수정** (하나의 원인이 여러 결과를 낳는 실제 뉴스 패턴 반영)

## 6. 기타

- **Property Graph(Neo4j) vs RDF**: Property Graph는 엣지에도 자유롭게 속성(confidence, evidence 등)을 붙일 수 있어 지금 온톨로지 설계에 적합. RDF는 엣지에 속성을 붙이려면 reification이라는 우회가 필요해 복잡함
- **엣지 분류가 필요한 이유**: 방향성/인과관계 표현, hop 기반 추천 시 관계별 감쇠율 차등 적용, 계층 관계(정보 공백 계산의 핵심) 구조화, Domain-Range 제약을 통한 데이터 품질 검증 등
- **페이지랭크 계열은 "관계가 무엇인지 판단"에는 못 쓰고, "이미 만들어진 그래프에서 무엇이 중요한지 필터링"에만 활용 가능** (예: Concept 허브 필터링, 오늘의 트렌드 산정)
