# TIL — 뉴스 지식 그래프 설계 및 정보 추출

## 2026-08-26 — 온톨로지 설계

뉴스를 기사 단위가 아니라 사건과 맥락 중심으로 연결하기 위해 온톨로지를 설계했다.

핵심 Node는 다음과 같이 정리했다.

```text
Article
Event
Story
Topic
Entity
Concept
Time
Statement
```

주요 구조는 다음과 같다.

```text
Article → Event → Story → Topic

Article / Event → Entity
Event → Concept
Event → Time
Article → Statement
Statement → Entity / Event
```

설계하면서 특히 다음 기준을 구분했다.

- `Event`: 실제로 발생한 사건·결정·발표
- `Statement`: 전망·주장·평가
- `Entity`: 사람, 기관, 장소 등 식별 가능한 대상
- `Concept`: 기준금리, 부동산 PF처럼 기사를 이해하기 위한 개념
- `Story`: 여러 Event가 이어지는 장기 뉴스 흐름
- `Topic`: 정치, 경제, 사회, 생활/문화, IT/과학, 스포츠/엔터의 고정 대분류

Event 간 관계는 의미가 명확한 경우만 `CAUSES`, `RESPONDS_TO`로 연결하고, 시간 순서는 별도 관계를 저장하지 않고 `occurredAt`을 기준으로 계산하기로 했다.

## 2026-08-27 — 정보 추출 모델 Pilot

온톨로지의 `Entity`, `Event`, `Statement`, `Concept`, `Time`을 실제 기사에서 어떻게 추출할지 공개 모델 중심으로 Raw Pilot을 진행했다.

### Entity

`KPF-BERT-NER`를 테스트했다.

- 뉴스 특화 NER 모델
- 조직 탐지는 비교적 안정적
- 인명 분절, 바이라인 오탐, offset 부재 등의 문제 존재
- Adapter를 적용한 뒤 재평가할 가치가 있어 **조건부 채택**

```text
KPF-BERT-NER
→ EntityAdapter
→ PERSON / ORGANIZATION / LOCATION / PRODUCT
```

### Event / Statement

기존 AI Hub 다중 이벤트 모델과 문장 유형 분류기는 우리 정의와 잘 맞지 않았다.

추가로 `LQ-FSE-base`를 테스트한 결과:

- Event 문장 Recall 약 `0.82`
- Outlook 문장 Recall 약 `0.76`

최종 Event/Statement를 직접 추출하기에는 부족하지만, 관련 문장을 먼저 찾는 **Candidate Selector**로 활용 가능성이 있었다.

```text
LQ-FSE
→ Event / Outlook 후보 문장 탐지
→ 이후 상세 추출
```

추후 Gold가 충분히 확보되면 `EVENT / FORECAST / CLAIM / EVALUATION` multi-label 방식으로 fine-tuning하는 방향도 검토한다.

### Concept

`KPF-KeyBERT`를 테스트했지만 KG의 Concept을 직접 추출하기에는 성능이 부족했다.

- 중요 키워드는 찾지만 Entity·일반 명사가 많이 섞임
- 복합 개념을 유지하지 못하는 문제가 있음

따라서 현재 방식은 보류하고 추후 명사구/복합 개념 중심으로 다시 설계한다.

### Time

처음에는 `KPF-BERT-NER`의 시간 label을 재사용했다.

- Overlap Recall: `0.94`
- 시간 표현 자체는 잘 찾음
- 복합 span과 TIMEX3 type 분류는 부정확

Normalization에 사용한 `dateparser`는 정확도가 약 `14%`로 낮아 제외하기로 했다.

이후 AI Hub `71613 시간 표현 탐지 데이터`와 가이드라인을 확보했다.

이 데이터는 다음을 제공한다.

```text
TIMEX3
EVENT
TLINK
```

TIMEX3에는 `DATE / TIME / DURATION / SET`, span, 정규화된 `value` 등이 포함되며 DCT(Document Creation Time)를 이용한 한국어 상대시간 처리 기준도 확인할 수 있었다.

또한 공식 `KoBERT / KoELECTRA` 기반 TIMEX3·EVENT·TLINK 모델도 제공하므로, 다음 단계에서는 KPF를 바로 확정하지 않고 AI Hub 공식 모델과 동일 Gold 기준으로 비교하기로 했다.

## 2026-08-28 — Backend 아키텍처 설계

Spring Boot, FastAPI, MySQL, Neo4j의 역할과 데이터 흐름을 정리했다.

### 서버별 역할

```text
Frontend / 수집기
→ Spring Boot
→ MySQL·Neo4j·FastAPI
```

* `Spring Boot`

  * 전체 화면 API
  * 인증·회원·기사·열람 기록 관리
  * MySQL 읽기·쓰기
  * Neo4j 읽기
  * FastAPI 분석·추천 요청
  * 최종 응답 조합

* `FastAPI`

  * 기사 정보 추출
  * Event Matching과 Story 연결
  * 추천 계산과 근거 생성
  * Neo4j 읽기·쓰기

그래프 수정은 FastAPI만 수행하고, Spring Boot에는 Neo4j 읽기 권한만 제공한다.

### 데이터 저장

벡터 검색은 Neo4j Vector Index가 담당하므로 RDB는 `MySQL 8.4 LTS`를 사용하기로 했다.

```text
MySQL
→ 사용자, 기사 원문, 관심·비관심
→ 열람·추천 기록, 분석 상태, 트렌드

Neo4j
→ Article 참조 Node
→ Event·Story·Entity·Concept
→ 관계·근거·임베딩
```

### 기사 수집·분석

```text
수집기 → Spring Boot
→ MySQL에 Article 저장
→ FastAPI 분석 요청
→ 기존 Event 조회·Matching
→ Neo4j에 KG 저장
→ MySQL 분석 상태 갱신
```

Chunk, EventMention, 임베딩 등 중간 데이터는 FastAPI 메모리에서 처리하고 최종 결과만 Neo4j에 저장한다. 비동기 처리와 작업 복구가 필요해지면 Redis를 검토한다.

### 사용자 탐색·추천

일반 화면 조회는 Spring Boot가 직접 처리한다.

```text
Spring Boot
→ MySQL에서 기사·사용자 정보 조회
→ Neo4j에서 Node·Edge 조회
→ 결과 조합
```

추천이나 정보 공백 계산이 필요한 경우에만 FastAPI를 호출한다.

```text
Spring Boot → FastAPI
→ Neo4j에서 후보 탐색
→ 추천 articleId·점수·근거 반환
```

### 사용자 지식 그래프

초기에는 사용자가 읽은 기사만 MySQL에 저장한다.

```text
user_id
article_id
read_at
```

개인 그래프 요청 시 해당 articleId와 연결된 공용 KG를 Neo4j에서 조회한다. 성능 개선이 필요하면 `node_type`, `node_key`, `acquired_at`을 추가한다.

`node_key`에는 Neo4j 내부 ID가 아니라 FastAPI가 생성한 `eventId`, `storyId` 등의 UUID를 사용한다.

### 오늘의 트렌드

Spring Scheduler가 하루 두 번 Neo4j에서 `Article-COVERS→Event` 수를 집계한다.

```text
Neo4j Edge 집계
→ 상위 Event 선정
→ MySQL에 스냅샷 저장
→ Frontend 요청 시 최신 결과 반환
```

### API 경계

```text
Frontend → /api/v1/** → Spring Boot
수집기 → /internal/v1/ingestions/** → Spring Boot
Spring Boot → /internal/v1/** → FastAPI
```

초기에는 내부 HTTP로 연결하고 메시지 큐는 사용하지 않는다.
