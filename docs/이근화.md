# TIL - 2026-08-27

## 1. 온톨로지(그래프 스키마) 정리

- **Story**: 기존 Issue/Story를 하나로 통일. 여러 Event를 장기 흐름으로 묶는 단위.
- **Event**: 실제 발생한 사건만 해당. 전망·주장은 Event가 아니라 **Statement**로 분리.
- **Entity 관계**: `INVOLVES` 하나로 뭉치지 않고 `ACTOR`/`TARGET`/`PLACE`로 세분화.
- **Topic**: 정치/경제/사회/생활문화/IT과학/스포츠엔터 고정 6개만 사용, AI가 임의 생성 안 함.
- **Event-Event 관계**: `CAUSES`, `RESPONDS_TO` 두 가지만 사용. 단순 시간 선후관계는 Edge로 안 만듦.
- **Concept**: Topic(뉴스 대분류)과 구분되는, 사건 이해에 필요한 지식/용어(지진, 기준금리 등).
- 전체 파이프라인: Article → NER/Concept/시간 추출 → Event Candidate → 기존 Event 매칭 →
  Story 매칭/Topic 분류 → Relation Extraction → Neo4j 반영

## 2. NER 모델 비교 (Entity 추출 단계)

4개 모델(KPF, monologg, chunwoolee0, taengk) 테스트 → **KPF-bert-ner이 confidence·속도·
라벨 세분화(67종) 전부 1위**. taengk는 confidence 0.227로 제외.

중간에 라벨이 `LABEL_0`처럼 깨져 나온 문제를 두 번 겪었음:
- KPF는 실제 라벨 매핑 파일(`label.py`)을 적용
- monologg는 라벨 표기가 표준(`B-PER`)이 아니라 접미사(`PER_B`) 방식이라 병합 로직을 고쳐서 해결


## 3. Event/Statement 추출 착수

Event 추출은 NER과 달리 고정 라벨 분류가 아니라서 한국어 전용 모델이 사실상 없음.

후보 문장을 최종 Event/Statement로 구조화하는 방식은 아직 미결정 (직접 Gold 데이터
만들어서 파인튜닝 / 규칙 기반 + 의존구문분석 / 기타 — 나중에 판단).

LQ-FSE는 태그상 `finance` 도메인 특화로 보여서, 우리 9개 카테고리 전반(특히
스포츠/엔터)에서도 후보선별이 잘 되는지 검증이 먼저 필요함. LQ-FSE 하나로는 부족할
가능성이 있어서, **다른 한국어 Event/문장유형 분류 모델을 추가로 더 찾아봐야 함**

```text

   ↓
Spring Boot
   ├─ MySQL

          ↓
       FastAPI
          ├─ AI Model
```

### 2. MySQL ERD 구조 정리

MySQL은 서비스 운영에 필요한 사용자·기사·행동 로그·트렌드 데이터를
관리하고, Neo4j는 기사에서 추출한 의미 관계와 지식그래프를 관리하도록

-   **사용자 영역**
    -   `users`: 회원 기본 정보 및 계정 상태 관리
    -   `user_topic_preferences`: 사용자의 관심/비관심 Topic 관리
-   **기사 영역**
    -   `news_sources`: 언론사 및 뉴스 출처 정보 관리
    -   `ingestion_runs`: 뉴스 수집 작업의 실행 상태와 결과 관리
    -   `articles`: 기사 원문, 요약, 발행 정보, 분석 상태 등 서비스의
        기사 원본 데이터 관리
    -   `article_topics`: 하나의 기사에 연결된 복수 Topic 관리
-   **사용자 행동 영역**
    -   `article_reads`: 사용자가 읽은 기사와 최초·최근 열람 시각, 누적

    -   `user_node_interactions`: Entity·Event·Story·Concept 등 그래프

    -   `user_knowledge_nodes`: 사용자가 접한 지식 노드를 누적해 개인
        지식그래프 및 추천에 활용
-   **트렌드 영역**
    -   `trend_snapshots`: 특정 시점의 트렌드 집계 회차와 집계 범위 관리
    -   `trend_items`: 각 집계 회차에서 Event별 관련 기사 수와 순위·증감
        정보 관리

### 3. MySQL ↔ Neo4j 역할 분리

-   **MySQL**: 사용자, 기사 원문, 관심사, 열람 기록, 서비스 상태 등 정형
    데이터의 Source of Truth
-   **Neo4j**: Article, Event, Story, Entity, Concept, Statement 등의
    Node와 관계를 저장하는 지식그래프
-   Spring Boot는 MySQL을 중심으로 서비스 데이터를 관리하고 Neo4j의
    그래프 데이터를 조회한다.
-   FastAPI는 MySQL에 직접 접근하지 않고 기사 분석·추천·의미 검색과
    Neo4j KG 생성/갱신을 담당한다.
-   두 DB의 데이터는 `articleId`, `eventId`, `storyId` 등 업무 ID를
    기준으로 연결한다.

| 점수 결합 | 가중합 (두 신호가 같은 방향이라 섞어도 안전) | 1단계 하드 필터 → 2단계 가중합 (성격이 달라 단계 분리) |

## 후보 필터링 (공통, 두 추천 모두 적용)

1. 사용자가 아직 열람하지 않은 Event만
2. 비선호 Topic에 속한 Event 제외
3. Hop 거리 먼 Event 제외 (기준값 정해야 함)
4. 오래된 Event 제외 (날짜 범위 정해야 함)

이 4가지를 먼저 통과한 Event/Story 후보군을 대상으로 아래 각 추천 로직을 적용한다.

## 1. 관심 기반 추천 (INTEREST_BASED) — Content-based + Collaborative Filtering

### (1) Content-Based Filtering

> 사용자가 좋아한 콘텐츠와 "내용이 비슷한" 다른 콘텐츠를 찾아 추천하는 방식
>
- 사용자가 읽은/즐겨찾기한 Event들의 임베딩을 가중평균해서 "사용자 프로필 벡터" 생성
- 가중치: 최근성, 즐겨찾기 여부, 클릭 수 등 반영
- 이 벡터로 Vector 인덱스에서 유사한 Event 검색

### (2) Collaborative Filtering

> "이 사용자와 비슷한 소비 패턴을 보인 다른 사용자들"의 반응을 참고해 추천하는 방식
>
- `read_article_count`, `node_click_count`, `favorite_count` 등 암묵적 신호를
  사용자×아이템 상호작용 행렬로 구성
- Item-based CF로 계산 - Event끼리의 유사도를 미리 계산해두고, 사용자가 읽은 Event와 유사한 다른 Event를 추천하는 방식
  (User-based CF는 사용자 수가 늘수록 계산 비용이 급격히 커져서 제외했고, ALS는 사용자 상호작용 데이터가 충분히 쌓이면 추후 도입 검토)

### (3) 결합 + Cold Start 처리

> 위 두 점수를 하나로 합쳐 최종 추천 순위를 정하는 단계
>

```
final_score = w1 * 콘텐츠기반_점수 + w2 * CF_점수
```

## 2. 관심 확장 추천 (KNOWLEDGE_GAP) — Coverage + Collaborative Filtering

### 한 줄 요약

Story(사건 흐름) 단위로 읽은 비율(coverage)이 낮은 것을 걸러내고, 그 안의 안 읽은 Event를 coverage와 CF를 함께 반영해 정렬한다.

### Coverage 계산 기준

- `user_knowledge_nodes.read_article_count` 사용, `> 0`이면 "읽음"으로 이진 판정

```
coverage = Story 안에서 읽은 Event 수 / Story의 전체 Event 수
```

### 1단계 — Story 필터링 (하드 필터)

> "안 읽은 사건 흐름(공백)"에 해당하는 Story만 먼저 걸러내는 단계
>

```
coverage < 임계값(예: 30%) 인 Story만 후보로 통과
```

- 통과하는 Story가 너무 적으면 임계값을 완화(30% → 50%)해서 재시도

### 2단계 — Event 정렬 및 최종 노출 (가중합)

> 걸러진 Story들 안에서, 공백 정도와 인기도를 함께 반영해 순위를 매기는 단계
>

```
score = w1 * (1 - coverage) + w2 * CF_점수
```

- coverage가 낮을수록, 다른 사용자 반응이 많을수록 높은 점수
- CF 계산 로직 자체는 하나만 만들어서 두 군데서 재사용

### 왜 1단계(필터)와 2단계(가중합)를 분리하는가

coverage와 CF를 처음부터 하나로 합산하면, coverage가 높아도(이미 많이 읽은 Story) CF가
워낙 높으면 최종 점수가 역전될 위험이 있다 — "이미 다 읽은 것을 또 추천"하는 결과가
나올 수 있음. 1단계에서 coverage 임계값으로 먼저 자격 있는 후보만 남긴 뒤에만 2단계
가중합을 적용하므로, 이런 역전 문제가 구조적으로 발생하지 않는다.

### 참고

Calibrated Recommendation(추천 분포를 사용자 활동 분포에 맞추는 연구)과 Coverage 기반
다양성 연구를 참고해서 단순화한 것. 별도 ML 모델 학습 없이 집계 쿼리 + 기존 CF 로직
재사용만으로 구현 가능하다는 게 장점.
