# TIL - 2026-08-27

## 1. 온톨로지(그래프 스키마) 정리

- **Story**: 기존 Issue/Story를 하나로 통일. 여러 Event를 장기 흐름으로 묶는 단위.
- **Event**: 실제 발생한 사건만 해당. 전망·주장은 Event가 아니라 **Statement**로 분리.
- **Entity 관계**: `INVOLVES` 하나로 뭉치지 않고 `ACTOR`/`TARGET`/`PLACE`로 세분화.
- **Topic**: 정치/경제/사회/생활문화/IT과학/스포츠엔터 고정 6개만 사용, AI가 임의 생성 안 함.
- **Event-Event 관계**: `CAUSES`, `RESPONDS_TO` 두 가지만 사용. 단순 시간 선후관계는 Edge로 안 만듦.
- **Concept**: Topic(뉴스 대분류)과 구분되는, 사건 이해에 필요한 지식/용어(지진, 기준금리 등).
- 전체 파이프라인: Article → NER/Concept/시간 추출 → Event Candidate → 기존 Event 매칭 →
  Story 매칭/Topic 분류 → Relation Extraction → Neo4j 반영

## 2. NER 모델 비교 (Entity 추출 단계)

4개 모델(KPF, monologg, chunwoolee0, taengk) 테스트 → **KPF-bert-ner이 confidence·속도·
라벨 세분화(67종) 전부 1위**. taengk는 confidence 0.227로 제외.

중간에 라벨이 `LABEL_0`처럼 깨져 나온 문제를 두 번 겪었음:
- KPF는 실제 라벨 매핑 파일(`label.py`)을 적용
- monologg는 라벨 표기가 표준(`B-PER`)이 아니라 접미사(`PER_B`) 방식이라 병합 로직을 고쳐서 해결


## 3. Event/Statement 추출 착수

Event 추출은 NER과 달리 고정 라벨 분류가 아니라서 한국어 전용 모델이 사실상 없음.

후보 문장을 최종 Event/Statement로 구조화하는 방식은 아직 미결정 (직접 Gold 데이터
만들어서 파인튜닝 / 규칙 기반 + 의존구문분석 / 기타 — 나중에 판단).

LQ-FSE는 태그상 `finance` 도메인 특화로 보여서, 우리 9개 카테고리 전반(특히
스포츠/엔터)에서도 후보선별이 잘 되는지 검증이 먼저 필요함. LQ-FSE 하나로는 부족할
가능성이 있어서, **다른 한국어 Event/문장유형 분류 모델을 추가로 더 찾아봐야 함**

## 뉴스 지식그래프 서비스 백엔드 구조 정리

## 1. 전체 구조

우리 서비스는 Spring Boot와 FastAPI의 역할을 다음과 같이 분리한다.

```text
Frontend
   ↓
Spring Boot
   ├─ MySQL
   ├─ Neo4j 조회
   └─ FastAPI 호출
          ↓
       FastAPI
          ├─ AI Model
          └─ Neo4j 읽기·쓰기
```

### 역할 구분

| 구성 요소 | 주요 역할 |
| --- | --- |
| Spring Boot | 사용자·기사·행동 로그·서비스 API |
| FastAPI | AI 분석·KG 구축·추천 계산 |
| MySQL | 사용자·기사 원문·행동 데이터 저장 |
| Neo4j | Event·Story·Entity·Concept 등 KG 저장 |

---

## 2. Spring Boot 역할

- 인증·회원 관리
- 관심·비관심 분야 관리
- 뉴스 수집 및 원문 저장
- 뉴스 목록·상세·검색
- 기사 열람·저장·추천 노출·클릭 기록
- 기사 공개 및 분석 상태 관리
- Article / Event / Story 등 그래프 화면 조회
- 오늘의 트렌드 API
- FastAPI에 기사 분석·추천 요청
- MySQL과 Neo4j 결과를 조합해 Frontend 응답 생성

---

## 3. FastAPI 역할

- 기사 전처리
- Entity / Concept / EventMention / Statement / Time 추출
- Event Embedding 생성
- 기존 Canonical Event Matching
- Story 생성·갱신
- Event 간 관계 판별
- Neo4j Node / Edge 생성·갱신
- 추천 Candidate Generation
- Ranking 및 추천 근거 생성
- AI/KG 처리에 필요한 Neo4j 조회

---

## 4. Neo4j 접근 방식

```text
FastAPI → Neo4j READ / WRITE
Spring  → Neo4j READ
```

Spring도 기술적으로 Write가 가능하지만, KG 생성·수정 책임을 FastAPI에 모아 정합성을 관리한다.

---

## 5. 기사 수집·분석 흐름

```text
1. 뉴스 수집기
   ↓
2. Spring Boot로 기사 전달
   ↓
3. MySQL에 Article 저장
   - 상태: PENDING
   ↓
4. Spring → FastAPI 기사 분석 요청
   ↓
5. FastAPI에서 정보 추출
   - Entity
   - Concept
   - EventMention
   - Statement
   - Time
   ↓
6. Event Embedding 생성
   ↓
7. Neo4j에서 기존 Event / Story 후보 조회
   ↓
8. Event Matching 및 관계 판별
   ↓
9. 기존 Event라면 갱신
   신규 Event라면 새 Node / Edge 생성
   ↓
10. FastAPI → Spring 분석 완료 응답
   ↓
11. MySQL 상태 COMPLETED 변경
```

즉,

```text
Spring
= 뉴스를 가져오고 상태를 관리

FastAPI
= 뉴스 내용을 분석하고 KG로 변환
```

## 7. 추천 처리 흐름

사용자 행동 로그는 Spring/MySQL에서 관리한다.

```text

SAVE

```

추천 요청이 오면:

```text
Spring
↓
사용자 행동 정보 전달
↓
FastAPI
↓
사용자 관심 Entity / Concept / Event 계산
↓
Neo4j Graph Traversal
↓
Candidate Generation
↓
Ranking
↓
Top-K 추천
↓
Spring
↓
Frontend
```

구분하면:

```text
단순 그래프 조회
Frontend → Spring → Neo4j

추천 계산
Spring → FastAPI → Neo4j
```

## 오늘 한 일

### 1. Spring Boot ↔ FastAPI 내부 API 명세 정리

-   `POST /internal/v1/articles/analyze`
    -   기사 본문을 분석해 Entity, Event, Story, Concept, Statement 등의
        지식그래프 정보를 생성하고 Neo4j에 저장
    -   동일 `articleId` 재요청 시 중복 Node·Edge가 생성되지 않도록 멱등
        처리
-   `POST /internal/v1/recommendations/calculate`
    -   관심 Topic과 기사 열람 기록을 기반으로 추천 후보 계산
    -   이미 읽은 기사는 추천 후보에서 제외
    -   추천 결과를 Article 또는 Graph Node 단위로 반환하는 방안 검토
-   `POST /internal/v1/search/semantic`
    -   자연어 Query를 임베딩하고 Neo4j Vector Index를 이용해 유사
        Article·Event·Story 검색
-   `GET /health`
    -   FastAPI 프로세스의 기본 기동 상태 확인

### 2. MySQL ERD 구조 정리

MySQL은 서비스 운영에 필요한 사용자·기사·행동 로그·트렌드 데이터를
관리하고, Neo4j는 기사에서 추출한 의미 관계와 지식그래프를 관리하도록
역할을 분리했다.

-   **사용자 영역**
    -   `users`: 회원 기본 정보 및 계정 상태 관리
    -   `user_topic_preferences`: 사용자의 관심/비관심 Topic 관리
-   **기사 영역**
    -   `news_sources`: 언론사 및 뉴스 출처 정보 관리
    -   `ingestion_runs`: 뉴스 수집 작업의 실행 상태와 결과 관리
    -   `articles`: 기사 원문, 요약, 발행 정보, 분석 상태 등 서비스의
        기사 원본 데이터 관리
    -   `article_topics`: 하나의 기사에 연결된 복수 Topic 관리
-   **사용자 행동 영역**
    -   `article_reads`: 사용자가 읽은 기사와 최초·최근 열람 시각, 누적
        클릭 수 관리
    -   `user_node_interactions`: Entity·Event·Story·Concept 등 그래프
        노드 클릭 및 탐색 순서 기록
    -   `user_knowledge_nodes`: 사용자가 접한 지식 노드를 누적해 개인
        지식그래프 및 추천에 활용
-   **트렌드 영역**
    -   `trend_snapshots`: 특정 시점의 트렌드 집계 회차와 집계 범위 관리
    -   `trend_items`: 각 집계 회차에서 Event별 관련 기사 수와 순위·증감
        정보 관리

### 3. MySQL ↔ Neo4j 역할 분리

-   **MySQL**: 사용자, 기사 원문, 관심사, 열람 기록, 서비스 상태 등 정형
    데이터의 Source of Truth
-   **Neo4j**: Article, Event, Story, Entity, Concept, Statement 등의
    Node와 관계를 저장하는 지식그래프
-   Spring Boot는 MySQL을 중심으로 서비스 데이터를 관리하고 Neo4j의
    그래프 데이터를 조회한다.
-   FastAPI는 MySQL에 직접 접근하지 않고 기사 분석·추천·의미 검색과
    Neo4j KG 생성/갱신을 담당한다.
-   두 DB의 데이터는 `articleId`, `eventId`, `storyId` 등 업무 ID를
    기준으로 연결한다.

## 정리

오늘은 서비스 데이터가 MySQL과 Neo4j에 어떤 기준으로 나뉘어 저장되는지
ERD 구조를 정리하고, Spring Boot와 FastAPI 사이에 필요한 내부 API를
설계했다. 특히 FastAPI는 AI 및 그래프 처리에 집중하고 Spring Boot는
사용자·기사·행동 데이터와 최종 응답을 담당하도록 역할을 구분했다.
