# TIL — 별빛 뉴스 MySQL·Neo4j DB/ERD 설계 정리

> 기간: 2026-08-31 ~ 2026-09-01  
> 프로젝트: 별빛 뉴스  
> 담당: DB

## 학습 목표

MySQL 테이블을 기능에 필요한 최소 구조로 정리하고, MySQL과 Neo4j의 데이터 소유권 및 기사 분석 파이프라인을 구체화했다. 또한 온톨로지 초안을 그대로 구현하지 않고 실제 조회와 분석에 필요한 Neo4j 프로퍼티를 다시 설계하기로 했다.

---

## 1. DB별 역할

```text
Spring Boot
├─ MySQL 읽기·쓰기
├─ Neo4j 읽기 전용
└─ FastAPI 분석 요청

FastAPI
└─ Neo4j 읽기·쓰기
```

### MySQL

- 기사 원본과 서비스용 요약
- 회원 및 관심·비관심 분야
- 기사 열람 기록
- 개인 지식 노드 참조
- 기사·노드 즐겨찾기
- 수집 실행 이력과 트렌드 결과
- 기사별 AI 분석 상태

### Neo4j

- Article의 그래프 투영
- Canonical Event, Story
- Entity, Concept, Statement
- Topic, Time
- 노드 사이의 관계와 관계 생성 근거

EventMention은 Canonical Event를 만들기 위한 중간 결과이므로 최종 그래프 노드로 저장하지 않는다.

---

## 2. 기사 수집·분석 흐름

한 기사 안에서는 MySQL 원본 저장을 먼저 완료하고 FastAPI 분석을 요청한다.

```text
기사 수집
→ Spring Boot가 MySQL에 원본 저장
→ MySQL article_id 생성 및 COMMIT
→ FastAPI 분석을 비동기 작업으로 요청
→ FastAPI가 분석 결과를 Neo4j에 저장
→ Spring Boot가 MySQL analysis_status 갱신
```

MySQL 저장과 같은 기사의 FastAPI 분석을 동시에 시작할 수도 있지만, MySQL 저장 실패 시 원본이 없는 Neo4j 노드가 생길 수 있다. AI 분석 시간이 INSERT 시간보다 훨씬 길기 때문에 기사 내부 작업을 병렬화하기보다 기사 간 파이프라인을 병렬화하는 방향이 안전하다.

```text
기사 A: MySQL 저장 → FastAPI 분석 ─────────
기사 B:             MySQL 저장 → FastAPI 분석 ─────────
기사 C:                         MySQL 저장 → FastAPI 분석 ───
```

---

## 3. ID 정책

모든 노드에 UUID가 필수인 것은 아니다. 이미 안정적인 ID가 있으면 해당 값을 사용하고, FastAPI가 새로 생성하는 Canonical 객체에는 UUID를 사용한다.

| 노드 | 식별자 |
| --- | --- |
| Article | MySQL `articles.article_id` |
| Event | UUID |
| Story | UUID |
| Entity | UUID |
| Concept | UUID |
| Statement | UUID |
| Topic | 고정 `topicCode` |
| Time | `YYYY`, `YYYY-MM`, `YYYY-MM-DD` 형식의 `timeId` |

FastAPI가 만든 UUID는 해당 Neo4j 노드의 프로퍼티에 저장한다. 분석 응답으로 모든 UUID를 Spring Boot에 전달할 필요는 없다. Spring Boot는 그래프 조회 또는 사용자 행동이 발생했을 때 필요한 노드 ID만 전달받아 사용한다.

MySQL에는 다음처럼 필요한 Neo4j ID만 논리 참조로 저장한다.

```text
user_knowledge_nodes.graph_node_id
user_node_favorites.graph_node_id
trend_items.event_id
```

서로 다른 DB 사이에는 실제 FK를 만들 수 없으므로 Neo4j 노드 병합·삭제 시 참조 정합성 정책이 필요하다.

## 4. MySQL 테이블 정리

### 사용자

- `users`: 자체 로그인과 소프트 탈퇴 관리
- `user_interest`: 고정 6개 Topic에 대한 `INTEREST`, `DISLIKE` 관리
- 역할과 중복 상태 컬럼은 제거하고 `deleted_at`으로 탈퇴 여부 판단

### 기사 및 수집

- `news_organizations`: 정규화한 언론사 관리
- `ingestion_runs`: 데이터셋·GNews 수집 실행 결과를 최소 컬럼으로 기록
- `articles`: 기사 원본, 서비스용 요약, 분석 상태 저장
- 기사는 MySQL `BIGINT AUTO_INCREMENT` ID를 전체 파이프라인에서 사용
- 분석 완료 후 즉시 서비스에 제공하므로 별도 공개 상태 컬럼 제거
- 분석 상태는 `PROCESSING`, `COMPLETED`, `FAILED`, `DROPPED` 사용
- 추가 카테고리 테이블은 실제 입력 데이터에 복수 카테고리가 확인될 때 추가

`DROPPED`는 중복·본문 부족·데이터 문제 등으로 의도적으로 분석 대상에서 제외한 상태이며, `FAILED`와 구분한다.

### 사용자 행동

- `article_reads`: 사용자·기사별 최초/최근 열람 시각과 클릭 수 저장
- `user_knowledge_nodes`: 사용자가 접한 Neo4j 노드와 누적 정보를 저장
- 클릭 경로와 탐색 세션은 MVP에서 저장하지 않음
- 화면 상단의 탐색 경로는 프론트 상태로 처리

`read_article_count`는 개인 지도에서 많이 읽은 노드의 크기를 결정하는 집계값이다. `node_click_count`는 기사를 통한 간접 노출과 직접 노드 탐색을 구분하는 값이며, 향후 추천 가중치로 활용할 수 있다.

### 즐겨찾기

열람·노드 접촉과 즐겨찾기는 생명주기가 다르므로 별도 테이블로 분리한다.

- `user_article_favorites`
- `user_node_favorites`

즐겨찾기 해제 이력은 현재 요구사항에 없으므로 해제 시 행을 하드 딜리트한다. 이력이 필요해지면 별도 행동 로그를 추가한다.

### 트렌드

- `trend_snapshots`: 06:00·18:00 KST 트렌드 계산 상태
- `trend_items`: 스냅샷별 Event 기사 수·순위·증감률
- 각 스냅샷은 최근 24시간의 분석 완료 기사를 집계
- 일반적인 `created_at`, `updated_at`은 두지 않고 `snapshot_at`, `finished_at`으로 시각을 표현

## 5. Neo4j 설계 원칙

온톨로지 초안은 노드와 관계의 의미를 정하는 참고 자료로 사용한다. 실제 프로퍼티는 화면·쿼리·분석 파이프라인에서 필요한지 확인한 후 다시 결정한다.

프로퍼티마다 다음 내용을 확인한다.

1. 정확한 의미
2. 생성 주체와 원본 데이터
3. 화면 또는 Cypher 쿼리의 사용처
4. 필수·선택 여부와 타입
5. 갱신 및 노드 병합 정책
6. 제약조건과 인덱스 필요 여부

노드 자체의 사실은 노드 프로퍼티로, 두 노드 사이에서만 의미가 생기는 값은 관계 프로퍼티로 저장한다.

```text
Event.occurredAt                 → 노드 자체의 사실
Article-[COVERS].primary         → 해당 기사에서의 Event 중요도
Article-[COVERS].relevance       → Article과 Event 사이의 관련도
```

`confidence`, `relevance`, `similarityScore`는 모델이 실제로 생성하고 정렬·필터에 사용할 때만 저장한다. 점수의 계산 방식과 의미가 정의되지 않았다면 우선 제외한다.

Neo4j에서 선택 프로퍼티의 값이 없으면 `null` 값을 보관하는 것이 아니라 해당 프로퍼티 자체를 생성하지 않는다.

---

## 6. 현재 그래프 식별 흐름

```text
MySQL Article 저장
→ article_id를 FastAPI에 전달
→ 분석을 통과한 경우에만 동일 article_id의 Neo4j Article 생성
→ 신규 Canonical 노드에 UUID 생성
→ 기존 Canonical 노드와 일치하면 기존 UUID 재사용
→ 관계 생성 및 Neo4j 저장
```

MySQL에는 있지만 중복 또는 데이터 부족으로 Neo4j에는 없는 Article이 존재할 수 있다. Neo4j Article ID가 연속적일 필요는 없으므로 이 경우에도 MySQL `article_id`를 그대로 사용할 수 있다.

## 정리

MySQL은 기사 원본과 사용자·서비스 데이터를 관리하고, Neo4j는 FastAPI 분석으로 생성된 지식그래프를 관리한다. Article은 MySQL ID를 공유하고, 자연키가 없는 Canonical 노드에는 UUID를 사용한다. 앞으로는 온톨로지의 프로퍼티를 그대로 복사하지 않고, 각 노드와 관계를 실제 조회 목적에 맞춰 하나씩 다시 설계한다.

## 1. 전체 서버 구조

```text
React
  ↓
Spring Boot
  ├─ MySQL 8.4 LTS
  ├─ Neo4j 읽기 전용
  └─ FastAPI
      ├─ AI 모델
      └─ Neo4j 읽기·쓰기
```

### Spring Boot

사용자와 서비스 기능을 담당하는 주 백엔드 서버다.

- 인증 및 회원 관리
- 관심·비관심 분야 관리
- 뉴스 목록·상세·검색
- 열람 기록 저장
- 기사 공개 상태 관리
- 사용자 지식그래프 데이터 관리
- 오늘의 트렌드 관리
- FastAPI 호출
- 최종 응답 조합

### FastAPI

AI 모델과 공용 뉴스 지식그래프를 담당한다.

- 기사 전처리
- Entity·Concept·Statement 추출
- EventMention 추출
- Canonical Event 통합
- Story 생성·갱신
- Neo4j 그래프 생성·갱신
- 그래프 탐색 쿼리
- 추천 알고리즘 및 추천 근거 생성

### Neo4j 접근 권한

- FastAPI: 읽기·쓰기
- Spring Boot: 읽기 전용
- 그래프 노드와 관계 생성·수정은 FastAPI만 담당한다.

두 서버가 모두 Neo4j를 수정하면 중복 노드나 갱신 충돌이 발생할 수 있으므로 쓰기 주체를 FastAPI로 통일했다.

## 4. EventMention과 Event 구분

뉴스에서 사건을 추출할 때 처음부터 Event 노드를 생성하지 않는다.

```text
Article
→ EventMention 추출
→ 기사 내부 중복 표현 정리
→ 다른 기사의 EventMention과 동일 사건 여부 판별
→ Canonical Event로 통합
→ Neo4j Event 노드로 저장
```

### EventMention

- 개별 기사에서 추출한 사건 후보
- AI 파이프라인의 중간 데이터
- 최종 지식그래프 노드가 아님
- 파일이나 메모리에서 관리

### Event

- 여러 EventMention을 동일한 실제 사건으로 판단해 통합한 결과
- 최종 지식그래프 노드
- Neo4j에 저장
- Article과 `COVERS` 관계로 연결

기사 속 전망·주장·평가는 Event가 아니라 Statement로 분리한다.

---

## 5. 지식그래프 노드

공용 뉴스 지식그래프에는 기존 통합 온톨로지의 노드를 사용한다.

- Article
- Event
- Story
- Topic
- Entity
- Concept
- Time
- Statement

EventMention은 포함하지 않는다.

사용자 지식그래프는 공용 그래프를 MySQL에 복제하지 않고, 사용자가 접한 Neo4j 노드의 ID와 타입을 저장하는 방식으로 구성한다.

```text
user_knowledge_nodes
- user_id
- neo4j_node_id
- node_type
- article_count
- first_seen_at
- last_seen_at
```

화면을 구성할 때 Spring Boot가 MySQL에서 사용자별 노드 ID를 가져오고, Neo4j에서 실제 노드와 관계를 조회한다.

## 6. Topic 관리

Topic은 기존에 정한 6개 카테고리만 사용한다.

| 내부 코드 | 표시 이름 |
|---|---|
| `POLITICS` | 정치 |
| `ECONOMY` | 경제 |
| `SOCIETY` | 사회 |
| `LIFE_CULTURE` | 생활/문화 |
| `IT_SCIENCE` | IT/과학 |
| `SPORTS_ENTERTAINMENT` | 스포츠/엔터 |

DB에는 변경되지 않는 영문 코드를 저장하고, 화면 표시용 한글 이름은 별도로 관리한다.

MySQL과 Neo4j에서 동일한 Topic 코드를 사용하고 AI가 새로운 Topic을 생성하지 않도록 한다.

## 7. 뉴스 데이터 수집 방식

뉴스는 두 경로로 수집한다.

### 초기 데이터셋

- 제공받은 데이터셋 전체를 저장
- 기사 원문이 있으면 원문 전체 저장
- 데이터 정제 및 중복 제거
- Article ID 부여
- FastAPI AI 파이프라인 실행
- 초기 Neo4j 지식그래프 구축

### GNews API

- Spring Boot가 주기적으로 신규 기사 수집
- 가져올 수 있는 최대 길이의 본문 저장
- 전문을 가져올 수 없으면 수집기에서 생성한 요약 저장
- 관계형 DB에 Article을 저장한 후 FastAPI 분석 요청
- FastAPI가 Neo4j 지식그래프에 증분 반영

```text
전체 데이터셋
→ 초기 Article 및 KG 구축

GNews API
→ 신규 Article 저장
→ FastAPI 분석
→ 기존 Event와 통합
→ Story 및 그래프 갱신
```

## 8. Article 저장 정책

기사 출처에 따라 확보할 수 있는 내용을 저장한다.

```text
articles
- article_id
- ingestion_source
- external_article_id
- title
- content
- content_type
- summary
- summary_source
- summary_model_version
- original_url
- publisher
- published_at
- collected_at
- topic_code
- analysis_status
- summary_status
- created_at
- updated_at
```

### content_type 예시

- `FULL_TEXT`: 데이터셋 등에서 전문을 확보
- `TRUNCATED_TEXT`: GNews에서 일부 본문만 확보
- `SUMMARY_ONLY`: 본문 대신 수집기 요약만 확보

원문과 요약은 같은 컬럼에 혼합하지 않고 별도로 저장한다.

Neo4j의 Article 노드에는 전문을 중복 저장하지 않고 `articleId`, 제목, 링크, 발행 시각 등 그래프 탐색에 필요한 정보만 저장한다.

---

## 9. 뉴스 카드 구성

사용자가 지식그래프 옆의 뉴스 카드를 클릭하면 다음 정보를 보여준다.

- 뉴스 제목
- GMS 등을 이용한 뉴스 요약
- 뉴스 원문 링크

예상 응답 구조는 다음과 같다.

```json
{
  "articleId": "article-001",
  "title": "뉴스 제목",
  "summary": "요약된 뉴스 내용",
  "originalUrl": "https://example.com/news",
  "publisher": "언론사",
  "publishedAt": "2026-08-28T10:00:00Z"
}
```

GMS의 정확한 모델 또는 서비스 명칭은 추후 확인이 필요하다. DB 컬럼은 특정 서비스에 종속되지 않도록 `summary_source`, `summary_model_version`과 같은 일반적인 이름을 사용한다.

## 10. 실제 열람 판정

기존에는 클릭, 스크롤, 잔류 시간 등을 고려했지만 회의 결과 다음 기준으로 단순화했다.

> 지식그래프 옆의 기사 목록에서 뉴스 카드를 클릭하면 해당 기사를 읽은 것으로 판정한다.

따라서 MVP에서는 스크롤 깊이와 잔류 시간을 저장하지 않는다.

```text
뉴스 카드 클릭
→ Spring Boot에 열람 기록 요청
→ MySQL에 열람 기록 저장
→ 사용자 지식그래프 갱신
→ 뉴스 카드 내용 표시
```

예상 테이블은 다음과 같다.

```text
article_reads
- article_read_id
- user_id
- article_id
- first_read_at
- last_read_at
- click_count
```

`user_id`, `article_id` 조합에는 Unique 제약을 적용한다.

같은 기사를 다시 클릭하면 열람 행을 중복 생성하지 않고 `last_read_at`과 `click_count`를 갱신한다.

사용자 지식그래프에는 같은 Article을 여러 번 반영하지 않고, 고유하게 읽은 Article을 기준으로 지식 가중치를 계산하는 방안을 우선 고려한다.

---

## 11. 오늘의 트렌드

오늘의 트렌드는 Event별 관련 기사 수를 기준으로 계산한다.

```text
trendScore(Event)
= 해당 기간에 Event를 COVERS한 DISTINCT Article 수
```

- 하루 오전·오후 총 2회 갱신
- Spring Boot가 Neo4j를 읽어 Event별 기사 수 집계
- 집계 결과의 Event ID와 순위를 MySQL에 저장
- Event 이름과 설명은 Neo4j에서 조회

예상 테이블은 다음과 같다.

```text
trend_snapshots
- snapshot_id
- calculated_at
- period_type
```

```text
trend_items
- snapshot_id
- event_id
- article_count
- rank
```

정확한 오전·오후 실행 시각과 집계 구간은 추가 결정이 필요하다.

## 12. 개인화 추천

추천 알고리즘은 현재 지식그래프 관련 모델과 파이프라인을 구축하는 단계다.

예상 요청 흐름은 다음과 같다.

```text
React
→ Spring Boot
→ MySQL에서 관심·비관심 분야 및 열람 기록 조회
→ FastAPI에 추천 요청
→ FastAPI가 Neo4j 기반 추천 알고리즘 실행
→ 추천 결과와 연결 근거 반환
→ Spring Boot가 최종 응답 조합
→ React
```

알고리즘이 구현되면 실행 시간을 측정하고 다음 중 하나를 선택할 예정이다.

- 요청 시 동기 계산 후 즉시 반환
- 일정 시간 캐시
- 사전 계산
- 비동기 처리
- 추천 결과 이력 저장

현재 추천 결과의 MySQL 저장 여부는 확정하지 않았다.

---

## 정리

오늘은 별빛 뉴스의 DB 설계를 시작하기 전에 Spring Boot, FastAPI, MySQL, Neo4j의 역할과 데이터 소유권을 정리했다.

Spring Boot는 사용자 및 기사 서비스 데이터를 담당하고, FastAPI는 AI 처리와 공용 뉴스 지식그래프를 담당한다. MySQL에는 Article 원문과 사용자 관련 데이터를 저장하며, Neo4j에는 Article·Event·Story·Entity 등의 공용 지식그래프를 저장한다.

이제 현재 결정을 기준으로 MySQL ERD와 테이블 정의서를 작성할 수 있다.




# TIL: Event·Statement 라벨링 기준 구체화

**2026년 8월 27일**

오늘은 뉴스 기사에서 `Event`와 `Statement`를 일관되게 구분하기 위한 라벨링 기준을 구체화했다.

먼저 Gold 데이터 제작에 사용할 PoC 기사를 선별했다. 동일한 사건을 여러 기사가 보도한 사례와 내용은 유사하지만 실제로는 다른 사건인 사례를 함께 포함했다.

선별한 기사로 `poc_articles` 파일을 만들고, 본문을 문단 단위로 분리해 각 문단에 `chunkId`를 부여했다. 이후 각 문단이 라벨링 대상인지 확인하고, 대상이라면 실제 발생한 사건인 `Event`인지 전망·주장·평가에 해당하는 `Statement`인지 판정했다.

## 검토한 판정 기준

- 어떤 문장을 라벨링 대상으로 포함할 것인지
- 한 문장에 여러 사건이 있을 때 Event를 어떻게 분리할 것인지
- 과거 사건이나 배경 설명을 Event로 추출할 것인지
- 발표 행위와 발표 내용을 어떻게 구분할 것인지
- 전망·주장·평가를 Statement로 어디까지 포함할 것인지
- 표현은 다르지만 동일한 사건을 같은 Event로 통합할 것인지

예를 들어 “기준금리를 동결하겠다고 밝혔다”는 문장은 실제 금리 동결이 완료된 것이 아니다. 따라서 `금리 동결 방침을 발표한 행위`와 `향후 금리를 동결하겠다는 Statement`를 구분해야 한다.

작성한 `poc_articles`를 이용해 실제 Gold 데이터를 추출한 뒤, 결과를 검토하고 잘못되거나 모호한 라벨을 수정했다. 이 과정에서 발견된 사례를 다시 판정 기준에 반영하며 지침을 보완했다.

## 작업 흐름

```text
Event·Statement 판정 기준 초안 작성
→ PoC 기사 선별
→ 기사 본문 청킹
→ 라벨링 대상 문장 판별
→ Event·Statement 구분
→ Gold 데이터 추출
→ 라벨 검토 및 수정
→ 판정 기준 보완
```

## 정리

오늘은 완성된 기준을 단순히 적용한 것이 아니라, 실제 Gold 데이터를 만들어 보고 수정하는 과정을 반복하면서 Event와 Statement의 판정 기준을 구체화했다.
